# PoC開発計画 ── Claude Code で何を作り、何に気をつけるか

作成日：2026年9月13日 ／ 対象：2026年9月〜12月のPoC期

---

## 1. PoC設計に矛盾があります

先に指摘しておきます。事業計画ではPoCを「ローカル保存のみ」としていますが、**PoCの検証項目3つのうち2つが測れません。**

| 検証項目 | ローカル保存のみで測れるか |
|---|---|
| 予測の精度が実感と合うか | ○ ヒアリングで測れる |
| CSV取込が月1回続くか | **× 誰が何回取り込んだか分からない** |
| 予測が見えることに対価を払う意思があるか | △ ヒアリングのみ。行動では測れない |

2つ目が最重要です。事業計画では「月に一度のCSV取込が続かないこと」を最大の離脱要因としており、モデルの解約率はここに乗っています。それを測らずにPoCを終えると、**最も重い仮定が未検証のまま2027年のリリースに入ります。**

したがってPoCは**認証と最小限の計測を持つ**構成にします。Supabaseの無料枠で足り、費用はドメイン代程度です。「ローカル保存のみ」という前提は撤回してください。

---

## 2. 技術スタック

| 領域 | 選定 | 理由 |
|---|---|---|
| フレームワーク | Next.js 15（App Router）+ TypeScript | PoCから本開発へ作り直さずに済む。認証とAPIが同じ枠内 |
| スタイル | Tailwind CSS + CSS変数トークン | デザインシステムのトークンをCSS変数で持ち、Tailwindはレイアウトに使う |
| チャート | Recharts | プロトタイプで検証済み |
| 認証・DB | Supabase（Auth + Postgres） | 無料枠で認証・DB・RLSが揃う。PoCの計測にも使える |
| テスト | Vitest | 計算ロジックの単体テスト。これが本体 |
| ホスティング | Vercel | 無料枠 |
| 計測 | Supabaseのテーブルに自前でイベント記録 | 外部の解析ツールを入れない（資金繰りデータを扱うため） |

**Viteではなく Next.js を選ぶ理由。** PoCをViteで作ると、認証・DB・課金を足す段階で作り直しになります。いま3ヶ月分の手戻りを避けるほうが、AIで速く書けることより効きます。

**注意：計算はクライアント側で行います。** 残高予測は日次52ヶ月ぶんの累積計算です。サーバーで実行するとMAUに比例してコストが跳ねます（事業計画書 8.0.1）。Next.jsを使いますが、`src/core/` は完全にクライアントで動く純関数にしてください。

## 3. Claude Code に渡すもの

リポジトリに以下を置いた状態で始めます。

```
/
├─ CLAUDE.md                    ← 規約。別添
├─ docs/
│   ├─ 要件定義書.md              ← 仕様の一次情報
│   ├─ designsystem.md           ← デザイントークン
│   ├─ prototype/cashflow-app.jsx ← 参照実装（移植元・そのまま使わない）
│   └─ adr/                      ← 設計判断の記録
├─ src/
│   ├─ core/                     ← 計算ロジック（純関数）
│   └─ styles/tokens.css
└─ .env.example
```

**プロトタイプは参照実装として置き、そのまま本番に持ち込まないでください。** 1ファイル1,500行の単一コンポーネントで、テストがなく、状態管理もありません。移植するのは計算ロジックの考え方だけです。

## 4. タスク分解

PoCは13タスク。1タスク1PRで、上から順に進めます。

### フェーズ1：計算ロジックを固める（2〜3週）

| # | タスク | FR | 完了条件 |
|---|---|---|---|
| 1 | リポジトリ初期化、トークン定義、CLAUDE.md配置 | — | `pnpm dev` が起動する |
| 2 | 型定義とCL-1（予定インスタンスの展開） | FR-04 | AC-02 が通る |
| 3 | CL-2（カード引落ラグ）とCL-3（残高推移） | FR-08, FR-09 | AC-01 が通る |
| 4 | CL-4（家事按分）とCL-5（年月別収支） | FR-10, FR-14 | AC-03, AC-05 が通る |
| 5 | オーバーライド（支払繰延）とCL-6（月次資金繰り表） | FR-07, FR-13 | AC-04, AC-06 が通る |
| 6 | CL-7（CSV解析と自動照合） | FR-16 | AC-07 が通る |

**フェーズ1が最重要です。** ここでテストが揃えば、以降のUI変更で計算が壊れても検知できます。逆にここを飛ばしてUIから作ると、後から手が付けられなくなります。

### フェーズ2：画面を作る（3〜4週）

| # | タスク | FR | 完了条件 |
|---|---|---|---|
| 7 | アプリシェル（左ナビ、残高ヘッダー） | — | AC-09 が通る |

| 10 | 実績入力と消し込み、予定の設定 | FR-05, FR-06, FR-02, FR-03 | AC-03 が画面から再現できる |
| 11 | CSV取込画面 | FR-16 | Shift_JISのファイルが取り込める |

### フェーズ3：計測と配布（2週）

| # | タスク | FR | 完了条件 |
|---|---|---|---|
| 12 | Supabase認証、データ同期、RLS | FR-17 | 他ユーザーのデータが取得できないことを確認 |
| 13 | 利用イベントの記録（取込、予定登録、閲覧） | — | 下表の5指標が取れる |

### PoCで取る指標

| 指標 | 取り方 |
|---|---|
| 初回30日以内の2回目CSV取込率 | 取込イベントのユーザー別カウント |
| 登録後14日時点の予定登録件数（中央値） | 予定テーブルの件数をスナップショット |
| 3ヶ月以上先まで予定があるユーザーの比率 | 北極星指標の分母と分子 |
| 残高警告からの操作率 | 警告表示イベントと、直後の操作イベント |
| 週あたりのログイン日数 | セッション記録 |

外部の解析ツール（GA等）は入れません。資金繰りの金額が第三者に渡る経路を作らないためです。

### 合計

7〜9週。2026年9月着手なら11月中に配布まで届きます。12月はモニター運用と観測に充てられます。

## 5. 実開発における懸念

PoCの後、本開発に入るときに顕在化する問題を、影響の大きい順に並べます。

### 5.1 計算ロジックの静かな回帰 ── 最大の懸念

資金繰りの計算は**間違っていても動きます。** 残高が10万円ずれていても、画面はエラーを出さずに表示します。AIは「動くコード」を書くのは得意ですが、「正しい金額」かどうかは判断できません。

さらに厄介なのは、AIが既存テストを「実装に合わせて」書き換えてしまうことです。テストが赤いと直したくなるため、仕様のほうが正しいのに実装に寄せてしまう。

**対策。** `src/core/` を純関数で切り出し、受入基準AC-01〜17をテストとして固定する。CLAUDE.mdに「既存テストを実装に合わせて書き換える前に、仕様がどちらなのかを確認する」と明記する。フェーズ1を先にやる理由がこれです。

### 5.2 金額の丸めと浮動小数点

AIは平気で `amount * 0.25` と書きます。按分・利息・端数が絡む箇所で丸めを入れ忘れると、累積誤差が出ます。特に借入返済表は60回の積み上げなので、1円の誤差が60円になります。

**対策。** 円単位の整数で扱う規約を明文化。借入返済表は「元金合計が元本と一致する」ことをテストで保証する（AC-11）。

### 5.3 日付とタイムゾーン

プロトタイプは `new Date()` のローカル時刻に依存しています。サーバー側でも同じコードを動かすと、UTCとJSTで日付が1日ずれます。月末処理が絡むため、ずれると請求の締めや引落日の判定が壊れます。

AIは `toISOString()` を無意識に使います。これはUTC変換を伴うため、`2026-09-01` が `2026-08-31T15:00:00Z` になります。

**対策。** 日付は `'YYYY-MM-DD'` 文字列で持ち、UTC変換を伴うAPIを使わない。JST固定でタイムゾーンを設定項目にしない。

### 5.4 RLSの漏れ

Supabaseでテーブルを作ってRLSを有効化し忘れると、**全ユーザーのデータが誰からでも読めます。** AIはマイグレーションを書くときRLSを忘れがちです。テーブルが増えるほど確率が上がります。

このプロダクトでは他人の資金繰りが見える事故は致命的です。

**対策。** CLAUDE.mdに明記。加えて「RLSが無効なテーブルを検出するSQL」をCIに入れるのが確実です。

```sql
select tablename from pg_tables
where schemaname = 'public'
  and tablename not in (select tablename from pg_policies where schemaname = 'public');
```

### 5.5 属人性が「AI属人性」に置き換わるだけになる

事業計画では属人性割引としてマルチプルから0.8〜1.2を引いています。AIで書くと速いのですが、**「なぜこの設計なのか」を誰も説明できないコードが残ります。** 買い手から見ると、作った本人がいなくなったら終わる資産である点は変わりません。むしろ悪化します。

**対策。** ADR（設計判断記録）をコードと同じPRで残す。「却下した選択肢」まで書くのが要点です。これは売却時のデューデリジェンスで直接効きます。事業計画の成功要因9.6に対応します。

### 5.6 コンテキストの限界

要件定義書は3万5千字あり、計算ロジックは9本、データモデルは8エンティティあります。AIは一度に全部を保持できません。ファイルをまたぐ整合性（例：CL-2の引落日の計算とCL-9の入金日の計算は同じ構造）が崩れます。

**対策。** `core` をロジック単位のファイルに分ける。共通の日付ユーティリティを1箇所に置き、両方から呼ぶ。タスクを1PR単位に切る。

### 5.7 パフォーマンス

プロトタイプは毎レンダーで52ヶ月ぶんの日次計算をやり直しています。データが少ないうちは動きますが、実績10万件の要件（非機能要件5.1）では厳しくなります。

**対策。** 本開発では増分計算かWeb Workerが必要。ただしPoCでは不要です。**先に作り込まないでください。** 実測してから対処します。

### 5.8 スキーマ移行

PoCから本開発でデータモデルが変わります。特にビジネスプラン（借入・入金サイト）と代理操作権限を追加する段階で、既存データの移行が必要になります。AIに移行スクリプトを任せると、ロールバックできない形で壊れます。

**対策。** マイグレーションは必ず前方のみ（破壊的変更をしない）。列の削除はせず、使わなくなった列を残す。移行スクリプトは本番適用前にダンプで検証する。

### 5.9 依存の膨張

放置するとAIはライブラリを増やします。日付ライブラリ、状態管理、UIキット、バリデーション。増えるほど属人性が下がるように見えて、実際は「なぜこれを入れたのか」が分からない負債になります。

**対策。** 許可リストをCLAUDE.mdに置く。追加は着手前に相談。特に日付ライブラリは5.3の規約と競合するため入れません。

### 5.10 PoCコードを本番に持ち込む誘惑

動いているものを捨てるのは心理的に難しいです。しかし1ファイル1,500行の単一コンポーネントは、テストも状態管理もなく、本開発の土台になりません。

**対策。** 最初から「プロトタイプは参照実装、移植するのは計算ロジックの考え方だけ」と決めておく。この文書と CLAUDE.md に明記してあります。

## 6. 優先順位の結論

やるべき順に3つだけ挙げます。

1. **`src/core/` を純関数で切り出し、AC-01〜17をテストにする。** これがないとAIに任せられません。
2. **PoCに認証と最小限の計測を入れる。** ローカル保存のみでは最重要の仮定が測れません。
3. **ADRを最初のPRから書き始める。** 後から遡って書けません。

逆に、PoCでやらなくていいことを挙げると、パフォーマンス最適化、課金基盤、法人向け機能、税理士の代理操作、モバイル最適化です。3ヶ月で13タスクを終えるには、範囲を守ることが最も効きます。
