# 受入基準の充足状況

対象：要件定義書 v1.33（v1.0 分を凍結）の AC-01〜AC-53
作成日：2026年9月25日 ／ 最終更新：2026年9月28日

AC-38 が「掲げたが一部未実装」だったことを受けて、全件を洗い直した記録。

## 判定の基準

| 列 | 「済」と書ける条件 |
|---|---|
| 実装 | その条項を満たすコードが存在する |
| テスト | その条項を固定する自動テストが存在する。**テスト名に AC 番号があるだけでは足りず、条項そのものを検査していること** |
| 実機 | ブラウザで実際に操作して確認した |

- 3列すべてが埋まらないものは**未**と書く。推測で埋めない
- 複数の条項を持つ AC は条項ごとに判定する
- 実機確認が要らないと判断したものは、理由を備考に書く

### `lastReconciledAt` が保存されていなかった（修正済み）

**往復の確認で見つけた。** マイグレーション適用後に候補を確定したところ、`actuals` は正しく書かれたのに `settings.last_reconciled_at` が `null` のままだった。

原因は差分の判定である。

```ts
const settingsChanged =
  base === null ||
  base.asOf !== next.asOf ||
  base.reserveLine !== next.reserveLine;   // lastReconciledAt が無い
```

`markReconciled` は画面の状態を書き換えるが、差分が「settings は変わっていない」と答えるので保存されない。**基準日か防衛ラインを同時に変えないかぎり、`lastReconciledAt` は永久に null のままになる。**

FR-43 の警告は起点に `lastReconciledAt ?? asOf` を使う（AC-29a）。null のままだと起点が基準日に固定されるので、**どれだけ消し込んでも基準日から45日で「一度も消し込んでいません」が出て、以後ずっと消えない。** 消し込みを促す警告が、消し込んでも消えない。

項目名を並べて比べる書き方をやめ、**送る中身そのもの（`settingsPayload`）を比べる**ようにした。項目が増えても差分側を直す必要がない（CLAUDE.md §2.8）。回帰テストと、`SettingsRow` の項目が全部差分の対象になっていることを確かめるテストを足した。

修正後、候補の確定で `last_reconciled_at` が `2026-09-27` になることを実機で確認した。

### ダッシュボードが2つの残高系列を並べていた（AC-49、修正済み）

負荷試験アカウント（実績10万件・未消し込み456件）で、**同じ「9/28 時点の現預金」が2つの値で出た。**

| 場所 | 値 | 出どころ |
|---|---|---|
| ヘッダー「現預金残高（9/28）」 | 294,086,677 | `todayRow.act`（CL-3 手順4 実績系列） |
| ダッシュボード「現在」 | 294,086,677 | 同上 |
| 口座・カードの「現預金 合計」 | 297,590,377 | `sum(todayRow.byAccount)`（**予測系列**） |
| 「最低残高（予測）」 | 297,590,377 @ 9/28 | `min(row.proj)`（今日〜90日先） |
| ヘッダー「30日後／90日後」 | 335,994,827／400,553,550 | `row.proj` |

**どれも計算としては正しい。** 同じデータをローカルで組み直したところ、5つの数字も、要対応456件・60日以上前354件・最古1/1・カード未払13,227,873 も、すべて1円まで一致した。

差 **3,503,700** の正体も特定した。**未消し込みの予定457件（基準日〜今日）を現金化した正味**である。未消し込みの予定を除いたカードの基準日未払を0にして計算し直すと、ちょうど 3,503,700 になる。

- `byAccount` は `projectedCash` からしか積んでいない（`actualCash` のループは `d.act` しか触らない）。だから `sum(byAccount) === proj` は構造的に成立する。**口座別の実績系列は存在しない**
- 最低残高の窓は `row.date >= today` なので今日から始まる。系列自体は基準日から積む。単調増加なので最小値は今日になり、その値は今日の `proj`

**問題は値ではなく、2つの系列を同じ名前で並べていること。**「最低残高（予測）297,590,377 ／ 現在 294,086,677」は1文のなかで `proj` と `act` を比べており、90日の最小値が現在より大きいという読めない表示になる。ヘッダーも「現預金残高（act）→ 30日後（proj）」と系列をまたいでいる。**引き算の両辺が違う系列**（CLAUDE.md §2.10）で、CL-5 の差異で直したのと同じ形である。

**仕様に根拠が無い。** CL-3 手順4 は実績系列の用途を「**グラフ上で線を切る**」と書いているだけで、ヘッダーの現預金残高に使うとは書いていない。残高として定義されているのは手順3の予測系列で、手順3は未消し込みの過去予定を「除外すると残高を楽観視することになる」ため残すと明記している。

**予測系列に揃えた。** ヘッダー・「現在」・口座一覧・最低残高をすべて `proj` から取り、`act` はグラフの実線にのみ使う。決め手は2つ。

1. **口座別に実績系列が存在しない。** `sum(byAccount) === proj` が構造的に成立する以上、ヘッダーを `act` のままにすると口座一覧と永久に一致しない。一致させるには口座別の実績系列を作ることになり、系列が2つに増えて食い違う余地も2倍になる
2. CL-3 手順4 は実績系列の用途を「グラフ上で線を切る」としか書いていない

**ラベルも直した。** 未消し込みが456件ある状態で「現預金残高」と言い切るのは、アプリが持っていない精度を主張している。中身は「記録された分 ＋ まだ記録されていない予定額」なので「現預金 見込み」にした。

**差を捨てず、情報として出す。** 食い違いとして現れていたものを、利用者が一番知りたい形にする。符号を出すので、消し込むと残高が上がるのか下がるのかが分かる。要対応が0件のときは出さない。

```
現預金 見込み（9/28）  ¥1,201,000
うち未記録の予定 −¥5,000（1件）
```

計算は `unrecordedInBalance`（`src/lib/unrecorded.ts`）の1箇所だけに置き、ヘッダーとダッシュボードの両方がそこを呼ぶ。**両方で数え直すと片方だけずれる**（CLAUDE.md §2.8）。金額は予測系列と実績系列の差そのものを使い、数え直さない。件数は**予定日ではなく現金が動く日**で数える（金額が現金ベースなので、予定日で数えるとカード払いのぶんだけ対象がずれる）。

| 最低残高（予測） | ¥911,200 @ 10/23（**現在以下**） |

9/22 の電気代（変動）5,000 が未消し込み、9/30 の固定資産税 30,000 は現金が動く日が今日より後なので数えない。手計算と一致した。

### グラフのツールチップが同じ日に2つの残高を出していた（AC-49c、修正済み）

ヘッダーとダッシュボードで直したのと同じ欠陥が、グラフに残っていた。**直した場所の隣に同じ形が残っていることに、AC-49 の確認時に気づけていない。** 画面に出る数値を列挙せずに、直した箇所だけを見ていたため。

### 「未消し込みの予定」の件数が画面に3つあった（AC-49d、修正済み）

ダッシュボードに、同じ「未消し込みの予定」を数えた数字が3つ出る。母数はどれも `series.unmatchedForecast` で同じだが、**絞り方が3つとも違う。**

| 画面の表示 | 絞り方 | 出どころ |
|---|---|---|
| 実績が未入力の予定（N件） | `plan.date <= today`（**2026-11-13 まで `<`**。AC-72） | `dashboard.unfilled` |
| うち未記録の予定（N件） | `cashDateOf(plan) <= today` | `unrecordedInBalance` |
| 60日以上前の予定がN件 | `plan.date < today` かつ60日以上前 | `buildReconcileWarnings` |

3番目は閾値が違うので別の数字だと分かる。**1番目と2番目がほぼ同じ値になる。** 違うのは (a) 本日ちょうどの予定、(b) カード払いの予定（発生日は過ぎたが引落日が未来）の2点だけで、実機では 456 と 456 のように一致していた。

**(a) は 2026-11-13 に是正した**（AC-72）。1番目が `plan.date < today` で本日を外していて、**金額から飛んだ先に本日の予定が無かった。** 境界は `isUnrecordedOn` の1箇所で決める。**(b) は残っている** ―― そちらは §3.3 が「これは仕様である」と定めた差で、AC-72 の「一覧の合計が金額と一致する」条項と衝突している（上の AC-72 の行）。

それぞれの絞り方は理由がある。2番目は金額（`proj − act`、現金ベース）と対象を揃えるために現金の日で数えている。1番目は「消し込む対象」なので発生日で数えている。**どちらも単独では正しい。** しかしカード払いが多い月には値が割れ、利用者には同じものを数えた2つの数字が違って見える。

**v1.20 の決定：件数を出す場所を1箇所に限る**（AC-49d）。

| 表示 | 基準 | 出すもの |
|---|---|---|
| うち未記録の予定 | 現金日 | **金額のみ。件数を並べない** |
| 実績が未入力の予定 | 発生日 | 件数。**ここが唯一の件数** |
| 60日以上前の予定 | 発生日 | 閾値を明示した部分集合なので別に数えてよい |

金額は現金日で数えるしかない（`proj − act` と一致させるため）。その隣に発生日基準の件数を置いたのが誤りだった。**発生日は過ぎたが引落日が未来のカード利用は、件数には入るが金額には入らない。** 件数が金額の内訳ではない、という関係が成り立つ。

ヘッダーとダッシュボードの両方から件数を外した。`Unrecorded.count` は残してあるが、**「0件なら金額を出さない」の判定にだけ使い、表示しない**（型のコメントに明記）。

### 測定の読み方（resource timing の上限）

`performance` の resource バッファは既定250件で、**満杯になると新しい方が捨てられる。古い方が残る。** ブラウザで実験して確かめた（上限3に設定して6回リクエストし、残ったのは1〜3）。リングバッファではない。

このため、250件に当たった測定では次のように読む。

- 観測できた往復は**最初の N 件**であって、最後の N 件ではない
- 「最後の REST 完了 24,424 ms」は**250件目が終わった時刻**であり、読み込み完了の**下限**である。実際はもっと遅い
- 往復回数も下限値

**所要の合計と、最初の開始〜最後の完了の比は、同時に何本走っていたかを表す。** 10万件の実測（修正前）では 22,015 / 23,115 ≒ 0.95 だった。3本が並行していれば約3になるはずなので、**観測できた範囲では1本ずつ順に走っていた**ことになる。

### パースは律速ではない。遅いのは本文の転送（ローカル再現）

前回の実測（B、`count` なし）で 101往復に 28.7秒かかり、そのうち「1往復 中央値 104ms」は `await fetch()` の解決までだった。**`fetch()` は応答ヘッダを受け取った時点で解決するので、本文の受信も `JSON.parse` も含まない。** 差の約18秒が何かを、同じマシン上のローカル再現で切り分けた。

```
pnpm bench
```

| 段 | 所要 | 規模 |
|---|---|---|
| `JSON.parse` | 73 ms | 31.9 MB のテキスト |
| `toActual` の変換 | 4 ms | 10万件 |
| CL-1 展開 | 4 ms | 予定インスタンス 1,810 件 |
| CL-3 残高系列 | 140 ms | 日次 1,101 行 |
| ダッシュボード | 1 ms | — |
| **合計** | **221 ms** | |

**パース以降のメインスレッド作業は 0.2 秒である。18秒ではない。** 差の18秒は `JSON.parse` ではなく、**32MB の本文をネットワークから受け取る時間**と考えるのが筋が通る（320KB/ページ ÷ 180ms/ページ ≒ 1.8 MB/s）。

この区別が効くのは、**転送は並列化で縮み、パースは縮まない**からである。「並列化しても20秒が床」という読みは、18秒がパースであることを前提にしていた。その前提は成り立たない。

ただし転送が縮むかは、回線が飽和しているかによる。HTTP/2 は1本の TCP 接続を多重化するので、帯域で頭打ちなら並列にしても合計時間は変わらない。**`measure-console.js` の D（8ページを直列と並列で比べる）で実測してから判断する。**

再現の限界。ローカル再現は同じ機械（開発機）で動かしているので CPU は実機と同条件だが、(a) 32MB を1回でパースしており、実機の 320KB × 100回とは違う、(b) supabase-js のレイヤと React の描画を含まない、(c) 一覧画面が10万行を描く分は別勘定。

### 読む列だけを取る（`select("*")` をやめた）

転送が律速だと分かったので、送るバイト数そのものを減らす。どのテーブルも `created_at` と `updated_at` を持つが、`Row` 型にはどちらも無く、アプリは一度も読まない。`user_id` も読まない（行を絞るのは RLS の仕事）。

10万件で測った（`pnpm bench`）。

| | 生 | gzip |
|---|---|---|
| `select("*")` 相当・時刻が行ごとに違う（実利用） | 39.6 MB | 1.7 MB |
| `select("*")` 相当・全行が同じ時刻（投入SQL） | 39.6 MB | 1.0 MB |
| 読む列だけ | 27.3 MB | 1.0 MB |

**圧縮の有無で効きが変わる。**

- 非圧縮なら **−31%**
- 圧縮ありなら **−43%**（実利用）。生の削減幅より大きい。`created_at` は行ごとに違う値なので、本文のなかで最も圧縮が効かない部分を丸ごと落とすため

**この効果は実機では測れない。** 負荷試験の10万件は1利用者・1文で投入したので、`user_id` も `created_at` も `updated_at` も全行が同じ値になっている。gzip はどれもほぼ消すため、3列落としても圧縮後のバイト数が動かない（±0%）。

**正とする数字は上の表（生 −31% / 圧縮あり −43%）で、実機の測定結果ではない。** 実測が0%でも、実装が効いていないのではなく、試験データが一様であることの帰結である（CLAUDE.md §2.11）。

副次的に、これは負荷試験の測定にとっては都合がよい。**この変更が圧縮後のバイト数を動かさないので、同じ試験データで測るかぎり「3回→1回」の効果だけが数字に出る。** デプロイを戻さずに before と比較できる。

列の過不足は型で捕まえる。`Record<keyof Omit<Row, "user_id">, true>` はキーの過不足を許さないので、`Row` に項目を足すと `rows.ts` が型エラーになる（CLAUDE.md §2.8）。`*` に戻していないことは `fetch-all.test.ts` で見る（戻して落ちることを確認済み）。

**圧縮そのものが有効かは未確認。** `measure-console.js` の B が `Content-Encoding` を出す。非圧縮なら、列を絞るより圧縮を有効にするほうが桁が大きい。

### 実績の件数に頭打ちがない（仕様の修正が要る）

要件定義書 §5.1 は、10万件を超えても困らない理由をこう書いている。

**この締め処理は存在しない。** OI-6 は「基準日を後ろにずらす操作を許すか」であり、PoC 期の検討対象から外してある。`asOf` は不変の入力として扱っていて、前に進める経路はどこにもない。

したがって、**実績は基準日から積み上がり続ける。上限を作る仕組みが1つもない。**

| 使用年数 | 月300件として | 読み込み件数 |
|---|---|---|
| 1年 | 3,600 | 3,600 |
| 5年 | 3,600 × 5 | 18,000 |
| 10年 | 3,600 × 10 | 36,000 |

v1.0 の規模では問題にならない。**問題は、止まる仕組みが無いことを仕様が「ある」と書いている点である。** この記述があるかぎり、次に件数の議論をするときも同じ前提から始まってしまう。

仕様側で直すべき2箇所（記入は仕様の書き手）。

1. §5.1 の上記の一文 — 「締め処理で縮む」を削り、**「上限を作る仕組みは無く、基準日以降の件数は単調に増える」**に差し替える

### 取得の遅さ。before を測ってから直す（未修正）

**測る前に予測を書いておく。** 測ってから原因を考えると、後付けの説明になる。

`fetchAll`（`src/lib/supabase/fetch-all.ts`）は `for` ループの中で `await` するので、1,000件ずつ**直列**に取る。基準日 2026-01-01 に対して実績10万件がすべて範囲内なので、**ちょうど100往復**。テーブル間は `Promise.all` で並列だが、`actuals` の内側100往復が律速になる。RTT 50〜100ms なら **5〜10秒**で、照合の1秒より1桁大きいはず。

**独立した無駄がもう1つある。** `count: "exact"` を毎ページ付けているので、絞り込み後の10万行の COUNT が**100回**サーバー側で走る。必要なのは1ページ目だけである。

```ts
.select("*", { count: "exact" })
.range(offset, offset + PAGE_SIZE - 1);
```

外れたときに何が言えるかも書いておく。fetch が支配的でなければ、RTT が想定より速いか `count: exact` が想定より安いかで、そのときは照合の1秒が相対的に大きくなり索引が先になる。

直す方向（測定後に決める）。

| 対象 | 直し方 | 備考 |
|---|---|---|
| `count: exact` × 100回 | 1ページ目だけ数える | 並列化と独立に直せる |
| 100往復が直列 | 総件数を先に取り、範囲リクエストを並列に投げる | 順序は `range` の境界と並び替えキーで保証されるので、並列でも重複・欠落は起きない。並列度は上げすぎない（同時接続数とレート制限） |

**総件数を1回だけ取ると、取得中に別端末から行が増えた場合に最後の件数照合が空振りする。** FR-47 の検知はカナリアなので、そこで誤報を出すと信頼が落ちる。不一致のときは**全体を1回だけ取り直してから判定し、それでも不一致なら例外にする**（AC-35）。

**Max rows を上げる方向には寄らない**（ADR-0016 で却下済み）。

### 照合が総当たりで、10万件だとメインスレッドが1秒以上止まる（AC-48、未修正）

負荷試験の投入SQLに定期項目が無かったことを指摘され、同じ形のデータをローカルで組んで計算側だけ測った（Node、開発機）。

| 処理 | 所要 | 規模 |
|---|---|---|
| CL-1 展開 | 2 ms | 予定インスタンス 1,160 件 |
| 実績→イベント | 2 ms | 10万件 |
| CL-3 残高系列 | 101 ms | 未消し込み 1,160 件 |
| **FR-46 候補照合** | **1,015 ms** | 10万 × 1,160 の総当たり |
| FR-43 警告 | 0 ms | — |

**候補照合だけが突出している。** `findCandidates` が実績ごとに未消し込み予定を全件走査するため、比較回数が実績件数 × 予定件数になる。1,015ms は候補が0件（生成データの金額が偶然一致しない）の軽い側の数字で、ブラウザではこれより遅くなる。§5.1 の 300ms 目標の3倍以上であり、クライアント側計算（ADR-0003）ではメインスレッドが止まる。

CL-7 の照合条件は**金額の完全一致**を含むので、未消し込み予定を `Map<金額, 予定[]>` に入れれば実績1件あたり1回の引きで済む。日付±12日・口座・向きの判定は同額の数件にだけ走る。**索引側は「同額の候補を絞る」までを担当し、4条件の判定は引き続き `planMatches` を呼ぶ**（条件が増えたときに索引側を直さずに済む。CLAUDE.md §2.8）。

**実環境の before を取ってから直す。** ローカルの予測値だけでなく、10万件での実測を before / after で残す。

### 口座を削除してもオーバーライドが残っていた（AC-47、修正済み）

`removeAccount` は口座・定期項目・単発予定・実績を消すが、`overrides` を消していなかった。検証用のカードを画面から削除したところ、そのカード利用の繰延だけが残り、設定画面に「（元の予定が見つかりません）2026-10-05 へ」と出た。

計算には影響しない（`buildForecast` はインスタンスのキーで引くので、インスタンスが無ければ適用されない）。ただし**利用者が手で解除するしかない壊れた行が、口座を消すたびに増える。**

`plan_key` は外部キーではないので DB の cascade に任せられず、削除の範囲を手で並べるしかない。**並べる以上、並べ忘れは必ず起きる。** 一覧を `ACCOUNT_SCOPED_COLLECTIONS` として持ち、`AppData` の全コレクションと突き合わせるテストを置いた。コレクションが1つ増えたらそのテストが落ちる（CLAUDE.md §2.8）。

キーの形を読むのは `recurringKey` / `oneoffKey` / `planKeySource` の3つだけにしてある。

### AC-20 後半の文面が広すぎた（v1.18 で差し替え済み）

AC-20 は「TRF グループの費目が…月次資金繰り表の出金に含まれること」と書いているが、**口座間振替（TRF-01）は出金に含まれないのが正しい。** CL-3 手順6 が「振替は合計残高に対して増減0」と定めており、含めると入金・出金の両方が同額ふくらんで、月次資金繰り表が実態より大きく見える。

実機で確認した（本日 2026-09-27、合計残高ベース）。

| 月 | 出金（画面） | 内訳 |
|---|---|---|
| 2026-11 | **174,800** | 家賃100,000＋電気20,000＋電気5,000＋通信9,800＋**カード引落40,000** |
| 2026-12 | **134,800** | 同上からカード引落を除いたもの |

口座間振替30,000 は毎月あるが、どの月の出金にも入っていない。カード引落（TRF-04）は `type = expense` として生成されるので入る。

### 「2つの機構が同じ対象に当たるのに優先順位が書かれていない」箇所

CL-7 の照合×費目推定（下記、AC-45 で解消）と同じ形を探した。

#### 1. オーバーライドで動かしたカード利用の引落日 — **問題なし**

CL-2 手順2（引落日は利用日から求める）と FR-07（オーバーライド）は別々に定義されている。実装が元の利用日から計算していると、利用日を動かしても引落日が動かない。

実機で確認した。月末締め・翌月27日払いのカードに 9/20 の利用40,000を置き、**画面から**「払えなかった」で 10/5 に繰り延べ、再読込した。

| | 引落日 |
|---|---|
| 9/20 利用（9月締め） | **10/27** |
| 10/5 に繰延（10月締め） | **11/27** |

締めの月をまたいで1ヶ月動いた。`buildForecast` がオーバーライドを適用したあとに CL-2 が走るため、引落日は新しい発生日から数え直される。`override-deferral.test.ts` に同じ条件のテストを足した。

#### 2. FR-46 の候補を確定したときの費目 — **同じ形。AC-46 で解消**

`linkActualToPlan` は `key` と `unplanned` だけを書き換え、照合先の予定の分類を引き継いでいなかった。同じ画面の「予定どおり」（`settleAsPlanned`）は予定から全項目をコピーしており、**同じ「予定と実績を結びつける」操作が経路によって違う結果になっていた。**

v1.17 が §3.3 の前書きに原則を置いた。

> **分類は予定が持ち、事実は実績が持つ。**
> 費目・固定変動区分・事業割合は予定から、日付・金額・口座は実績から。

3つの経路（CL-7 の自動照合、FR-06 の「予定どおり」、FR-46 の候補確定）すべてが `applyClassification`（`src/core/classification.ts`）を通る。経路ごとに書き分ける余地を残さない。

**黙って上書きしない。** 変わった項目だけを文にして画面に出し、実績の編集から直せる（`unplanned` と同じ扱い）。変わらなかった項目は並べない。3項目のうち1つだけ変わったときに3つとも読ませると、どれが変わったのか分からなくなる。

#### 3. CL-7 の `matchPlan` と FR-46 の `isCandidate` が同じ4条件を別々に書いている — **解消**

優先順位の穴ではなく、**同じ規則を2箇所に書いている**ことによるずれの危険だった。AC-33 の「口座が一致」を両方に手で足したのがすでに危険信号で、次の条件は片方だけに入る。

`planMatches`（`src/core/csv.ts`）を唯一の定義とし、`matchPlan` と `isCandidate` の両方がそれを呼ぶ。`isCandidate` に残るのは候補提示の文脈にだけ要る除外（`key` がある・`unplanned` が立っている）だけ。**テストで一致を確かめるのではなく、食い違いが起きない形にした**（CLAUDE.md §2.8）。

### 照合が成立しても、照合先の予定の費目を引き継がない（AC-45、修正済み）

CL-7 は2つの仕組みを別々に定義している。

- **予定との自動照合**：金額・±12日・収支の向き・口座 で予定を探し、`key` を張る
- **費目の自動推定**：既存項目の**名称**の先頭4文字を摘要に部分一致させ、費目・固定変動・事業割合を引き継ぐ

**同じ対象に両方が当たったときの優先順位が書かれていなかったため、実装はこの2つを独立に動かしていた。** 照合が成立した行でも費目は名称からの推定に頼っていた。

v1.17 で CL-7 に優先順位を追記し、**照合が成立した行は費目・固定変動区分・事業割合を照合先の予定から引き継ぐ**ようにした。名称からの推定は照合が成立しなかった行にだけ当てる。金額は実績の値を使う。

実機で修正前後を比べた（Shift_JIS の銀行CSV、摘要は半角カナ）。

| 行 | 照合先 | 修正前 | 修正後 |
|---|---|---|---|
| 9/22 −5,000 | 電気代（変動） | 雑費／変動費／0% | **水道光熱費／変動費／50%** |
| 9/28 −220 | なし | 雑費／変動費／0% | 雑費／変動費／0%（変わらず） |
| 10/20 −100,000 | 事務所家賃 | 雑費／変動費／0% | **地代家賃・住居費／固定費／100%** |
| 10/25 +500,000 | 売上 | 事業売上／100%（推定が当たった） | 事業売上／100% |

修正前は次のようになっていた。

| | 照合先の予定（事務所家賃 10/20） | 取り込まれる実績 |
|---|---|---|
| 金額 | 100,000 | 100,000 |
| 費目 | 地代家賃・住居費 | **雑費** |
| 固定/変動 | **固定費** | **変動費** |
| 事業% | **100** | **0** |

**銀行CSVの摘要は半角カナなので、名称からの推定は原理的にほとんど当たらない。** 「事務所家賃」の先頭4文字は「ﾌﾘｺﾐ ｼﾞﾑｼｮﾔﾁﾝ」に含まれない。AC-07 が対象にしている Shift_JIS の銀行CSVが、まさに推定の効かないケースである。今回の4行でも、漢字の「売上」を含む1行だけが推定に当たり、残り2行は照合できているのに費目が雑費になった。

CL-5 への影響は合計では見えない。予定側は 地代家賃・固定費、実績側は 雑費・変動費 になるため、**差異は 地代家賃 +100,000（節約したように見える）と 雑費 −100,000 に割れる。** 収支は合う。事業スコープでは事業割合が 100 → 0 になるぶん、100,000 が事業から家計に移る。

照合先の予定は、名称の先頭4文字の部分一致より確実な情報である。誤った照合は確認画面で行ごとに直せるため、引き継ぎで固定してよい。

### 「実績」モードが未来月の実績を表示しない（修正済み）

`applyMode`（`src/core/pl.ts`）が `case "actual": return isPast ? actual : null;` になっており、今月より後の月にある実績が「実績」モードで消えていた。

CL-5 手順3（実績側は実績のみを集計する）には期間の限定が無い。過去／未来の切り分けは手順6 の `実績+予定` の定義に属するものであり、それが `実績` に漏れていた。**仕様違反として `return actual;` に修正した。**

未来日の実績は実在する。前払い、CSVの先日付行、そして最も多いのは**日付の打ち間違い**である。2027年と打ってしまった実績が画面から消えると、残高だけが合わない状態になって原因が追えない。

### 表示モードから期間の場合分けをなくした（AC-42・AC-44、修正済み）

4モードそれぞれに、期間の場合分けを持たない定義を与えた（ADR-0020）。`applyMode` は**引数に期間を取らない。**

| モード | 定義 |
|---|---|
| `予定` | 全予定インスタンス（手順2） |
| `実績` | 全実績（手順3） |
| `差異` | **両辺とも発生日が本日以前** |
| `実績+予定` | **本日までの実績 ＋ 未消し込みの予定インスタンス** |

CL-3 との整合を実機で確認した（本日 2026-09-26）。

| | CL-3 入出金予定表 2026年9月 | CL-5 実績+予定 2026年9月 |
|---|---|---|
| 入金 | +535,000 | 収入 535,000 |
| 出金 | −190,000 | 固定費 182,000 ＋ 変動費 8,000 |
| 収支 | 345,000 | 345,000 |

出金の内訳も一致する。実績4件（120,000・25,000・3,000・7,000）に、要対応リストに出ている未消し込みの2件（電気代（変動）5,000・固定資産税30,000）が足されている。

未来日の実績の検知は別の仕組みで扱う（OI-21）。

| 段階 | 差異の予定側 | 差異の実績側 | 画面に出た誤り |
