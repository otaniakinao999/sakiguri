## 1. 本書の位置づけ

### 1.1 目的

本書は、本サービスが満たすべき業務要件・機能要件・非機能要件を定義する。プロトタイプ（React 単一ファイル実装）で検証済みの計算ロジックを正式仕様として確定させ、実装・テスト・受入判定の基準とする。

### 1.2 スコープ

| 区分 | 内容 |
|---|---|
| 対象 | 資金繰り予測、予実管理、家事按分集計、CSV取込、支払繰延、借入返済スケジュール、取引先別の入金サイト |
| 対象外 | 仕訳・複式簿記、決算書作成、確定申告書の作成・電子申告、金融機関API連携、請求書発行、承認フロー、部門別予算、監査ログ（いずれも従業員20名超の要求であり対象外とする） |
| 想定利用者 | 個人事業主・フリーランス本人、ひとり社長〜従業員10名規模の小規模法人、税理士等の閲覧者 |

### 1.3 用語定義

| 用語 | 定義 |
|---|---|
| 基準日 | 残高計算の起点となる日付。この日の口座残高を入力値として与える |
| 定期項目 | 毎月または指定月に繰り返し発生する入出金の定義（マスタ） |
| 予定インスタンス | 定期項目を特定の日付に展開した1件の予定 |
| 単発予定 | 1回限りの入出金予定 |
| 実績 | 実際に発生した入出金 |
| 消し込み | 予定インスタンスに実績を紐づけ、予測から除外する操作 |
| オーバーライド | 予定インスタンス1件だけの日付・金額の変更、または当回スキップ |
| 家事按分 | 支出のうち事業経費として計上する割合（0〜100%） |
| 引落ラグ | カード利用日と、口座から引き落とされる日の差 |
| 発生ベース | 取引が発生した日で集計する見方（損益に用いる） |
| 現金ベース | 現金が実際に動く日で集計する見方（資金繰りに用いる） |
| 生活防衛ライン | 下回ると警告する残高の下限値。利用者が設定する。法人では「必要運転資金ライン」と読み替える |
| 入金サイト | 売上の締めから入金までの期間。取引先ごとに異なる（例：月末締め翌々月末払い） |
| 据置期間 | 借入金のうち、元金返済を行わず利息のみを支払う期間 |
| 元利均等返済 | 毎回の返済額（元金＋利息）が一定になる返済方式 |

## 2. 業務要件

### 2.1 ペルソナ

**P1：本業フリーランス（主要ターゲット）**
30〜45歳、事業所得が主たる収入。取引先2〜4社。事業口座と生活口座を分けている。クラウド会計ソフトを利用済み。年に数回の大型支出（予定納税、住民税、設備投資）で毎回ヒヤリとしている。

**P2：副業＋給与の兼業者**
給与収入があり事業所得は補助的。家事按分の比率が細かく、確定申告のたびに按分計算をやり直している。

**P3：小規模法人の代表（v2.0以降）**
従業員1〜10名。売上は取引先ごとに入金サイトが異なり、日本政策金融公庫からの借入がある。役員報酬と社会保険料が毎月固定で出ていく。決算書は税理士が作るが、来月の資金が持つかは自分で見ている。使っているのはExcelの資金繰り表。

**P4：税理士・記帳代行担当（v2.0以降）**
複数の顧問先の資金繰りを俯瞰したい。編集ではなく閲覧とコメントが中心。

### 2.2 主要な業務シナリオ

| ID | シナリオ | 頻度 |
|---|---|---|
| BS-1 | 初期設定：口座残高と定期的な入出金を登録し、予測を立ち上げる | 導入時1回 |
| BS-2 | 月次更新：銀行・カードのCSVを取り込み、予定を消し込む | 月1〜2回 |
| BS-3 | 予定追加：大型支出の予定が決まったら先に入れて残高への影響を見る | 随時 |
| BS-4 | 繰延判断：支払えない予定の日付をずらし、資金繰りが持つか確認する | 随時 |
| BS-5 | 予実レビュー：月次・年次で予定と実績の差異を確認する | 月1回 |
| BS-6 | 申告準備：事業側の年間集計を出し、会計ソフトの数字と突き合わせる | 年1回 |

### 2.3 業務フロー（BS-2 月次更新）

```
銀行CSVをダウンロード
      │
      ▼
[CSV取込] ファイル選択 ─→ 文字コード自動判定 ─→ 列マッピング（自動推定＋手修正）
      │
      ▼
明細の読み取り ─→ 費目の自動推定（過去の名称との部分一致）
      │         └→ 未消込の予定との自動照合（金額一致 かつ 日付±12日以内）
      ▼
確認画面で費目・事業割合・照合先を修正
      │
      ▼
一括登録 ─→ 照合済みの予定は予測から除外、実績として残高に反映
      │
      ▼
[ダッシュボード] 未消込の予定を確認 ─→ 必要なら繰延（オーバーライド）
```

### 3.1.1 仕様の確定度

**v1.0 の機能（FR-01〜FR-17、FR-34、FR-37〜FR-43、FR-46）は仕様が確定している。** 計算ロジックは 3.3 で定義済みで、プロトタイプで動作を検証している。

**v1.5 以降の機能（FR-18〜FR-33）は現時点の想定であり、仕様は未確定である。** 特に次の6点は設計判断が残っており、実装量と提供時期が振れる可能性がある。

| 機能 | 未確定な点 |
|---|---|
| FR-20 複数シナリオの比較 | シナリオの保持方法。オーバーライドをシナリオ単位で持つか、データ全体を複製するか。前者は軽いが分岐の深いシナリオを表現できない（OI-12） |
| FR-21 納付積立の算出 | 消費税の計算方式。本則課税・簡易課税・2割特例で算出が変わる。どこまで対応するか |
| FR-24 借入返済スケジュール | 繰上返済・借換の扱い。既存スケジュールを打ち切って作り直すか、履歴として残すか（OI-7） |
| FR-27 請求データの登録 | 手入力させるか、請求書発行サービスのCSV取込に寄せるか。後者は連携先ごとの対応が必要（OI-8） |
| FR-32 必要調達額の算出 | 借入は返済という新たな支出を生むため反復計算になる。収束条件と提示方法が未定義 |
| FR-33 資金繰り表のPDF出力 | 様式。日本政策金融公庫と民間金融機関で求められる項目が異なる。どこまで汎用化するか（OI-11） |

このうち FR-32 と FR-33 は**プロプランの価格を正当化する中核機能**であり、FR-24 と FR-27 は**ビジネスプランの存在理由そのもの**である。仕様が固まらないまま価格を先に確定させると、提供内容と価格が乖離する。**両プランの提供時期は、これらの設計が完了した時点で確定させる。**

### 3.1.2 費目マスタ

#### 資金移動（TRF）

| コード | 費目 | 生成 | 説明 |
|---|---|---|---|
| TRF-01 | 口座間振替 | 手動 | 口座間の資金移動 |
| TRF-02 | 事業主貸 | 手動 | 事業口座から生活口座へ |
| TRF-03 | 事業主借 | 手動 | 生活口座から事業口座へ |
| TRF-04 | カード引落 | **自動** | CL-2 が生成する。利用者は作成・編集できない |
| TRF-05 | 借入実行 | 手動 | 借入金の入金 |
| TRF-06 | 借入返済（元金） | **自動** | CL-8 が生成する元金充当分 |
| TRF-07 | 消費税の納付積立 | 手動 | v2.0 |

**CL-8 の返済1回は2件のイベントに分解する。** 元金充当分は TRF-06、利息分は EXP-15（支払利息）。これにより、資金繰りには合算額が出て、損益には利息のみが出る。

#### 適用規則

1. **費目と固定／変動は独立した属性である。** 費目マスタの `推奨` は新規登録時の初期値にすぎず、利用者は項目ごとに変更できる。同一の費目が固定費と変動費の両方に出現しうる（例：定額制の電気契約を固定費、従量制を変動費として登録した場合）。
2. **CL-5 のグルーピングは `(type, costType)` で決まる。** 費目はそのグループ内で、このマスタの掲載順に並べる。金額の大小で並べ替えない。
3. **表示順はコードの昇順とする。** 利用者による並べ替えは v1.0 では提供しない。
4. **v1.0 では利用者が費目を追加・削除できない。** 足りない場合は EXP-20 雑費 または INC-07 その他収入 を使う。ユーザー定義費目は v1.5 の検討事項（OI-13）。
5. **TRF グループは CL-5 の集計対象外。** CL-3 の現金計算には含める。
6. **収入に固定／変動の区別を設けない。** `costType` は `type = EXP` のときのみ意味を持つ。
7. **費目マスタは事業割合（`bizRatio`）を持たない。全費目の初期値は 0 とする。** 固定／変動は費目の性質でほぼ決まる（食費は変動、家賃は固定）ため推奨値に意味があるが、事業割合を決めているのは費目ではなく**利用者の事業形態**である。同じ通信費でも専業なら80%、副業なら20%になる。マスタに持たせると全員に同じ値を押し付けることになるため、持たせない。この非対称は意図したものであり、揃える必要はない。費目ごとの推奨値をオンボーディングで当てる案は v1.5 の検討事項（OI-14）。

**取引先×月のマトリクス（FR-44）は独立したエンティティではない。** 予定インスタンス（CL-1 の出力）を「取引先 × 発生月」でピボットした**表示**であり、実体は既存の定期項目と単発予定である。したがって正本はつねに定期項目・単発予定の側にあり、両者の同期は発生しない。

| 操作 | 実体への作用 |
|---|---|
| 空セルに金額を入れる | 単発予定（収入）を1件作成する |
| 単発予定由来のセルを直す | その単発予定を更新する |
| 定期項目由来のセルを直す | **当該回のオーバーライド（FR-07）として保存する。** 他の月には波及しない |
| セルを消す | 単発予定由来なら削除。定期項目由来なら当回スキップ（FR-07） |

定期項目を表示元に含めるのは、毎月定額の顧問契約を定期項目で登録している取引先が、マトリクス上で0と表示されるのを防ぐためである。同じ理由で、**取引先が未設定の収入は「未設定」行に集計して表示する**（AC-32）。マトリクスに現れない収入があると、マトリクスの合計と年月別収支の収入が一致せず、どちらが正しいのか利用者に判断できない。

実績側は、消し込み済みの実績を同じ軸で集計する。実績の取引先は消し込み時に予定から継承する（`settleAsPlanned` が予定の項目をコピーする既存の挙動に従う）。

**v1.0〜v1.5 では入金サイトの自動計算を行わない。** 入金日は利用者が決める。定額・定日の取引先は定期項目で吸収できるため手入力は発生せず、手入力が必要になるのは変動額で請求する取引先に限られる。その負担が実利用で問題になるかどうかで FR-26 の前倒しを判断する（OI-18）。

### 3.3 計算ロジック仕様

#### CL-1 予定インスタンスの展開

1. 対象期間の各月について、`months` が null または当月を含む場合に1件生成する。
2. 発生日は `min(day, その月の末日)` とする。`day = 31` は自動的に月末になる。
3. 単発予定はそのまま1件とする。
4. 各インスタンスにオーバーライドを適用する。`skipped` なら除外、`date` があれば日付を差し替え、`amount` があれば金額を差し替える。元の日付は `origDate` として保持し、UI で「◯/◯ ← ◯/◯」と表示する。
5. 期間外に出たものを除外し、日付昇順で整列する。

#### CL-2 現金イベントへの変換（カード引落ラグ）

入力：予定インスタンスと実績を合わせたイベント列。出力：口座残高を動かすイベント列。

1. イベントの `accountId` が `kind = card` の口座を指し、かつ `type ≠ transfer` の場合、これを**カード利用**とみなし、口座残高を動かさない。
2. カード利用の引落日を次式で求める。
   - 利用日の日 ≤ 締日 → 締め月 = 利用月。それ以外 → 締め月 = 利用月 + 1ヶ月
   - 支払月 = 締め月 + `payMonthOffset`
   - 引落日 = `min(payDay, 支払月の末日)`
3. `(カードid, 引落日)` ごとに金額を合算する。支出は正、返金（カードへの入金）は負として相殺する。
4. カードの基準日時点の未払額を、次のように引落日に割り当てる。
   - `balance`（次回の引落額）→ 基準日以降で**最初に**到来する引落日
   - `unbilledBalance`（未確定の利用額）→ その**次に**到来する引落日。未入力なら0

   **単一の値をまとめて最初の引落日に加算してはならない。** 締め翌月払いのカードでは、基準日時点で「締め済みで次回引落を待つ束」と「まだ締まっていない束」の2つが同時に未払として存在する。これを1つにまとめて最初の引落日に載せると、**最大1ヶ月ぶんの支出を前倒しで計上する。** 近い将来の残高が実際より低く出るため、防衛ラインの警告が誤って鳴る。2つの値はいずれもカード会社の明細に「確定金額」「未確定分」として並んで表示されるため、利用者が読み取って入力できる（AC-36）。

   なお、`payMonthOffset = 2`（翌々月払い）では未払の束が3つになりうるが、2項目では表現できない。この場合の3束目は `unbilledBalance` に含めて2回目の引落日に載せる近似とする（OI-19）。
5. 合算が0でないものについて、引落イベントを生成する。属性は `type = expense`（合計が負なら income）、`accountId = settleAccountId`、`src = 'settle'`。
6. カード以外のイベントと引落イベントを結合し、日付昇順で返す。

**例：** 締日15日／翌月／支払日10日のカードで 8/20 に利用 → 8/20 は 15日を超えるため締め月は9月 → 支払月は10月 → 引落日は10/10。

#### CL-3 残高推移の算出

1. 現金・銀行口座の基準日残高を合計し、開始残高とする（カードは含めない）。
2. 実績のうち `key` を持つものを収集し、そのキーを持つ予定インスタンスを予測から除外する（＝消し込み）。
3. **予測系列** = 実績 + 未消込の予定インスタンス を CL-2 で現金イベント化し、基準日から日次で累積する。
4. **実績系列** = 実績のみを CL-2 で現金イベント化し、基準日から日次で累積する。今日（または最終実績日のうち遅い方）以降は null とし、グラフ上で線を切る。
5. 口座別系列とカード未払残高系列も同様に日次で保持する。
6. 振替（`type = transfer`）は合計残高に対して増減0、口座別では送金元をマイナス・送金先をプラスとする。

**未消込の過去予定の扱い：** 実績が入力されていない過去の予定は、予定額のまま予測に残す。除外すると残高を楽観視することになるため。UI では「実績が未入力の予定」として件数と一覧を提示し、消し込みを促す。

**二重計上の回避（FR-46）。** 手順2の除外は `key` の一致のみで行う。したがって **`key` が null の実績は、同じ取引を指す未消込の予定を除外しない。** 同一の支出が予定額と実績額の両方で残高から引かれ、残高が実際より低く出る。これは CSV取込の自動照合（CL-7）が外れた行と、予定を使わずに手入力した実績で通常運用中に発生する。

同一取引かどうかを日付・金額から**自動で判定して除外してはならない。** 金額の突き合わせを推定で行うと、利用者が気づけない誤りを残高に混ぜることになる。代わりに、`key` が null の実績に対して CL-7 の照合条件（金額一致 かつ 日付±12日以内 かつ 同一口座）を適用し、**候補として提示して利用者に確認させる。** 確認された時点で `key` を張り、以降は手順2で除外される。確認されるまでは二重計上のまま残し、その旨を画面に表示する。

自動スキップによる解消は OI-4 の検討対象であり、v1.0 では行わない。

#### CL-4 家事按分の適用

損益集計時にのみ適用する。資金繰りには適用しない（現金は全額動くため）。

| 集計対象 | 計上額 |
|---|---|
| 合算ビュー | `amount` の全額 |
| 事業ビュー | `amount × bizRatio ÷ 100` |
| 家計ビュー | `amount × (100 − bizRatio) ÷ 100` |

按分後の金額が0となる項目は、そのビューの明細に表示しない。

#### CL-5 年月別収支（予実マトリクス）の集計

1. 対象は `type ≠ transfer` かつ `src ≠ settle` のイベントのみ。振替とカード引落は損益ではないため除外する。
2. **予定側**は、消し込み済みかどうかに関わらず、オーバーライド適用後の全予定インスタンスを集計する（＝当初予算を保つ）。
3. **実績側**は実績のみを集計する。
4. 集計日は**発生日**（カードは利用日）とする。CL-3 の現金ベースとは日付が異なる。この差異は仕様であり、画面上に明記する。
5. 行は 収入／固定費／変動費 の3グループ、その下に費目を並べる。列は1〜12月と年計。
6. 表示モードは4種：`実績+予定`（過去月は実績、未来月は予定）、`予定`、`実績`、`差異`。差異は収入なら `実績 − 予定`、費用なら `予定 − 実績` とし、正の値を良い方向（緑）とする。

#### CL-6 月次資金繰り表

CL-3 の予測系列と現金イベントから、月ごとに以下を算出する。

| 列 | 算出方法 |
|---|---|
| 前月繰越 | 前月の月末残高。初月は 月末残高 − 当月入金 + 当月出金 |
| 入金 | 当月の現金イベントのうち `type = income` の合計 |
| 出金 | 同 `type = expense` の合計（カード引落を含む） |
| 収支 | 入金 − 出金 |
| 月末残高 | 当月末日の予測残高 |
| 月中最低 | 当月の日次予測残高の最小値 |

月中最低が生活防衛ラインを下回る月には、その日付と種別（防衛ライン割れ／資金ショート）を注記する。

#### CL-7 CSV取込

**文字コード判定：** UTF-8 で厳格デコードを試み、失敗した場合 Shift_JIS でデコードする。先頭の BOM は除去する。

**列の自動推定：** ヘッダ行に対し以下の正規表現でマッチさせる。

| 用途 | パターン |
|---|---|
| 日付 | `日付｜年月日｜取引日｜利用日｜ご利用日｜日時` |
| 摘要 | `摘要｜内容｜お取引内容｜利用店名｜ご利用先｜店名｜備考｜明細` |
| 入金 | `入金｜お預り｜お預入｜預入` |
| 出金 | `出金｜お支払｜お引出｜引出｜支払金額` |
| 金額 | `金額` |

ヘッダがない場合は、1行目の各セルを日付としてパースできるか、数値としてパースできるかで推定する。推定結果は必ず画面に表示し、利用者が修正できること。

**日付の正規化：** `YYYY/M/D`、`YYYY-M-D`、`YYYY年M月D日`、`YYYYMMDD` を受け付ける。和暦は対象外。

**金額の正規化：** `¥` `,` `、` 空白 `円` を除去。`▲` `△` はマイナスとして扱う。

**符号の解釈：** 入金列・出金列が分かれている場合は入金を正、出金を負とする。1列の場合は「出金がマイナス／出金がプラス」を利用者が選択する。

**予定との自動照合：** 未消込の予定インスタンスのうち、以下をすべて満たす最初の1件を候補とする。
- 金額が完全一致
- 日付の差が12日以内
- 収支の向き（income / expense）が一致
- **口座が一致**（予定インスタンスの `accountId` が、取込対象として選択した口座と同一）

口座の一致を条件に含めるのは、同額・同日の予定が別口座に存在した場合に、取り込んだ行と無関係な予定を消し込んでしまうためである。支払いは必ず特定の口座から出るため、口座をまたいだ照合が正しい場面は存在しない。カードの予定（`accountId` がカード）が銀行口座のCSVの行と照合されることも、この条件で同時に防がれる。カードの引落はCL-2で合算された1件として銀行口座に現れるため、個別の利用明細とは金額が一致しない（AC-33）。

**費目の自動推定：** 既存の定期項目・単発予定・実績の名称から、括弧内を除いた先頭4文字を取り出し、CSVの摘要に部分一致するものを探す。一致したらその費目・固定変動区分・事業割合を初期値として引き継ぐ。2文字未満のキーは照合に使わない。

**確認画面：** 取込前に全行を一覧表示し、行ごとに 取込可否・収支・固定変動・費目・事業割合 を修正できること。自動照合された行は照合先を明示すること。

#### CL-8 借入返済スケジュールの生成（v2.0）

借入金1件から、返済期間ぶんの予定インスタンスを生成する。キーは `l:{loanId}:{返済日}` とする。

**月利** は `年利 ÷ 12 ÷ 100` とする。

**据置期間中**（借入実行日から `graceMonths` ヶ月）は、毎回の支払額を `残元本 × 月利` とし、元金充当額を0とする。

**元利均等（equalTotal）** の毎回返済額は次式で求める。

```
r = 月利, n = 返済回数（termMonths − graceMonths）
毎回返済額 = 元本 × r ÷ (1 − (1 + r)^(−n))
利息 = 期首残元本 × r
元金充当 = 毎回返済額 − 利息
```

**元金均等（equalPrincipal）** は `元金充当 = 元本 ÷ n` で固定し、利息を都度計算する。毎回返済額は逓減する。

**期日一括（bullet）** は毎月利息のみを支払い、最終回に元本を全額返済する。

**端数処理。** 各回の金額は円未満を切り捨て、最終回で残元本と累積誤差を調整する。返済表の合計が元本と一致することを保証する。

**元金と利息の分離。** これが法人資金繰りの要点である。

| 区分 | 資金繰り（現金） | 損益（P/L） |
|---|---|---|
| 元金充当 | 出金として計上 | 計上しない（負債の減少） |
| 利息 | 出金として計上 | 支払利息として計上 |

したがって借入返済の予定インスタンスは、金額を1件で持たず、`principalPortion` と `interestPortion` の2つを持つ。CL-2の現金イベント化では合算額を使い、CL-5のP/L集計では利息のみを使う。

**返済日の丸め。** `min(payDay, その月の末日)` とする。CL-1と同じ規則。

#### CL-9 売掛金の入金予定（v2.0）

請求データ1件から、入金予定を1件生成する。キーは `i:{invoiceId}` とする。

**入金予定日の算出** は、カード引落（CL-2）と同じ構造を持つ。

1. 請求の `issueDate` の日 ≤ 取引先の `closingDay` → 締め月 = 計上月。それ以外 → 締め月 = 計上月 + 1ヶ月
2. 入金月 = 締め月 + `payMonthOffset`
3. 入金予定日 = `min(payDay, 入金月の末日)`
4. `avgDelayDays` が0でない場合、入金予定日にこれを加算する

**例：** 月末締め翌々月末払い（closingDay=31、payMonthOffset=2、payDay=31）の取引先に対し、3月15日に計上した請求は、3月末締め → 5月末入金となる。

**カード引落との違い。** カードは締め期間内の利用を合算して1件の引落にするが、売掛金は請求単位で個別に予定を持つ。取引先ごと・請求ごとに入金確認と消し込みを行う必要があるためである。ただし同一取引先・同一入金日の予定は、入出金予定表の表示上はグループ化する。

**入金遅延の学習（FR-28）。** 請求のステータスが `paid` になったとき、`paidDate − 入金予定日` を遅延日数として記録する。取引先ごとに直近6件の中央値を `avgDelayDays` として更新する。中央値を使うのは、1件の異常な遅延に引きずられないためである。

遅延日数が10日を超える取引先については、入出金予定表と取引先一覧に注意表示を出す。資金繰りにおいて「いつも遅れる取引先」を把握することは、予測精度そのものより重要な場合がある。

**消費税の扱い。** 入金額は `amount + taxAmount` とする。資金繰りには税込で入る。損益には税抜で計上する。消費税の納付予測（v2.0の別機能）は、この差分を積み上げて算出する。

## 5. 非機能要件

### 5.1 性能

| 項目 | 目標値 |
|---|---|
| 初回表示 | 3秒以内（回線 4G 想定） |
| 残高再計算 | データ変更から画面反映まで 300ms 以内（定期項目50件・実績3,000件・予測期間24ヶ月） |
| CSV取込 | 1,000行を5秒以内に解析・照合 |
| 同時保持データ量 | 1ユーザーあたり実績10万件まで劣化しないこと。**この件数は「基準日以降の実績」で数える**（下記） |
| 一覧の表示件数 | 件数の多い一覧は全件を描画しない。**ただし総件数だけを表示して到達手段のない状態にしてはならない**（FR-42）。実績一覧は月単位で区切り、月内200件を超えた場合のみ件数ページングを併用する。無限スクロールは採用しない |
| データ保持期間 | 実績・予定は無期限。ただしインフラ費がMAUに比例するため、退会後30日で物理削除する |

**実績の取得範囲は基準日以降に限る。** CL-3 の開始残高が基準日時点で定義され、FR-40 で基準日より前の月を参照しないと決めたため、**基準日より前の実績を読み込む必要がない。** 残高計算・一覧・グラフのいずれも基準日以降だけで成立する。

これは性能上の都合ではなく、計算の定義から従う制約である。したがって「実績10万件」は蓄積総量ではなく**基準日以降の件数**を指す。総量がこれを超えても、基準日を前に進める操作（締め処理）で読み込み範囲は縮む。締め処理の設計は OI-6 の対象である。

性能目標は2段階で読む。**300ms は実績3,000件での目標**であり、10万件で保証するのは「一覧表示・実績入力・消し込みの操作が破綻しないこと」である。10万件で 300ms を満たすことは要求していない。

### 5.1.2 データ取得の完全性（FR-47）

計算に使うデータが**一部だけ取得された状態で計算を実行してはならない。** 残高は取得できた範囲で計算しても値が出てしまうため、欠落はエラーにならず、画面上でも正常に見える。消し込み済みの予定が未消し込みとして復活し、残高と防衛ラインの警告が同時に狂う。**間違った残高を表示するより、読み込めなかったことを伝えて止めるほうが安全である。**

取得側は次の4点を満たすこと。

| 要件 | 内容 |
|---|---|
| 範囲を指定する | 実績・単発予定は基準日以降に絞る（前項）。全件取得をしない |
| **順序を固定する** | 分割取得を行う場合、`order` を明示しないと行の順序が保証されず、ページの境界で**重複と欠落が起きる**。`date` の昇順、同日は `id` の昇順で固定する |
| 分割して取得する | APIの1回あたりの返却上限（PostgREST の Max rows。既定 1000）を超える件数は、範囲を分けて全件を取得する |
| 切り捨てを検知する | 総件数を別途取得し、受け取った件数と一致しない場合は例外とし、計算に進まない。画面には再試行の手段を示す。この例外が発生した事実を件数とともにイベント記録に残す（金額・費目名・口座名は含めない） |

順序の固定は分割取得の前提条件である。**順序を指定せずに範囲で分割すると、取得漏れが起きたうえで件数の照合は通ってしまう場合がある**（同じ行が2回返り、別の行が1回も返らない）。検知だけでは防げないため、両方を実装する。

### 5.1.1 インフラ費に影響する設計判断

インフラ費は売上ではなくMAUに比例する（事業計画書 8.0）。したがって次の3点は、機能要件ではなく原価に直接影響する設計判断として扱う。

| 判断 | 原価への影響 |
|---|---|
| 計算をクライアント側で行うか | 残高予測は日次52ヶ月ぶんの累積計算になる。クライアント側で実行すればサーバー負荷はほぼゼロ。プロトタイプはこの方式を採っており、v1.0でも維持する |
| CSVの解析をどこで行うか | クライアント側で解析し、確定した実績のみを送信する。ファイル本体はサーバーに保存しない。転送量とストレージの両方を抑えられる |
| 読み取り専用データを何ヶ月保持するか | 未課金ユーザーのデータは課金収入を生まないまま累積する。12ヶ月で削除することで頭打ちにする（FR-38） |
| トライアル発行に上限を置くか | 想定を超える流入が来たときにコストを止める唯一の手段。フリープランと違い、トライアルは発行を絞れる（FR-39） |

#### トライアルと読み取り専用の状態遷移

```
未登録 ──登録（カード不要）──> トライアル中（30日・全機能）
                                    │
                          ┌─────────┴─────────┐
                       課金                  30日経過
                          │                     │
                          ▼                     ▼
                       有料 <──課金──── 読み取り専用（12ヶ月）
                          │                     │
                       解約│                    │12ヶ月経過
                          └────────────>        ▼
                                            削除（30日前に予告）
```

**読み取り専用の定義。** 予定・実績の閲覧、グラフと表の表示、PDF以外のエクスポートは可能。新規登録・編集・削除・CSV取込はできない。トライアル中に入力したデータはそのまま保持する。

**自動課金は行わない。** カード登録を求めないため、30日経過時点で課金が発生することはない。読み取り専用への切替の7日前と前日に通知する。

**削除の予告。** 読み取り専用のまま11ヶ月が経過した時点で、30日後にデータを削除する旨をメールで通知する。通知後に課金すれば削除は取り消される。

**CSVファイル本体は保存しない。** 取り込んだ結果の実績データのみを保持する。再取込が必要な場合は利用者が再度ファイルを選択する。これは原価だけでなく、口座情報を含みうるファイルを保持しないという安全側の設計でもある。

### 5.2 可用性・信頼性

- 月間稼働率 99.5% 以上。
- 保存は変更から400ms のデバウンス後に自動実行し、失敗時は画面上に明示する。保存失敗時もセッション中のデータは失わないこと。
- データは日次でバックアップし、7日分を保持する。

## 7. 制約・前提

1. 金融機関との自動連携は行わない。明細の取得は利用者による CSV ダウンロードと取込に依存する。
2. カードの分割払い・リボ払い・ボーナス払いは対象外とし、一括払いのみを扱う。
3. 借入金の返済スケジュールは v2.0 で自動計算する（CL-8）。**v1.0 および PoC では、毎月の返済額を定期項目として1件手動で登録する。** この場合、元金と利息が分離されないため年月別収支の費用が過大になるが、資金繰りの予測は実態と一致する。PoC の検証目的は資金繰りの実感であり、この近似で足りる。利用者にはその旨を画面上で注記する。
4. 減価償却は扱わない。設備投資は支出時に全額を資金繰りに、費目「消耗品費」等として損益に計上する。損益上の正確な処理は会計ソフト側の責務とする。
5. 為替・外貨建て取引は対象外。
10. スタンダードとプロは最低契約期間を設けず、月単位での解約を許可する。ビジネスプランは最低契約期間6ヶ月とし、期間内の解約は残期間の支払いを要する。この差異は課金基盤の要件に影響する。
6. 複数ユーザーでの同時編集は行わない。ビジネスプランでも最大5名までとし、同時編集ではなく最終書き込み優先とする。
9. 税理士事務所向けの一括管理画面、顧問先一覧、監視・通知機能は提供しない。事務所は顧問先から招待された代理操作権限を用い、1件ずつ開いて作業する。この線引きは意図的なものであり、事務所側の運用効率化を目的としたコンポーネントは v2.0 の範囲外とする。
7. 手形、でんさい、ファクタリングは対象外とする。
8. 従業員20名を超える規模は対象外とする。承認フロー、部門別予算、監査ログ、SSO は実装しない。
