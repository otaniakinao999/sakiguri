## 1. 形を押さえる ―― 守りがどこに1本しか無いか

ブラウザが publishable key を持って**Postgres に直接話す。** 自前のサーバーが間に無い。だから守りの相手ごとに、効く仕組みが違う。

| 相手 | 効いているもの | 状態 |
|---|---|---|
| **他の利用者** | RLS（8表 × 4本） | **厚い。** 48通りの検査が控えている |
| **自分のページで動くスクリプト** | CSP | **強制で入っている**（下の2）。ただし `'unsafe-inline'` 付き |
| **盗まれたセッション** | セッションの寿命・パスワード方針・2段階 | **測った。** 60分・6文字・漏洩の照合は無効・2段階なし（下の3） |

**RLS は上の1行目にしか効かない。** 差し込まれたスクリプトはサインイン済みの本人として動くので、RLS からは正しい利用者に見える。

**2行目は半分である。** CSP は強制で入ったが、`'unsafe-inline'` が要る
（下の2）。**止まるのは「出て行くこと」であって「動くこと」ではない。**
nonce を買っても止まる相手が増えないことは下の2に書いた。

**3行目は測れただけで、まだ何も変えていない。** 60分・6文字・漏洩の

#### `'unsafe-inline'` の代償 ── **半分になる**

Next の App Router は RSC のペイロードを**inline script で流す**ので、
`script-src 'self'` だけでは本文が出ない。nonce を使うには middleware が
必要で、**20ルート全部が静的生成から外れる**（いまは `pnpm build` の
出力が全部 ○）。

`'unsafe-inline'` を入れると、**差し込まれたスクリプトの実行は止められない。**
上の表の2行目の守りは、こう変わる：

| | |
|---|---|
| 止められない | **スクリプトが動くこと**（inline なら実行される） |
| 止まる | **出て行くこと** ── `connect-src`（別の宛先への fetch）・`img-src`（画像ビーコン）・`form-action`（別の宛先への送信）・外部スクリプトの読み込み |

**「実行を止める」から「持ち出しを止める」に下がる。** 消えるわけでは
ないが半分である。

#### 測り方 ── **メールを1通も使っていない**

新しいアドレスで登録を試すと、**成功した場合に確認メールが飛ぶ。**
いま確認メールの枠は共有の基線を止めている当の資源なので、測定でそれを
減らさない。代わりに**既に確認済みの負荷試験アカウントのアドレス**に
`signUp` を投げた。GoTrue は確認済みの相手には作りもせず送りもせず、
存在を伏せた応答を返す。**パスワードの検査はその前に走るので、弾かれ方
だけが見える。**

**「その前に走る」ことを先に確かめている。** 逆（先に相手を探す）だと
どんなパスワードでも伏せた応答が返り、**照合が無効でも有効でも同じ結果**
になる。1文字で叩いて長さの文句が返ることを見てから、漏洩の照合を測った
（§2.11）。

#### 読み方

**60分は「盗られたときの影響の長さ」ではない。** refresh token が一緒に
あるので、`localStorage` の中身を持って行かれたら**更新し続けられる。**
上の表の3行目を短くしても、ここは短くならない。

**6文字・漏洩の照合なしは、`docs/セキュリティの状況.md` の1番（公開
リポジトリ）と組で効く。** 有効なアドレスが分かっていて、条件が6文字で、
漏洩の一覧と照合されない。**どちらか一方を閉じれば釣り合いが変わる。**
#### 決めた値 ── **最低10文字。文字種の条件は付けない**（2026-11-17）

| | |
|---|---|
| 最低文字数 | **10** |
| 文字種（大文字・数字・記号の必須） | **付けない** |

**長さを取って組み合わせを捨てた。** 文字種を必須にすると `Password1!`
の形に寄るので、10文字のほうが強くて使いやすい。Supabase の文書も8未満を
勧めていない。金融のデータなので8ではなく10にする。

**変えるのは dashboard で、利用者の手番である。** コードの側は
`src/components/auth/SignInScreen.tsx` の2箇所（`hint` の「6文字以上」と
`minLength={6}`）だけ。**dashboard を変えたあとに合わせる** ―― 逆順にすると
**画面が通して本番が弾く**形になる。

#### **上げても、いま弱いものは弱いままである**

**最低文字数は新規と変更のときにだけ効く。** 既存のパスワードは作られた
当時の条件のまま残る。つまり ──

**6 の記帳代行の共有サインインは、方針を上げても変わらない。** 弱いのは
まさにそれである。

**だから値打ちは「これから作るアカウントが全部これになる」ことにある。**
モニター配布の**前**に入れる意味がここで、**配布の後だと配った分には
効かない。**

いまある共有サインインのほうは、方針では直らない。**grants / invites が
それを畳むための仕事である**（6）。

**この区別を書かないと「パスワード方針を直した」で終わり、既存が弱いまま

| | |
|---|---|
| **方針が本番に効いたか** | **測れる。** `pnpm loadtest:auth` が外から境を出す。**基線は 6 文字**（2026-11-17 に測った。上の表） |

| `pnpm build` | **404**（3ページとも） |
| `ALLOW_DEV_SCREENS=1 pnpm build` | 200（3ページとも） |

`"1"` 以外の値（`"0"` `"false"` `"true"` `""`）で開かないことも検査にした。
**「無効にしたつもり」が開いたままだと、倒れる方向が元に戻る。**

### 5. バックアップが無い

既知（`docs/バックアップの状況.md`）。**機密だけが security ではない。** 誤操作・悪意の削除・ランサムに対して、いま戻す手段が無い。

### 6. 記帳代行の共有サインイン ―― **いま実在する最大の漏れ**

顧客ごとに1つのサインイン情報を、こちらの担当者と税理士が共有している。**個別に失効できず、誰がやったか分からず、担当者が替わっても残る。**

**これはコードの穴ではなく運用の穴で、いま作っている grants / invites がその置き換えである。** 作り切る理由がここにある。モニター配布の前に確認メールを入れる判断も同じ線。

**パスワード方針を上げても、ここは変わらない。** 最低文字数は新規と変更のときにだけ効き、既存のパスワードは作られた当時の条件のまま残る（3 の末尾）。**畳めるのはこの表を作ってからである。**

### 7. 依存の既知脆弱性 ── **済（本番の依存を0件にして、ゲートに入れた）**

`pnpm audit` を初めて流した。**33件。うち critical が1件で、本番の依存だった。**

| | 中身 |
|---|---|
| **critical** | **`next` の Image Optimization API ＋ SVG で未認証の RCE**（`>=10.0.0 <=15.5.27`） |
| high | `next` の Server Actions で DoS（**`"use server"` は0件**なので経路が無い）／`postcss` の sourceMappingURL で任意ファイル読み出し2件／`source-map-js` の DoS |
| moderate | `next` の SSG/ISR のキャッシュ汚染／`postcss` の `</style>` 由来 XSS ほか |

**3つ手を打った。**

1. **`next` を 15.5.29 に上げた。** critical が消え、`sharp` も 0.35.5
   （修正版）に上がった
2. **画像の最適化を止めた**（`images: { unoptimized: true }`）。
   `next/image` の呼び出しは**0件**、`public/` も無く、SVG も持っていない。
   **それでも `/_next/image` は 200 を返していた**（本番・ローカルの両方で
   確かめた）。いまは 404
3. **`postcss` と `source-map-js` を `overrides` で上げた**
   （`pnpm-workspace.yaml`。pnpm 12 では `package.json` の `pnpm` フィールドは
   **読まれない** ―― 書いても黙って無視される）

**2つ目が要る理由は、版を上げても次の穴が同じ口に出るからである。**
**使っていない口を開けている理由が1つも無い。**

#### 3つ目について ── **前の読みを訂正する**

ここには「残り5件は `next` が内側に固定している `postcss@8.4.31` なので
`next` 側が上げるまで動かせない。`overrides` で剥がすのは壊す側の危険が
上回る」と書いていた。**この読みは外していた。**

`^8.5.33` に上書きして、**`pnpm build` と `pnpm test`・`typecheck`・`lint`
が全部通った**（組み上がった CSS に `:root` の変数が319個、`sp-16` や
`layout-field-width` も在ることを確かめた）。危険は上回っていなかった。

**「経路が無い」という読みのほうは正しい** ―― ビルド時にしか動かず、
通す CSS は自分のものだけである。**だが「悪用できないから直さない」と
「バーを下げる」は別である。** 塞げるなら塞いで、ゲートは high に置く。

| | 本番の依存 | 全体 |
|---|---|---|
| 最初 | 10件（critical 1） | 33件 |
| `next` を上げた後 | 5件（high 3・moderate 2） | 28件 |
| **`overrides` の後** | **0件** | 23件（全部 devDependency） |

#### ゲートに入れた ── **`--prod --audit-level=high`**

```
pnpm audit --prod --audit-level=high
```

`pnpm gate` の中に入っている。**`--prod` が要る理由**は、全部を流すと
**本番に出ない23件が毎回赤く出る**こと ―― 赤が常態になった検査は
読まれなくなる。

**水準を下げるときは、ここに理由と見直す時期を書くこと。** 黙って
`critical` に下げると、次に本番依存の high が出たときに静かに通る。

**`overrides` は外せるようになったら外す。** `next` が `postcss` の
固定を上げたら、`pnpm-workspace.yaml` の2行を消して
`pnpm audit --prod --audit-level=high` が通ることを見てから外す。

### hydration の不一致 ── **本番の経路では起きていない**

本番ビルドで確かめた。`/` `/cashflow` `/pl` の**配られる HTML に
`role="tablist"` が1つも無い**（ローカルの本番ビルドでも、本番のサイトでも
0件）。期間タブは**サインインした後にクライアント側だけで組まれる**ので、
server と client を突き合わせる場面が無い。

出ていたのは `/dev/screens/*` のほう。**あちらは固定値を持っているので、
ビルド時にタブまで組まれる。** いまは `/dev` の shell を `Suspense` で
包んだ（下記）ので、そこでも組まれなくなった。

**security ではないが、出し方が server と client で違うことの印**という
元の読みは正しかった。**違っていたのは場所である。**

### `pnpm build` ── **ゲートに入れた**

**2026-11-17 に一度落とした。** `/dev` の shell に `useSearchParams()` を
足したところ、`/dev/screens/*` の prerender が落ちて `pnpm build` が
失敗するようになった。**ゲートは typecheck / test / lint だけだったので、
PR は通り、push もできた。** 気づいたのはこの文書を書くために本番ビルドを
作ったときで、**その間 Vercel のデプロイは失敗し続けていた**（本番は
最後に成功した版を配り続けるので、画面は壊れない ── だから静かである）。

**いま `pnpm gate` の最後が `pnpm build` である。** Vercel がどうせ毎回
流すものなので、早く落ちるほうが安い。

#### 入れた留め具を、壊して確かめた（§2.11）

**ゲートに足しただけでは、拾えることを測っていない。** 本当に
「typecheck / test / lint が通るのにビルドで落ちる」を拾うかを見た。

| 壊したもの | typecheck | `pnpm build` |
|---|---|---|
| prerender の途中で `throw`（`(app)/pl/page.tsx`） | **通る**（0） | **落ちる**（1） |

**他の3本が見ない失敗を、この1本だけが見ている。**

#### 同じ実行で分かったこと ── **あの失敗は、もう再現しない**

**元の落ち方（`/dev` の shell の `Suspense` 外し）を 15.5.29 で再現
させようとしたら、通ってしまった。** `/dev/screens/*` は静的に生成され、
ビルドは成功する。落ちたのは 15.5.25 のときである。

**包むのはやめていない。** `useSearchParams()` を Suspense の外で呼ぶのは
React の側では正しくない書き方のままで、**次の版でまた落ちる側に戻りうる。**
`src/app/dev/dev-shell.tsx` の注をこの内容に直した ―― **「これが無いと
落ちる」と書いたままにすると、読んだ人が外して確かめて、通ったことを
根拠に外す。**

#### まだ塞がっていない穴が1つ残っている

ビルドを測るようになっても、**デプロイが落ちたことが誰にも届かない形**は
変わらない。Vercel の通知設定は利用者側の手番。**今日の静けさの原因は
ゲートではなく、ここだった。**
