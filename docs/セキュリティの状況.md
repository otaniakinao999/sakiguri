# セキュリティの状況（2026-11-17 時点）

**実コードを見て確かめた内容である。** 一般論のチェックリストではない。

## 1. 形を押さえる ―― 守りがどこに1本しか無いか

ブラウザが publishable key を持って**Postgres に直接話す。** 自前のサーバーが間に無い。だから守りの相手ごとに、効く仕組みが違う。

| 相手 | 効いているもの | 状態 |
|---|---|---|
| **他の利用者** | RLS（8表 × 4本） | **厚い。** 48通りの検査が控えている |
| **自分のページで動くスクリプト** | CSP | **無い。** `next.config.ts` が空 |
| **盗まれたセッション** | セッションの寿命・パスワード方針・2段階 | **既定のまま。どこにも書かれていない** |

**RLS は上の1行目にしか効かない。** 差し込まれたスクリプトはサインイン済みの本人として動くので、RLS からは正しい利用者に見える。**この案件の労力はほぼ1行目に入っていて、2行目と3行目は手付かずである。**

## 2. 強い点 ―― **壊さないように書き留める**

| | |
|---|---|
| **第三者への通信が1つも無い** | 依存に解析も障害報告も無い。外に出る宛先は Supabase だけ。フォントも自前（`@fontsource`）。**金融系でいちばん多い漏れ方（Sentry・GA が明細と金額を持って行く）が、そもそも経路として存在しない** |
| **service_role キーを使っていない** | コード中に出るのは「使わない理由」の注だけ |
| **鍵を一度もコミットしていない** | 全履歴を JWT 形の文字列とパスワード代入で走査した。当たった2つは**lockfile の sha512** と**環境変数名**（値ではない） |
| `usage_events` | 列の注で**金額と名称を入れないと明示**している |
| `accept_invite` | `security definer` を正しく書いている ―― `set search_path = ''`、`revoke execute from public`、**「招待が無い」と「自分宛でない」で文面を分けない**（id の総当たりで存在を試せないように） |
| 48通りの検査が**本番の project に対して走る** | publishable key と本人セッションで組んであるので、測っている壁が実際の壁である |

**次に何かを足すとき、いちばん戻りやすいのが1行目である。** Sentry・GA・PostHog を入れた瞬間に、銀行明細の摘要と金額が第三者に渡る。入れるなら、何を送らないかを先に決める。

## 3. 直すもの（**この順**）

### 1. リポジトリが公開されている ―― **ここから**

`github.com/otaniakinao999/sakiguri` は未認証で見える。**鍵は漏れていない**（上記）。漏れているのは**偵察の材料**である。

| 公開されているもの | なぜ効くか |
|---|---|
| `supabase/config.toml` の `project_id` | **本番の API の宛先が分かる。** publishable key は元から公開なので、**誰でも Supabase クライアントを本番に向けられる** ―― 止めているのは RLS だけ |
| 大谷さんの実アドレス（`docs/測定結果/` の2件） | **有効なアカウントのアドレスが分かる。** パスワード方針とレート制限は既定のままで、どこにも書かれていない |
| `docs/バックアップの状況.md` | **復旧手段が無いことが書いてある** |
| 8表の RLS の述語 | 壁の形がそのまま分かる |

**非公開にするのが効率が最も良い。** ライブラリではないので公開の利点が無く、**1手で上の全部が消える。** ただし**すでに取られた複製は戻らない**ので、これは下の項目の代わりにはならない。

### 2. CSP と応答ヘッダが無い

`next.config.ts` が空。`Content-Security-Policy` / `Strict-Transport-Security` / `X-Frame-Options`（または `frame-ancestors`）/ `Referrer-Policy` / `X-Content-Type-Options` のいずれも無い。

**この案件は CSP を厳しく張りやすい** ―― 第三者スクリプトが0で、フォントも自前なので、`script-src 'self'` が現実的である。普通は第三者タグが邪魔をして張れない。**張れるうちに張る。**

### 3. 認証の設定が dashboard にしか無い

パスワードの最低条件、セッションの寿命、漏洩パスワードの照合、レート制限 ―― `supabase/config.toml` に `[auth]` の記述が無く、**本番の実際の値は誰も読めない。**

`config push` は使えない（**差分13件で本番を上書きする**。`docs/新規登録の経路.md`）。**押すのではなく、書き出して読めるようにする。**

### 4. `/dev` の遮断が開く方向に倒れている

`process.env.VERCEL_ENV === "production"` のときだけ `notFound()`。**preview では `/dev` が生きている**し、この変数が無い場所でも生きる。

**データは出ない**（dev のページはどれも Supabase を触らない。確認した）。出るのは画面の構造だけ。ただし**倒れる方向が逆**なので、`NODE_ENV` を見る形にする。preview で必要なら、無効の既定に対して明示的に開ける形にする。

### 5. バックアップが無い

既知（`docs/バックアップの状況.md`）。**機密だけが security ではない。** 誤操作・悪意の削除・ランサムに対して、いま戻す手段が無い。

### 6. 記帳代行の共有サインイン ―― **いま実在する最大の漏れ**

顧客ごとに1つのサインイン情報を、こちらの担当者と税理士が共有している。**個別に失効できず、誰がやったか分からず、担当者が替わっても残る。**

**これはコードの穴ではなく運用の穴で、いま作っている grants / invites がその置き換えである。** 作り切る理由がここにある。モニター配布の前に確認メールを入れる判断も同じ線。
