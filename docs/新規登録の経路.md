## 1. 登録直後に出るもの（AC-51 の前半）

`SignInScreen.tsx` が出す。**無言ではない。**

> 登録しました。**確認メールが届いている場合は、**リンクを開いてからサインインしてください。

```ts
} else if (mode === "signup") {
  setNotice("登録しました。確認メールが届いている場合は、リンクを開いてからサインインしてください。");
}
```

問題は2つ。

- **「届いている場合は」が条件付き。** Confirm email が ON なら必ず届くので、この書き方だと「自分は届かない側かもしれない」と読める
- 画面は**登録フォームのまま**。サインインに切り替わらない

## 2. 既に登録済みのアドレスで登録すると「登録しました」と出る（AC-51）

**これが一番重い。**

Supabase は既存アドレスの `signUp` に対して**エラーを返さない。** メールアドレスの存在を外から探れないようにするための仕様で、`user` は返るが `identities` が空配列になる。

```
identities  []     ← 既存。新規なら [1件]
```

アプリは `error` だけを見ている。

```ts
const { error: failed } = await supabase.auth.signUp(credentials);
if (failed) { setError(failed.message); }
else if (mode === "signup") { setNotice("登録しました。…"); }
```

`failed` が無いので「**登録しました**」が出る。**メールは届かない。** 利用者は届かないメールを待ち続ける。

登録済みを忘れて再登録する人は必ず出る。**判別する手段は `identities.length === 0` で、応答に入っている。**

## 3. 確認リンクを踏んでも、サインインされない（AC-52）

`client.ts` に `detectSessionInUrl: false` が入っている。

```ts
auth: { persistSession: true, autoRefreshToken: true, detectSessionInUrl: false }
```

確認リンク → Supabase が検証 → アプリにリダイレクト、のとき**URL に載って戻ってくるトークンを拾わない。** `/auth/callback` 相当のルートも無い（`src/app/` に認証用のルートは無い）。

**メール確認そのものはサーバー側で成立する**（Supabase の `/auth/v1/verify` が処理する）。壊れてはいない。利用者から見るとこうなる。

> リンクを踏む → アプリが開く → **またサインイン画面** → 何も説明がない → もう一度メールアドレスとパスワードを入力 → 入れる

**入れるが、説明が無い。**

### リダイレクト先が未確認

`signUp` に `emailRedirectTo` を渡していないので、戻り先はプロジェクトの **Site URL** 設定になる。**既定のままだと `http://localhost:3000`。** その場合、モニターの確認リンクは本人の手元の localhost に飛ぶ。

**追加の操作なしで確かめられる。** `+loadtest-probe` の確認メールが受信箱にあるはずなので、**リンクを踏まずに** URL の `redirect_to=` を見る。

| 見えるもの | 判断 |
|---|---|
| `redirect_to=https://…`（本番ドメイン） | 問題なし |
| `redirect_to=http://localhost:3000` | **配布前に直す** |

## 4. エラーが生の英語で出る（AC-53）

```ts
if (failed) setError(failed.message);
```

日本語の画面に、認証基盤の英語がそのまま出る。

| 状況 | 画面に出る文字列 |
|---|---|
| 確認前にサインイン | **`Email not confirmed`** |
| パスワード違い | `Invalid login credentials` |
| 6文字未満で登録 | `Password should be at least 6 characters` |

**モニターが一番高い確率で踏むのが1行目。** 登録 → 待てずにサインイン → 英語。

### パスワード違いと未登録は、区別しない

`Invalid login credentials` は**パスワード違いと未登録アドレスの両方**で返る。

一度これを「分けられない制約」として報告したが、**誤りだった。分けられないのではなく、分けてはいけない。** 区別して見せると、任意のアドレスを入れて**登録の有無を調べられる。** Supabase が同じ文言を返すのは制約ではなく設計で、別の手段で区別し直すのはその設計を無効にする行為である（v1.27 AC-53）。

**代わりに、同じ場所に導線を両方置く。** パスワードの再設定と新規登録。アプリはどちらなのか言わない。利用者は自分で試せる。

### 「確認が済んでいない」だけは区別してよい

同じ論法で全部隠すと、確認メールを踏んでいない人が理由を知る手段を失う。線を引く根拠は §5.3 にある。

> 認証基盤がこの状態に専用の応答を返すため、**アプリが隠しても列挙は防げない。** 隠した場合の損失だけが残る。

`email_not_confirmed` という専用のコードが返る以上、アプリが文面を濁しても、応答を直接見れば分かる。**隠して実際に何かが防げるかを、応答の形ごとに確かめて決める**（§5.3）。

## 2026-10-07 に外から確かめたこと

**受信箱を見ずに分かる範囲を、Supabase の公開エンドポイントから取った。**

### Confirm email はオンに戻っている

```
GET /auth/v1/settings
  mailer_autoconfirm     false      ← オン（自動確認しない）
  disable_signup         false
  external（有効）        email
```

### Site URL は localhost ではない

無効なトークンで `verify` を叩くと、Supabase は Site URL にリダイレクトして返す。その `Location` が Site URL である。

```
GET /auth/v1/verify?token=invalid-probe&type=signup
  303 → https://sakiguri.vercel.app/#error=access_denied&error_code=otp_expired&…
```

**`https://sakiguri.vercel.app`。** 懸念されていた localhost ではなかった。モニターの確認リンクは開ける。

### リダイレクトの許可リストは効いている

`redirect_to` が許可リストに無ければ Site URL に落とされる。その性質で外から確かめた。

| 指定した `redirect_to` | 結果 |
|---|---|
| `https://sakiguri.vercel.app` | 許可 |
| `https://sakiguri.vercel.app/auth/confirm` | **許可**（サブパスも通る） |
| `http://127.0.0.1:3100` | 許可 |
| `http://localhost:3000` | **却下** → Site URL に落ちる |
| `https://example.invalid/pwned` | **却下** → Site URL に落ちる |

**最後の行が効いている。** これが「許可」になるなら、上の「許可」は何も意味しない（§9.1 の6つ目）。

`/auth/confirm` が通るので、**専用の経路を作っても許可リストの追加は要らない。**

`http://localhost:3000` が却下される点は注記する。**ローカル開発では確認リンクを受けられない。**

### リンクの形は、受信箱を見ないと確定しない

分かっていること。

- `client.ts` は `flowType` を指定していない。`@supabase/supabase-js` v2 の既定は **implicit**
- 上の probe の戻りが**フラグメント**（`#error=…`）である
- `token_hash=` を指定すると 400 になり、`token=` は 303 を返す

ここから**既定のテンプレート（`{{ .ConfirmationURL }}` → `/auth/v1/verify?token=…&type=signup&redirect_to=…`）で、成功時は `{SITE_URL}/#access_token=…` に戻る**と見ているが、**これは推定である。** メールのテンプレートは外から読めない。

**`+loadtest-probe` の確認メールの URL を、リンクを踏まずに確認してもらう必要がある。**

`src/lib/auth-messages.ts` に文面を分けた。**React を import しない純粋な変換**なので、テストで全文面に禁止語を当てられる。

## AC-52 の受け口（2026-10-07 実装）

**リンクの形をアプリ側が決める。** Supabase のメールテンプレートを書き換えて、リンクを `/auth/confirm` に向ける。

```
Confirm signup   {{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=signup
Reset password   {{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=recovery
```

受け口は1本。`verifyOtp({ token_hash, type })` でセッションを張る。`signup` ならそのままアプリへ、`recovery` なら新しいパスワードの入力に進む。

**既定の形に合わせなかった理由**（v1.31 §5.3）。

- アクセストークンが URL の断片に乗り、ブラウザの履歴に残る
- `detectSessionInUrl: true` にすると**全ページの読み込みで URL を認証情報として検査する**ことになる。認証情報を扱う場所は1本に閉じたい
- リンクの形を確かめるために毎回メールを開くことになる

### 実装前に確かめたこと

`verifyOtp` が `token_hash` を受けるかを、無効なハッシュで叩いて確かめた。

```
type=signup    status=403 code=otp_expired        msg=Email link is invalid or has expired
type=recovery  status=403 code=otp_expired        msg=Email link is invalid or has expired
type=bogus     status=400 code=validation_failed  msg=Invalid email verification type
```

**形は受け付けられている。** 以前 `GET /auth/v1/verify?token_hash=…` が 400 だったのは別の経路（`verifyOtp` は POST で本文に載せる）。

**`{{ .TokenHash }}` がテンプレートで使えるかは、外からは確かめられない。** Supabase の文書にある変数だが、実際に置き換わるかはメールを見るまで分からない。

### 既定で通さない

`type` が `signup` / `recovery` 以外なら、**`verifyOtp` を呼ばずに**エラーを出す。実機で確認した。

| URL | 画面 |
|---|---|
| `?token_hash=…&type=signup`（無効なハッシュ） | リンクの有効期限が切れているか、すでに使われています。… |
| `?token_hash=…&type=magiclink` | このリンクは扱えません。メールのリンクをそのまま開いてください。 |

### トークンは1回で使い切られる

`useEffect` を素直に書くと、開発時の StrictMode が2回走らせて**2回目が必ず失敗する**（1回目で消費済み）。画面には失敗だけが出て原因が分からない。`useRef` で1回に固定してある。

## 配布の前提条件：独自のメール送信（SMTP）

**AC-52 の実装では解決しない、別の問題。**

既定のメール送信は共有の仕組みで、**1時間あたり数通で制限される。** モニターが同じ時間帯に登録すると、**2人目以降にメールが届かない。** 送信元も共有のドメインなので迷惑メールに分類されやすい。

| 日付 | 独自のメール送信 | 設定した人 |
|---|---|---|
| 2026-10-07 | **未設定** | — |

状況が変わったら行を足す。**行を書き換えずに足す**（`docs/バックアップの状況.md` と同じ運用）。

### いま制限値を測らない

**測ると、そのぶんの枠を使ってしまう。** 枠を使い切ると AC-51・AC-52・AC-53 の実機確認（新規登録1回＋確認メール1通）がその時間できなくなる。

**確かめたい相手を壊してから測ることになる。** 制限値は配布の判断のときに、SMTP を入れる前提で扱う。
