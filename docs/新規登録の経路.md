# 新規登録の経路（現状の記録）

**実装は変えていない。読んで分かったことの記録。** 対応する受入基準は AC-51 / AC-52 / AC-53（v1.26 で追加。**配布前の必須**）。

調べた日：2026-10-05 ／ 根拠：`src/components/auth/SignInScreen.tsx`、`src/lib/supabase/client.ts`、`src/app/` の構成、および Supabase への実リクエスト（`+loadtest-probe` での `signUp` → `signIn`）

---

## なぜ急ぐか

**モニター配布時は Confirm email を ON に戻す。** つまり**モニター全員がこの経路を通る。** 大谷さんとスタッフは既存アカウントを使うので、いま詰まらない。

実測で確定している（2026-10-05、新規アドレスでの `signUp`）。

```
error       なし
user        返った
identities  1
session     返らない          ← 確認待ち
signIn      失敗: email_not_confirmed Email not confirmed
```

## 1. 登録直後に出るもの（AC-51 の前半）

`SignInScreen.tsx` が出す。**無言ではない。**

> 登録しました。**確認メールが届いている場合は、**リンクを開いてからサインインしてください。

```ts
} else if (mode === "signup") {
  setNotice("登録しました。確認メールが届いている場合は、リンクを開いてからサインインしてください。");
}
```

問題は2つ。

- **「届いている場合は」が条件付き。** Confirm email が ON なら必ず届くので、この書き方だと「自分は届かない側かもしれない」と読める
- 画面は**登録フォームのまま**。サインインに切り替わらない

## 2. 既に登録済みのアドレスで登録すると「登録しました」と出る（AC-51）

**これが一番重い。**

Supabase は既存アドレスの `signUp` に対して**エラーを返さない。** メールアドレスの存在を外から探れないようにするための仕様で、`user` は返るが `identities` が空配列になる。

```
identities  []     ← 既存。新規なら [1件]
```

アプリは `error` だけを見ている。

```ts
const { error: failed } = await supabase.auth.signUp(credentials);
if (failed) { setError(failed.message); }
else if (mode === "signup") { setNotice("登録しました。…"); }
```

`failed` が無いので「**登録しました**」が出る。**メールは届かない。** 利用者は届かないメールを待ち続ける。

登録済みを忘れて再登録する人は必ず出る。**判別する手段は `identities.length === 0` で、応答に入っている。**

## 3. 確認リンクを踏んでも、サインインされない（AC-52）

`client.ts` に `detectSessionInUrl: false` が入っている。

```ts
auth: { persistSession: true, autoRefreshToken: true, detectSessionInUrl: false }
```

確認リンク → Supabase が検証 → アプリにリダイレクト、のとき**URL に載って戻ってくるトークンを拾わない。** `/auth/callback` 相当のルートも無い（`src/app/` に認証用のルートは無い）。

**メール確認そのものはサーバー側で成立する**（Supabase の `/auth/v1/verify` が処理する）。壊れてはいない。利用者から見るとこうなる。

> リンクを踏む → アプリが開く → **またサインイン画面** → 何も説明がない → もう一度メールアドレスとパスワードを入力 → 入れる

**入れるが、説明が無い。**

### リダイレクト先が未確認

`signUp` に `emailRedirectTo` を渡していないので、戻り先はプロジェクトの **Site URL** 設定になる。**既定のままだと `http://localhost:3000`。** その場合、モニターの確認リンクは本人の手元の localhost に飛ぶ。

**追加の操作なしで確かめられる。** `+loadtest-probe` の確認メールが受信箱にあるはずなので、**リンクを踏まずに** URL の `redirect_to=` を見る。

| 見えるもの | 判断 |
|---|---|
| `redirect_to=https://…`（本番ドメイン） | 問題なし |
| `redirect_to=http://localhost:3000` | **配布前に直す** |

## 4. エラーが生の英語で出る（AC-53）

```ts
if (failed) setError(failed.message);
```

日本語の画面に、認証基盤の英語がそのまま出る。

| 状況 | 画面に出る文字列 |
|---|---|
| 確認前にサインイン | **`Email not confirmed`** |
| パスワード違い | `Invalid login credentials` |
| 6文字未満で登録 | `Password should be at least 6 characters` |

**モニターが一番高い確率で踏むのが1行目。** 登録 → 待てずにサインイン → 英語。

`Invalid login credentials` は**パスワード違いと未登録アドレスの両方**で返る（列挙を防ぐため Supabase が同じ文言にしている）。AC-53 が3つを区別せよと言っているので、**未登録かどうかはこの応答だけでは分けられない。** 設計時に扱いを決める必要がある。

## まとめ

| | 現状 | AC |
|---|---|---|
| 登録直後の案内 | ある。ただし条件付きの言い回し | AC-51 |
| 既存アドレスでの登録 | **「登録しました」と出る。メールは来ない** | AC-51 |
| 確認リンクのあと | 確認は成立するが**サインインされない。説明も無い** | AC-52 |

**無言で失敗はしない。** だが「登録しました」が嘘になる経路（2番）があり、ここが一番重い。
