## 業務ルール（画面の文言から読み取れるもの）

### 照合（自動消し込み）

- **条件：** 金額が完全に一致し、日付の差が12日以内で、口座も同じ予定です。1円でも違えば候補になりません。
- **CSV取込のとき：** 条件に合う予定は、取り込みと同時に消し込みます。その予定は「やること」に出ません。
- **照合したときの値の取り方：**
  - 予定から引き継ぐもの：費目・固定変動の区分・事業割合
  - 実績の値を使うもの：日付・金額・口座

### やること

- 次の2種類を、予定日の古い順に並べます。
  - 消し込まれていない予定（予定日を過ぎたもの）
  - 照合されていない実績
- 60日以上前の予定が残っているときは、info の Callout で知らせます。

### 予定の生成

- **定期項目：** 毎月の発生日に予定を作ります。発生日に「末日」を指定した項目は、月の最終日に合わせます（2月は28日、うるう年は29日など）。
- **カード：**
  - 締日・支払月・支払日・引き落とし口座から、引き落としの予定を自動で作ります。この行は編集できません。
  - 確定金額は、基準日のあと最初の引き落とし日に入ります。
  - 未確定分は、その次の引き落とし日に入ります。

### 振替・年月別 収支

- **振替：** 損益に含めません。合計残高も変えません。
- **年月別 収支：** 振替とカード引落は含めません。差引は「収入 − 固定費 − 変動費」です。

### 基準日

- 基準日より前の実績は、残高の計算から外れます。
- 口座の残高は「基準日時点の残高」として持ちます。
- 基準日を変えると、口座とカードの残高を入れ直す必要があります。そのため確認ダイアログを必ず出します。

### この回だけ変更

- 定期項目のうち特定の1回だけ、日付や金額を変えられます。
- 変えた予定には元の日付を残します。表示例：「繰延（元の日付 10/8）」。

### CSV

- CSV のファイル自体はサーバーに保存しません。読み取った結果だけを登録します。
- 文字コードは Shift_JIS に対応します。
- 列の割り当ては自動で推定し、ユーザーが確認します。

## 未決事項・既知の問題（実装前に確認すること）

   - モックデータを作るときは、1/17 に大口の出金（例：税金の納付）を置いてください。
2. **ロゴ** ―― **解決（2026-11-13 支給）**
   - ~~「SAKIGURI」は Cormorant Garamond で仮置き~~ → SVG のワードマークに差し替え済み（`src/components/sakiguri/Wordmark.tsx`）。
   - **塗りは `currentColor`。** 支給物は `fill="white"` だったが、置いた側が `text-*` で決める形にしてある（CLAUDE.md §2.6）。サイドバー（濃い面）は `text-primary-foreground`、サインイン・確認（明るい面）は `text-object-base-high`。
   - **高さは呼び出し側が決める**（既定を持たせない。既定と呼び出し側の `h-*` が両方付くと、どちらが効くかは CSS の順序で決まる）。サイドバー `h-40`、サインイン・確認 `h-40`（2026-11-13、大谷さんの指定）。ワードマークが 224px の内側の幅をほぼ埋めるが、**ロゴを大きく出すほうを採った。**
   - **字は総高の約 15/19**（上に弧があるため）。24px の文字に合わせるなら `h-32`。
   - **中央に寄せるときは `mx-auto` が要る**（サインイン・確認）。`<svg>` は preflight で `display: block` になるので、**親の `text-center` では文字だけが寄ってロゴは左のまま**になる。2026-11-13 の実機で見つけた。
   - **留め具**：`src/components/sakiguri/__tests__/wordmark.test.ts`。`src/` を走査して `Wordmark` を置いている全部を見る（手で並べると4箇所目で漏れる）。**色が見えていることは測れない** ―― `currentColor` の解決も面との対比も jsdom には無い。測るのはその手前（ロゴ自身が色を持たないこと／置いた側が `text-*` と `h-*` を渡していること／濃い面と明るい面で違う色であること）。

5. **レスポンシブ** ―― **375px は解決（2026-11-13、大谷さんの決定）**
   - 1440px のデザインしかなく、1280px 未満は未定のままだった。**375px でどの画面も横にはみ出していた**（ダッシュボード 524px・実績一覧 453px・入出金予定表 631px）。
   - **原因は2つで、どちらも1語。** ①パネルの `self-start` ―― `flex-col` の親の中では**横方向**（cross axis）に効くので、同じ要素が持つ `min-w-0 flex-1` は効かない（あれは主軸＝縦の話）。②Hero の操作行の `shrink-0`。
   - **原因だけ直すと品目名が消える。** 実測で「電気代」が **4px**（表示には 43px 要る）。はみ出しと引き換えに一覧が読めなくなるので、原因の修正だけでは足りない。
   - **決めたこと（375px）**
     1. **ボタンは折り返す**（期間タブと「CSVを取り込む」）。
     2. **グラフは横スクロールさせる**（縮めない）。
     3. **やること以下はカードにせず、横いっぱいに使う。** カードの内側余白が幅を食うのが理由。
     4. **横の余白は 16px**（`p-24` ではなく `px-16`。§2.6 のスケール内）。
     5. **予定の行は2段。** 1段目が日付と項目、2段目が金額・タグ・予実。
   - **この形で 375px ちょうど・はみ出し0件・「電気代」251px**（2026-11-13 に実アプリ `/dev/screens/dashboard-wired` を 375px で描いて実測）。
   - **広い幅は変えない。** `wide:` の側に現在の値を残す（`wide:self-start`・`wide:shrink-0`・`wide:p-24`・1段の行）。
   - **レイアウトは jsdom で測れない**（§2.7）。確認は実機で、**375 と 1280 の両方**を見る。
   - **前提は PC である**（2026-11-13、大谷さん）。375px は**読めれば足りる**という水準で、ここを作り込む判断はしていない。モバイルを主戦場にするなら、この5点はやり直しの出発点であって完成形ではない。
   - 1280px 未満の残り（サイドバーの畳み方など）は引き続き未定。
