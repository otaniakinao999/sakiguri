### 読み方

**`actuals` が3往復**なのが要点。1,000件の上限を2回またいでいる。またいだうえで、受取3,000 = ユニーク3,000 = 総件数3,000 で、並びの逆転が0。

**`overrides` は40件。** `plan_key` が並び替えキーなので、ここに行があって初めて「全テーブルで一意」が確かめられる。40件は定期項目1〜20 × 2ヶ月（2026-03 / 2026-06）で、`(定期項目id, 発生日)` の組が重複しない。繰延20件（`date` を5日後に差し替え）と金額変更20件の両方を含む。

**残る弱さが1つある。** `seed.ts` は `plan_key` を**組み立てている**（`r:{id}:{発生日}`）。`forecast.ts` の `recurringKey` を import できないため（`./date` を拡張子なしで import していて Node が解決できない）。形式を変えると AC-50 のテストは落ちるが、**`seed.ts` は落ちない。** そのとき `seed.ts` は古い形式のキーを作り続ける。

## AC-28b 実績一覧の初期表示（4G）

データ：`pnpm loadtest:seed`（`--rows=3000 --span=550`。19ヶ月・月約158件）

回線は CDP で絞った。Chrome DevTools の "Fast 4G" と同じ値（下り4Mbps／上り3Mbps／遅延20ms）。**絞らずに測ると、開発機から Supabase への速い回線で測ることになり、§5.1 の「回線 4G 想定」と違う。**

```
===== AC-28b 実績一覧の初期表示（4G） =====
  画面に出た総件数                     3,000
  開いてから行が出るまで                  885 ms
  目標値（§5.1）                    3,000 ms
  navigation DOMContentLoaded  50 ms
  navigation loadEventEnd      51 ms
  REST リクエスト数                  9
  最後の REST 完了                  384 ms
  resource エントリ総数              33
```

**885 ms / 3,000 ms。合格。**

読み方。

| | |
|---|---|
| 「開いてから行が出るまで」 | `/entry` を直接開いてから、**表の最初の行が見えるまで**。見出し（件数）が出た時点で止めると描画の時間が落ちるので、行まで含めた |
| REST 9回 | 設定1 + 口座1 + 定期1 + 単発1 + 変更1 + 実績3（3,000件 ÷ 1,000）＋認証1。**読み込みが1回しか走っていない。** 3回走っていた頃なら20回を超える |
| resource 33 | 上限250に遠い。**この数字は下限値ではない** |

**件数（3,000）を先に検査している。** 0件でも3秒は切るので、件数を見ないと「測りたいものを測った」ことにならない（§9.1）。
