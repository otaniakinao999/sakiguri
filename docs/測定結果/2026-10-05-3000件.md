## これまでの実機確認は別の経路だった

備考に「読み込み失敗時に画面を出さないことを実機で確認」と書いてあったが、**それは通信の失敗**であって、AC-35 が見ている**件数の不一致**ではなかった。症状はどちらも「読み込めない」なので、確認したつもりになっていた（§9.1 の5つ目）。

**今回は通信を成功させたまま行だけを落とした。** `route` で応答を横取りし、各ページから1行だけ削る。`Content-Range` の総件数はそのままなので、`fetchAll` の最後の照合が合わなくなる。

ステータスが全部 206 であることを spec 自身が検査している。**400以上が1つでもあれば、確かめたい経路を通っていない。**

## 片方の状態だけを見ていない

spec は3段階で見る。

1. **横取りなしで残高が出る**ことを先に確かめる
2. 横取りして、残高が出ず失敗が示されることを確かめる
3. **横取りをやめて再試行すると直る**ことを確かめる

1 が無いと、「残高が出ない」のが横取りのせいなのか、もともと出ないのかが分からない（§9.1 の4つ目）。

## 落とした数と、足りない数は一致しない

ここで一度落ちた。**アプリは正しく、こちらの算術が誤っていた。**

`fetchAll` は「受け取った件数ぶんだけ」次の開始位置を進める。1行落とすと次の範囲が1つ手前から始まるので、**前のページで落とした行が次のページで拾い直される。**

| ページ | 要求 | 返った | 落とした後 | 累計 |
|---|---|---|---|---|
| 0 | 0-999 | 1000 | 999 | 999 |
| 1 | 999-1998 | 1000 | 999 | 1998 |
| 2 | 1998-2997 | 1000 | 999 | 2997 |
| 3 | 2997-3996 | 3 | 2 | 2999 |
| 4 | 2999-3998 | 1 | 0 | 2999（打ち切り） |

5ページ横取りして、足りないのは1行だけ。**これは `fetchAll` の「受け取った件数ぶんだけ進める」が効いている証拠でもある。** `PAGE_SIZE` ずつ進める実装なら、落とした行は二度と読まれず5行足りなくなる。

spec は「落とした数ぶん少ない」とは書かず、**「足りない」「落とした数より多くは失っていない」「0件ではない」**の3つで見る。0件を許すと、通信の失敗と区別がつかない。

最初は「要対応（N件）」を未消込の数とみなして書いた。**508件で、1,200に届かず落ちた。**

**要対応は `plan.date <= today` で絞ったあとの数で、照合が舐める集合とは別物だった**（1,241 と 508）。画面の数で代用していたら、**測りたい負荷の半分以下で「満たした」と書くところだった**（§9.1 の3つ目）。

## AC-10 閉じて再度開いてもデータが残る

```
  入れた値            126,276
  開き直したあとサインイン済み  はい
  開き直したあとの値       126276
```

**合格。**

**再読込での代用をやめた。** `launchPersistentContext` で同じプロファイルを使い、**ブラウザを本当に閉じて開き直している。** 再読込ではプロセスもタブも閉じないので、「閉じて開く」で失われるものは失われない。

見たのは2つ。片方だけでは足りない。

| | 壊れると何が起きるか |
|---|---|
| セッションが残る | 開き直すとサインイン画面に戻る。データは消えていないが利用者には同じこと |
| 変更が保存されている | 閉じる前の入力が消える。保存は400msのデバウンス後（FR-17） |

入れる値は毎回変えている。**固定値だと、前回の残りを「残った」と読み違える。**

デバウンス（400ms）の5倍待ってから閉じている。**待たずに閉じて消えるのは AC-10 ではなく保存の競合の話**なので、ここでは分けた。
