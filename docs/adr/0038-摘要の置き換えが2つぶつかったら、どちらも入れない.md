# ADR-0038 摘要の置き換えが2つぶつかったら、どちらも入れない

日付：2026-11-12 ／ 対応：FR-59・AC-66 ／ 関連：FR-58・FR-62・CLAUDE.md §2.9

## 文脈

利用者の要望：「仕訳ルールで**摘要も置き換えたい**。例：『振込＊カ）ラボル』→
『㈱ラボル』」。

これで**摘要を書き換える機構が2つになる。**

| | いつ当たるか |
|---|---|
| 仕分けルールの置き換え（FR-59） | `pattern` が摘要の原文に含まれるとき |
| デビット明細の店名（FR-62） | 日付と金額が突き合うとき |

同じ行に両方が当たって**違う名前を言う**ことがある。仕様はどちらが勝つかを
書いていない。CLAUDE.md §2.9 は、こういうときに実装で決めず**優先順位を
確認する**ことを求めている。

## 判断

**どちらも入れない。** 表示名は摘要の原文のままにして、確認画面に両方を出し、
利用者が選ぶ（2026-11-12 の決定）。

同じ名前を言っているときはぶつかりではない（どちらを採っても同じ）。

## 理由

**機械が選ぶと、間違えたほうが黙って入る。** どちらが正しいかは取引ごとに違う
ので、優先順位を決めても半分は外れる。しかも**外れたことが画面に出ない** ――
置き換わった名前は正しそうに見える。

**出すだけなら利用者が判断できる。** FR-50 の「似た行があります」（AC-65）と
同じ形である。**外す（＝勝手に決める）のは取り落とし、出すのは手数。**

**ぶつかった行でルールを使わないことにしたら、保留していた店名に落ちる。**
ぶつかった相手がもう居ないので、その店名を使うのが利用者の意図に近い。

## 置き換えても重複判定が壊れないこと（AC-66）

**原文（`Actual.sourceName`）は置き換えない。** 置き換えるのは表示名だけで
ある。したがって、

- 置き換えた行を取り込んで同じCSVを読み直すと「登録済み」になる
- **置き換えを後から変えても、過去に取り込んだ行の判定は変わらない** ――
  原文は保存時のままだからである

FR-58（ADR-0036）が先に要るのはこのためで、無いと**ルールを作った行が全部、
重複判定から外れる。**

**`pattern`・`accountId`・`direction` の一意制約は変えない。** 置き換える摘要は
「当たる条件」ではなく「当たったときに何をするか」である。条件に入れると、同じ
条件で違う置き換えをする2行が持ててしまい、どちらが勝つかは id の順で決まる
（画面からは見分けられない）。

**照合が成立した行では置き換えない。** そもそもルールを当てていない（AC-57a の
並び）。予定から費目を引き継いだ行の摘要を書き換えると、予定の内容ともCSVの
摘要とも違う名前になる。

## 却下した選択肢

**デビット明細を勝たせる。** 「デビット　４１２６６９」に当たるルールは
『デビット』のような広い `pattern` しか書けず、店名より情報が少ない ―― という
読みは成り立つが、**利用者が意図して書いたものを機械が上書きする**ことに変わり
はない。

**ルールを勝たせる**（AC-57a「利用者が意図して作ったものが機械の推定に勝つ」と
同じ並び）。デビット明細の店名は**推定ではなく、同じ取引の別の記録**なので、
AC-57a の理屈はそのままは当てはまらない。

どちらも「半分は外れ、外れたことが画面に出ない」という同じ欠点を持つ。

## 影響

- `import_rules.replace_name` が増える（0010）。**0009 の後に適用する**
- `ImportRule.replaceName`、`ImportRow.nameConflict` が増える
- 設定のルール表に［摘要を置き換える］の列が増える。確認画面の「次回もこうする」
  にも欄が増える（**初期値は空** ―― 表示名を初期値にすると、置き換えていない行
  にも置き換えのルールができ、結果が同じなので気づけない）
- **設定のルール表を横スクロールにした。** 列が8つになった時点で `w-full` では
  列が潰れ、向きが縦書きになり、置き換える摘要が読めない細い箱になった
  （`RecurringTable` が同じ理由で既にそうしている）。**ページ全体の横スクロール
  （1231px）も同時に消えた**

## 測ったこと

`core/__tests__/rule-replace-name.test.ts`（15件）、
`lib/__tests__/supabase-rows.test.ts`（+4件）。

**「後から変えても過去の判定が変わらない」は往復で測る。** 置き換えた状態で
取り込み、**ルールを変えてから**同じCSVを読み直す。読み直しのルールを変えないと、
原文を保存していなくても通る（置き換え後の名前が両方で同じになる）。

壊して測った10通り。

| 壊し方 | 落ちた |
|---|---|
| ルールの置き換えを当てない | 7 |
| 原文も置き換える | 7 |
| 照合が成立した行にも置き換えを当てる | 1 |
| ルールを使わないときに摘要を戻さない | 2 |
| 空の置き換えを null に寄せない | 1 |
| ぶつかっても片方を入れる | 2 |
| 同じ名前でもぶつかり扱いにする | 1 |
| ぶつかりを解消したときに保留した店名を使わない | 1 |
| **置き換えを DB に書かない** | **最初0 → 3** |
| **置き換えを DB から読まない** | **最初0 → 1** |

最後の2つは、FR-58 のときと同じ穴だった ―― 取込側のテストが DB を通らない。
`supabase-rows.test.ts` に足した。落ちると**置き換えが保存されず、次に開いた
ときルールが元に戻っている。**

実機（`dev/screens/import-wired`・`settings-wired`、1024幅と375幅）で確認した。
摘要の3つの状態（差し替わった行・ぶつかった行・触られていない行）が1画面に出る
こと、ぶつかりのボタンを押すとその名前が入ること、設定のルール表で置き換えが
入った行と空の行の両方が読めること。**DB の往復だけは未確認**（0009・0010 の
適用待ち）。
