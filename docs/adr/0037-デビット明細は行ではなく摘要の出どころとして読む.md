# ADR-0037 デビット明細は行ではなく摘要の出どころとして読む

日付：2026-11-12 ／ 対応：FR-62・AC-69 ／ 関連：制約10・FR-58・FR-18

## 文脈

**同じ取引が2つの明細に出る口座がある。** ドコモSMTBネット銀行では、普通預金の
明細にデビット利用が「デビット　４１２６６９」という**取引ごとに違う番号**で
出て、店名は別のデビット明細に出る。

2026年10月の実データで、**銀行明細232行のうち162行がこの形**だった（11月は
75行のうち67行）。番号は毎回違うので、

- **摘要からの費目推定が当たらない**（`historyKeyOf` の先頭4文字は「デビット」で
  全行同じ）
- **仕分けルールも当たらない。** 利用者が頼んだ「摘要の置き換えルール」
  （FR-59）も、当てる文字列が無いので効かない

店名は別のデビット明細に全部ある。実データでの突き合わせは、同日・同額が162件中
145件、±3日で157件、残り5件は外貨取引で**銀行の額 ＝ 明細の額 ＋ 海外事務手数料**
（FIGMA 3,134＋78＝3,212）だった。

## 判断

**デビット明細を「摘要の出どころ」として読む。行としては取り込まない。**

日付と金額で銀行明細の行に突き合わせ、当たった行の**表示名**を店名に差し替える。
`applyNameSource` は**行数を変えない。**

## 理由

**両方を行として取り込むと、同じ取引が二重に入る**（AC-69）。残高が二重に動き、
年月別収支も倍になる。利用者が気づくのは残高が合わなくなってからである。

**原文は触らない**（FR-58）。差し替えるのは表示名だけで、`sourceName` はCSVから
読んだままにする。書き換えると、次に同じ銀行明細を読んだときに重複判定が
当たらなくなる。

**ルールが当てるのも原文である。** 表示名で当てると、差し替わった行にはルールが
当たらなくなり、「このファイルの何行に当たるか」（AC-57e）も実際と違う数になる。
`ruleTargetOf` を足して、`buildImportRows`・`redecideWithoutRule`・
`countRuleMatches` の3箇所が同じ値を見るようにした ―― **以前は最初の1つだけが
原文を見て、残り2つが表示名を見ていた**（差し替えが入るまでは同じ値だったので
食い違っていなかった。§2.8）。確認画面の「次回もこうする」の `pattern` の初期値も
原文にした。

**厳しい当たり方を先に使い、1件ずつ使い切る。**

| 段 | 日付 | 金額 |
|---|---|---|
| 1 | 同日 | 同額 |
| 2 | ±3日 | 同額 |
| 3 | 同日 | 手数料ぶんの差 |
| 4 | ±3日 | 手数料ぶんの差 |

**違う店名の候補が2つ以上あるときは当てない**（AC-69「勝手に近いものへ
当てない」）。どちらか選ぶと、間違えたほうが黙って入る。同じ店名が並ぶのは
入れ替えても同じなので当ててよい。

**出金の行だけに当てる。** デビット明細は利用の一覧で向きを持たない。入金の行に
も当てると、同額の返金や振込に店名が付く。

**空欄の店名で上書きしない**（11月の実データで7件）。ただし**枠は使う** ――
その取引の相手はこれだと分かっているので、ほかの店名に当てさせない。同じ理由で
**空欄の行を読み飛ばさない** ―― 落とすと、その取引に当たるはずだった銀行の行が
別の店名に当たりうる。

## 却下した選択肢

**両方を行として取り込み、重複判定で片方を外す。** 判定の鍵（口座・日付・収支・
金額・摘要）のうち摘要が違うので当たらない。日付もずれる。**外せない。**

**デビット明細を主にして、銀行明細のデビット行を落とす。** 銀行明細の残高の列が
使えなくなる（FR-61 の検算が成り立たない）。落とす行を機械が決めることになり、
外すと取り落とす。

**手数料の上限だけを決める。** 大きな金額では窓が広く（200,000円で5%なら
1万円まで）、**無関係な額に当たりうる。** ありうる帯（0.5%〜5%）に収めた。

## 影響

- `src/core/name-source.ts` が増える（純関数）
- `ImportRow.nameFrom`（`"rule" | "source" | null`）が増える。確認画面の摘要列が
  「明細から差し替え（元：…）」を併記する ―― **見せないと、当たった相手が
  正しいかを確かめられない**
- 取込画面に［デビット明細を選ぶ］が増える。**読み取るたびに当て直す**ので、
  読み取ったあとに出どころを選んでも効く
- **帯の数字（±3日・0.5%〜5%）は仕様に書かれていない。** 実データの2.49%が
  入る帯としてこちらで決めた値である

## 測ったこと

`core/__tests__/name-source.test.ts`（21件）。

**当たる行だけで測ると、全部差し替える実装と区別が付かない。** 同じ実行の中で
「差し替えた3行」と「触らなかった3行」の両方を数えている。

壊して測った12通り。**2つは最初割れなかった。**

| 壊し方 | 落ちた |
|---|---|
| 当たらなかった行にも当てる（いちばん近いものへ） | 1 |
| 空欄の店名で上書きする | 3 |
| 空欄に当たった行の枠を使わない | 1 |
| 1件ずつ使い切らない | 1 |
| **入金の行にも当てる** | **最初0 → 1** |
| 原文を書き換える | 1 |
| 日付のずれを無制限にする | 2 |
| 手数料の下限を見ない | 1 |
| 手数料の上限を見ない | 1 |
| **厳しい順に試さない** | **最初0 → 1** |
| 空欄の店名の行を落とす | 4 |
| ルールを表示名に当てる | 3 |

**「入金の行にも当てない」は、当てられる相手が0件の状態で測っていた** ――
入金の行に当たりうる明細の行が、先に出金の行に使われていた。相手が0件なら
向きを見ない実装でも何も起きないので通る（§2.11 の3つ目の形）。相手が残る
データを足した。

**「厳しい順」は、入れ替えても同じ答えに着くデータだった** ―― 入れ替えると
「違う店名の候補が2つ」になってどちらも当たらず、ゆるい段を飛ばして正解に
着いていた。ゆるい段で候補が1つだけになるデータを足した（§2.11 の4つ目の形：
正しい実装と壊した実装が同じ結果になるデータ）。

**実機は未確認**（FR-58 と同じコミット群なので、0009 の適用待ち）。
