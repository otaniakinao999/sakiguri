# 0013. 利用イベントに金額を入れない。利用者には insert しか与えない

## 文脈

PoC開発計画 §1 は「ローカル保存のみでは、検証項目3つのうち2つが測れない」として、認証と最小限の計測を持つ構成を求めている。測るのは5つ（§4）。

| 指標 | 取り方 |
|---|---|
| 初回30日以内の2回目CSV取込率 | 取込イベントのユーザー別カウント |
| 登録後14日時点の予定登録件数（中央値） | 予定テーブルの件数をスナップショット |
| 3ヶ月以上先まで予定があるユーザーの比率 | 北極星指標の分母と分子 |
| 残高警告からの操作率 | 警告表示イベントと、直後の操作イベント |
| 週あたりのログイン日数 | セッション記録 |

イベントを貯めるテーブルを1つ足す。そこに何を入れ、誰に何を許すかを決める必要がある。

素直に作ると、イベントには「文脈」を入れたくなる。取り込んだ金額の合計、費目の名前、口座名、ファイル名。デバッグにも分析にも役立つように見える。

## 判断

### 1. イベントに資金繰りの中身を入れない

入れないもの：**金額、費目名、取引先名、口座名、ファイル名、IP、User-Agent、日付そのもの。**

入れてよいもの：**件数、期間の長さ（日数・月数）、種別、口座数。**

記録するのは「取り込んだ」という事実であって「いくら」ではない。

型でも縛る。`EventProps` は `Record<string, number | boolean>` で、**自由入力の文字列を許さない**。文字列を許すと、そこに名称が入り込む。加えて `FORBIDDEN_PROP_KEYS` で名前でも弾き、開発中は例外で落とす。

### 2. 利用者には insert しか与えない

`usage_events` の RLS ポリシーは insert だけ。**select も update も delete も書かない。**

- select：自分のイベント履歴を見る画面が v1.0 に無い。使わない権限は与えない
- update / delete：イベントは訂正も削除もしない記録

集計はダッシュボードの SQL Editor から secret 権限で行う。**secret キーはアプリにも CI にも置かない。**

### 3. 時刻はサーバーが決める

`occurred_at` の既定値は `now()`。クライアントから送らない。端末の時計は信用しない。

### 4. 退会したら消える

`user_id` は `auth.users` への参照で `on delete cascade`。退会後30日で物理削除する方針（非機能要件 5.1）に、イベントも自動で従う。

## 理由

**イベントに金額を入れると、アクセス制御の違う場所に資金繰りデータの複製ができる。** 本体（`accounts` / `actuals` ほか）は RLS で1行ずつ守っているのに、その要約が別のテーブルに、別のポリシーで置かれることになる。守る対象が2つになった時点で、片方の設定漏れが全体の漏れになる。**本体を RLS で守っている意味がなくなる。**

しかも計測テーブルは「分析のために広く読めるようにしたい」という圧力が常にかかる。金額が入っていなければ、その圧力に負けても失うものが小さい。入っていれば、負けた瞬間に資金繰りが漏れる。

**select を与えないのは、権限の最小化そのものである。** PoC開発計画 §5.4 が挙げる RLS の事故は「必要な制限を書き忘れる」形で起きる。書く権限が少ないほど、書き忘れる余地も小さい。`supabase-js` の `.insert()` は `.select()` を連鎖しない限り行を返さないので、insert だけでも動く。

**外部の解析ツールを入れないのも同じ判断である**（PoC開発計画 §4）。送り先を自前の Supabase だけにすれば、資金繰りの金額が第三者に渡る経路そのものが無い。

## 却下した選択肢

**イベントに金額の合計を入れる。** 「取り込んだ総額」はモニターの規模感を知るのに役立つ。ただし上記のとおり、複製を作ることになる。規模感が必要なら、本体のテーブルを secret 権限で集計すればよい。同じ数字が2箇所にある必要はない。

**select のポリシーを `auth.uid() = user_id` で書いておく。** 将来「自分の利用履歴」画面を作るときに備える案。使う予定のない権限を先に与えることになる。画面を作るときにポリシーを足せばよく、それは1行で済む。

**外部の解析ツール（GA など）を使う。** 実装は楽になる。PoC開発計画 §4 が明示的に否定している。

**イベントを本体のテーブルに持たせる（`actuals` に `imported_at` を足すなど）。** テーブルを増やさずに済む。ただし「いつ画面を見たか」のような、データに紐づかない事実を置けない。また本体のスキーマが計測の都合で膨らむ。

**クライアントの時刻を `occurred_at` に使う。** 端末の時計がずれていると、時系列の指標（2回目取込率、警告からの操作率）が壊れる。順序が入れ替わることすらある。

## 影響

- `usage_events` は利用者から読めない。**アプリの画面に利用履歴を出せない。** 出すときはポリシーを足す
- 指標の SQL は `supabase/analytics/metrics.sql` に置いてある。マイグレーションではなく、手で流す
- 同ファイルの末尾に**点検クエリ**を置いた。`props` に禁止キーや文字列が入っていないかを調べる。1行でも返したらこの ADR が破られている
- `track()` は投げっぱなし。失敗しても画面を止めない。指標が1件欠けることより、利用者の操作が止まるほうが重い
- イベントの種類を足すときは `EventMap` に型を書く。props の形が型で決まるので、うっかり金額を渡すとコンパイルが通らない
- v2.0 で税理士の代理操作（FR-31）を入れるとき、**操作履歴（AC-17）はこのテーブルとは別に設計すること。** あちらは「誰が何を変えたか」を残す監査の仕組みで、金額や対象を記録する必要がある。要件も保護も違う
