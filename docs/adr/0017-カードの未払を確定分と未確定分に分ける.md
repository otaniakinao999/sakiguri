# 0017. カードの未払を確定分と未確定分に分け、既存値のデータ移行は行わない

## 文脈

CL-2 手順4 は「基準日時点の未払残高を、最初に到来する引落日に加算する」と定義され、実装も単一の `balance` を1つの引落日に載せていた。

```ts
for (const account of accounts) {
  if (!isCard(account) || account.balance === 0) continue;
  bump(account, firstSettleDateOnOrAfter(account, asOf), account.balance);
}
```

これが誤っている。**締め翌月払いのカードでは、基準日時点で未払の束が2つ同時に存在する。**

月末締め・翌月27日払い、基準日 9/17 の場合：

| 未払の束 | 本来の引落日 |
|---|---|
| 8月利用分（締め済み） | 9/27 |
| 9/1〜9/16 利用分（まだ締まっていない） | 10/27 |

単一の値で両方を表すと、合計が 9/27 にまとめて計上される。**最大1ヶ月ぶんの支出を1ヶ月前倒しで計上する。** 月15万円使うカードなら7〜8万円が1ヶ月早く落ちる計算になる。

方向が問題である。**近い将来の残高が実際より低く出る。** 生活防衛ラインの警告が誤って鳴り、PoC で測る唯一の指標「残高警告からの操作率」が汚染される。FR-46（`key` なし実績の二重計上）とまったく同じ構図で、原因が違う。

## 判断

`CardAccount` に項目を1つ足し、CL-2 手順4 を2つの束に分ける。

| 項目 | 意味 | 計上先 |
|---|---|---|
| `balance` | **次回の引落額**（確定済み請求額） | 基準日以降で最初に到来する引落日 |
| `unbilledBalance` | 次回の引落に含まれない未確定の利用額 | その次に到来する引落日 |

`settleDateAfter(card, asOf, nth)` を導入し、`nth = 0` と `nth = 1` で2つの引落日を得る。`firstSettleDateOnOrAfter` は `nth = 0` の別名として残す。

**既存値を2つに分割するデータ移行は行わない。** `unbilled_balance` は既定値0で追加し、利用者に入れ直してもらう。

`payMonthOffset = 2`（翌々月払い）では束が3つになりうるが、2項目では表現できない。3束目は `unbilledBalance` に含めて2回目の引落日に載せる近似とする（OI-19）。

## 理由

**2つの値は利用者が入力できる。** カード会社の明細に「確定金額」「未確定分」として並んで表示されている。推定で分割するのではなく、明細に書いてある数字を写してもらう。入力欄のラベルもその言葉に寄せた。

**データ移行を書かないのは、分割の根拠がどこにも無いからである。** 既存の `balance` は「未払残高の全額」として入力された1つの数値で、そのうちいくらが確定分でいくらが未確定分かを決める情報が残っていない。締め日と基準日から機械的に按分することは考えられるが、それは利用者が実際に使った額とは無関係な推定にすぎない。**推定した数字を残高計算に入れるのは、いま直している誤りと同じ性質の誤りである。**

0 を入れておけば、少なくとも「前倒しで計上する」誤りは消える。未確定分が反映されない状態は残高を楽観視する方向だが、利用者が明細を見て入力すれば解消する。いまはテストアカウントしか存在しないため実害もない。

**`unbilledBalance` を省略可能（`?`）にしてある。** 列を足す前に保存されたデータは読み戻すと 0 になるが、型の上でも未設定を表現できるようにして、既存のテストや `blankCardAccount` を通らない経路が壊れないようにした。

## 却下した選択肢

**締め日から機械的に按分する移行を書く。** 上のとおり、根拠のない数字を残高に入れることになる。「移行した」という事実だけが残り、値が信用できない状態のほうが、0 で明示的に未入力とするより悪い。

**引落日ごとの内訳を配列で持つ。** `payMonthOffset = 2` の3束目まで正確に表せるが、利用者が入力する項目が可変長になる。カード会社の明細は「確定金額」「未確定分」の2つしか出さないので、3つ目に何を入れればよいか利用者が判断できない。翌々月払いのカードは少ないため、近似のまま OI-19 に残す。

**`balance` の意味を変えずに `unbilledBalance` だけを足す。** `balance` が「全額」のままだと、`balance` と `unbilledBalance` の和が実際の未払を超える。二重に数えることになる。

## 影響

- `balance` の意味が「未払残高の全額」から「次回の引落額」に狭まる。既存値はそのまま残り、意味だけが変わる
- 既存のカードは `unbilledBalance = 0` として扱われる。従来と同じ計算結果になるため、直した誤りはそのカードには残る。利用者が入力した時点で直る
- マイグレーション 0005 で `unbilled_balance bigint not null default 0` を追加
- 口座・カードの表に列が1つ増える。預金口座の行では「—」
