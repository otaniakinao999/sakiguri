# 0015. 数値入力欄は入力途中の文字列を保持する

## 文脈

`NumberInput` は制御された入力で、値を `number` で持ち、表示はその値から作っていた。

```tsx
value={value}
onChange={(e) => {
  const digits = e.target.value.replace(/[^\d]/g, "");
  const parsed = digits === "" ? 0 : Number(digits);
  onValueChange(max === undefined ? parsed : Math.min(parsed, max));
}}
```

利用者から「口座の基準日残高が入力できない」という報告があり、ブラウザで実際の挙動を測ったところ2つの欠陥が出た。

**欄を空にできない。** 全部消すと `digits` が `""` になり 0 が返る。値が 0 になると表示も `"0"` に戻るため、欄には常に何か文字が残る。既存の残高を消して入れ直す操作ができず、途中にキャレットを置いて打つと既存値と連結する（`100000` の欄に `500000` と打つと `500000100000`）。

**マイナスが符号ごと消える。** `[^\d]` が `-` を落とすため、`-8000` が `8000` になる。拒否ではなく**黙って正の数に化ける**。当座借越や残高マイナスを入力すると、残高予測が入力値の2倍ずれる。

要件定義書 §3.2 は `Account.balance` を「基準日時点の残高。card の場合は未払残高（正の値）」と定義しており、預金口座の残高に符号の制限を置いていない。CL-3 の残高計算の起点がここなので、入力できないと予測そのものが成り立たない。

また日本語IMEで全角数字（`５`）が打たれると `[^\d]` に落とされ、値が黙って 0 になる。

## 判断

**表示用の文字列を欄が自分で持ち、値とは別に管理する。**

- `draft: string | null` を `useState` で持ち、表示は `draft ?? String(value)`
- `onChange` のたびに `draft` を更新し、同時に解析した値を `onValueChange` で親へ渡す
- **欄からフォーカスが外れたら `draft` を捨てる。** 以後は値から作った正規形を出す
- 上限で丸めたときだけ、その場で `draft` を捨てて丸めた値を見せる

解析は純関数 `parseNumberField`（`src/lib/number-field.ts`）に切り出す。

- 空文字と符号だけの状態（`""` `"-"`）を `text` にそのまま残し、値は 0 とする
- 負を受けるかは `allowNegative` で呼び出し側が決める。**既定は false**
- 全角数字を半角に直す
- `-` に加えて U+2212（表示に使っている `MINUS`）、全角 `－`、通帳の `▲` `△` をマイナスとして受ける（§4.3 の正規化規則に合わせる）
- `allowNegative` が false のときマイナス記号は**無視する**（符号を読んでから 0 に丸めない）

呼び出し側では、預金口座の残高だけが `allowNegative` を立てる。

```tsx
allowNegative={!isCard(account)}
```

## 理由

`number` を唯一の状態にすると、`""` と `0` と `"-"` を区別できない。この3つは入力操作としては別物であり、区別できない限り「消して入れ直す」が成立しない。下書きを持つのは、表示可能な状態が値の集合より広いことを認めるということである。

フォーカスが外れたときに捨てるのは、`007` や `-` のような正規形でない文字列を残さないため。入力中は自由に、確定したら正規形に、という切り分けは利用者の期待と一致する。

`allowNegative` の既定を false にしたのは、既存の呼び出し（金額・事業割合・発生日・締日・支払日・防衛ライン）をすべて現状維持にするため。要件定義書 §3.2 が `amount` を「絶対値」と定めており、符号を持たせてよい欄のほうが例外である。例外側を明示的に書かせる。

符号を「無視」にしたのは、カードの未払残高に `-8000` と打たれた場合に 0 にするより 8000 にするほうが「絶対値」という仕様に沿うため。どちらも利用者の意図とは違うが、`balance` に 0 が入ると資金繰りの起点が消えるので害が大きい。

解析を純関数に切り出したのは、テストのため。`src/lib/` の関数は DOM を必要とせず、既存の vitest（`environment: "node"`）でそのまま検査できる。DOM のテストには jsdom が要るが、CLAUDE.md §2.7 の許可リストに無い（[[0001-金額を円単位の整数で扱う]] と同じく、依存を増やす判断は別に行う）。

## 却下した選択肢

**`type="number"` を使う。** ブラウザが符号と空文字を扱ってくれるが、`e.target.value` が `""` になる条件がブラウザごとに違い、ホイールで値が変わる事故があり、`,` 区切りの貼り付けを受けられない。等幅右寄せの見た目も揃わない。

**下書きを持たず、`value` を `number | ""` にする。** 型が滲む。`""` が `AppData` まで流れると CL-3 が `NaN` を返す。境界で止めるほうが安全である。

**`allowNegative` ではなく `min` を渡す。** `max` と対称で見た目はよいが、既定値を 0 にすると「符号を許す」ことが `min={undefined}` という消極的な書き方になる。呼び出し側で意図が読めない。

**フォーカス時に全選択する。** 連結の問題は軽くなるが、空にできない問題は残る。下書きを入れれば両方解決するため、追加の挙動を足さない。

## 影響

- 既存の呼び出しは引数を変えない。挙動も変わらない（符号は従来どおり無視、上限の丸めも従来どおり）
- 全角数字が値になるようになった。従来は 0 に落ちていた
- 口座の残高欄だけ `inputMode` が `numeric` から `text` に変わる。携帯の数字キーパッドに符号が無く、マイナスが打てないため。符号を使わない利用者にはキーボードが広くなる分だけ不利になる
- `parseNumberField` は `src/lib/` の純関数なので、CSV取込の金額正規化（CL-7）と規則が重複している。統合は行っていない。CL-7 は列の符号解釈（入金列／出金列）という別の関心を持つため
