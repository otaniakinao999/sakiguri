# ADR-0026 仕分けルールの印を、手で直した行から外す

- 状態：採用
- 日付：2026-11-10
- 対象：CL-10、AC-57a / AC-57b、`src/core/csv.ts`

## きっかけ

CL-10 の「このルールを使わない」は、**そのルールで決まっていた行だけ**を
費目推定で決め直す。取込行を丸ごと作り直すと、利用者がそこまでに手で直した
費目も、外した取込のチェックも全部消えるためである（AC-57b）。

ここで仕様が「`ImportRow` は『手で直した』という印を持たないので、作り直しと
区別がつかない」と書いている。**ところが、そこまでに手で直した行が、同じ
ルールで決まった行だったときはどうなるかが書かれていない。**

- 行 A：ルール R が費目を決めた
- 行 B：ルール R が決めたあと、**利用者が費目を手で直した**
- ここで「R を使わない」を押す

**「R で決まっていた行」に B を含めると、仕様が守ろうとした当のもの
（手で直した費目）を、狭めた側の処理が壊す。**

## 決めたこと

**費目を手で直した行から、`ruleId` と `guessedFrom` を外す。**

```ts
export function editImportRowCategory(row: ImportRow, categoryCode: string): ImportRow {
  return { ...row, categoryCode, costType: …, ruleId: null, rulePattern: null, guessedFrom: null };
}
```

これで2つが同時に成立する。

| | |
|---|---|
| 表示（AC-57a） | 手で直した行は「ルールで決まった」と言わなくなる。**実際そうではない** |
| 決め直し（AC-57b） | 「R で決まっていた行」から自然に外れる。B は触られない |

## 理由

**「手で直した」という印を別に持たせない。** 印と `ruleId` の2つを持つと、
「印は立っているが `ruleId` も残っている」状態が作れてしまい、どちらが本当かを
決める規則がもう1つ必要になる（CLAUDE.md §2.8）。

`ruleId` は「**いまこの行の費目を決めているのはこのルールである**」という意味で
持つ。手で直した瞬間にそれは成り立たなくなるので、外すのが意味に忠実である。
印を足す設計だと `ruleId` の意味が「かつてこのルールが決めた」に変わり、
表示（AC-57a）は印を見て、決め直し（AC-57b）は `ruleId` を見ることになる。

## 却下した選択肢

**`edited: boolean` を足して、立っている行を決め直しから除く。**
上のとおり、同じことを2つの場所で表すことになる。加えて `edited` は「何を
直したか」を区別しないので、金額だけ直した行も費目の決め直しから外れる。

**ルールで決まった行は手で直せないようにする。** 直すために「使わない」を
先に押させることになり、ルールを1つ外すだけで**ほかの行まで決め直される。**
順序が逆で、利用者の手数も増える。

## 影響

- 確認画面の「決まり方」は、予定から / ルール（`pattern`） / 推定（名称） /
  — の4通りになる。手で直した行は「—」になる
- `redecideWithoutRule` は `row.ruleId !== ruleId` の行を**同じ参照で返す。**
  値が同じでも別オブジェクトを返すと、作り直す実装との差がテストで出ない

# 付記：マイグレーション未適用でも読み込みが落ちないようにした

`import_rules` を読むのは `loadAppData` の `Promise.all` の中である。
**テーブルが無いと、1つの 42P01 でアプリ全体が読み込めなくなる。**

CLAUDE.md §2.5.1 は「適用が済むまで push しないか、未適用でも壊れないコードに
するか、どちらかを選べ」と言っている。ここでは後者を採った。順序を人の手順
だけに預けると、逆順になった瞬間に**全員が画面を開けない**。

`fetchRules` は「テーブルが無い」（42P01 / PGRST205）だけを見分けて空の一覧を
返す。**ほかのエラーは投げる** ―― 権限や通信の失敗を「空」として扱うと、
利用者のルールが消えたように見える。

**ただし未適用のままルールを作ると保存が失敗する**（画面に出る）。黙って
消えるよりはよいが、**適用を先に行うこと。**
