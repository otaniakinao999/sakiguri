# 0003. 残高計算をクライアント側で行う

## 文脈

残高予測は基準日から最長52ヶ月ぶんの**日次累積**である（CL-3）。1ユーザーあたり1万5千日ぶんの行を毎回組み立てる。

要件定義書 5.1.1 は、インフラ費が売上ではなく MAU に比例することを設計判断として明記している。PoC開発計画 §2 も同じ立場を取る。プロトタイプはクライアント計算で動作を検証済みである。

## 判断

`src/core/` を**純関数群**として実装し、ブラウザ上で実行する。

- React / DOM / fetch / `Date.now()` を import しない
- 現在日時は引数 `today: DateStr` で受け取る。`new Date()` を core 内で呼ばない
- サーバーは保存・認証・計測のみを担う
- CSV の解析もクライアントで行い、確定した実績のみを送信する。ファイル本体はサーバーに保存しない

## 理由

日次52ヶ月の累積をサーバーで回すと、原価が MAU に比例して跳ねる。クライアントで実行すれば追加原価はゼロになる。要件定義書 5.1.1 が挙げる4つの原価判断のうち2つ（計算の実行場所、CSV解析の実行場所）がここに含まれる。

副次的な効果のほうが大きいかもしれない。純関数であることが**テスト可能性**を生む。PoC開発計画 §5.1 は「計算ロジックの静かな回帰」を最大の懸念に挙げている。資金繰りの計算は間違っていても動き、残高が10万円ずれていても画面はエラーを出さない。純関数に切り出せば、受入基準 AC-01〜17 をテストとして固定でき、UI 変更で計算が壊れたときに検知できる。

CSV をサーバーに送らない設計は、口座情報を含みうるファイルを保持しないという安全側の判断でもある（要件定義書 5.1.1、5.3）。

## 却下した選択肢

**サーバーで計算して結果を返す。** MAU 比例のコストが乗る。要件定義書 5.1.1 が明示的に否定している。

**サーバーで計算し、結果をキャッシュする。** 予定を1件変えるたびに全期間のキャッシュが無効になる。予実管理は編集頻度が高い（BS-3 予定追加、BS-4 繰延判断はいずれも「随時」）ため、キャッシュ率が上がらない。複雑さだけが増える。

**Server Components で計算する。** 実行場所がサーバーになるため、原価の問題は同じ。加えて純関数がサーバー専用になり、テストは書けても UI の応答性（非機能要件 5.1：再計算300ms以内）を満たしにくい。

## 影響

- `src/core/` は CLAUDE.md §2.3 の制約下に置かれる。ロジック単位でファイルを分ける（forecast / cash / balance / proration / pl / monthly / csv / loan / receivable）
- 計算結果はクライアントの状態であり、サーバーには入力データ（口座・定期項目・単発予定・実績・オーバーライド）のみを保存する
- パフォーマンスは PoC では作り込まない。プロトタイプは毎レンダーで全期間を再計算しているが、PoC開発計画 §5.7 が「実測してから対処」としている。増分計算や Web Worker は先に入れない
- 非機能要件 5.1 の「実績10万件で劣化しない」は本開発の課題として残る
