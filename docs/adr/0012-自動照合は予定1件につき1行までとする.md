# 0012. 自動照合は予定1件につき1行までとする

## 文脈

CL-7 は自動照合をこう定めている。

> 未消込の予定インスタンスのうち、以下をすべて満たす**最初の1件**を候補とする。
> - 金額が完全一致
> - 日付の差が12日以内
> - 収支の向き（income / expense）が一致

「最初の1件」は CSV の1行から見た話であり、**逆向き**、つまり1件の予定が複数の行に照合されうるかは書かれていない。

これは実際に起きる。同じ金額の支出が月に2回あり、予定が1件しか登録されていない場合、CSV の2行が同じ予定に当たる。

```
CSV     4/25 スーパー 5,000
        4/26 スーパー 5,000
予定    4/25 食費     5,000  ← 1件だけ
```

素直に実装すると両行が同じキーを持つ。取り込むと、同じ予定インスタンスキーを持つ実績が2件できる。CL-3 の消し込み（手順2）はキーの集合で予定を除外するので、予定は1件ぶんだけ消え、実績は2件とも残高に効く。残高としては正しいが、**予実の対応が崩れる。** 年月別収支で「予定1件に対して実績2件」という状態になり、どちらが当初の予定だったのか追えなくなる。

## 判断

**1回の取込のなかで、1件の予定は最大1行にしか照合しない。**

`matchPlan` は照合済みキーの集合を受け取り、そこに入っている予定を候補から飛ばす。`buildImportRows` は行を上から処理し、照合が成立するたびにキーを集合へ加える。

上の例では、1行目が予定に照合され、2行目は照合先なし（`matchedKey: null`）になる。

## 理由

**消し込みは1対1の対応である。** 「予定インスタンスに実績を紐づけ、予測から除外する操作」（要件定義書 §1.3）という定義からして、1件の予定に2件の実績が紐づく状態は想定されていない。

**照合されなかった行は、確認画面で利用者が処理できる。** CL-7 は「取込前に全行を一覧表示し、行ごとに 取込可否・収支・固定変動・費目・事業割合 を修正できること」を求めており、照合先が無い行はそのまま突発的な支出として取り込めばよい。**取りこぼしても実害が小さい**のに対し、二重に紐づけると予実が崩れて後から直しにくい。安全側に倒す。

**行の順序は決まっている。** CSV は上から処理し、候補は予定の配列順（CL-1 が返す日付昇順）を見る。どちらも決定的なので、同じ入力からは同じ結果が返る（CLAUDE.md §2.3）。

## 却下した選択肢

**制限しない（プロトタイプの挙動）。** 実装は単純。ただし上記の崩れが残る。プロトタイプは1ファイル1,500行の検証用実装であり、この点を検討した形跡はない（PoC開発計画 §3、§5.10）。

**最も日付が近い予定を選ぶ（貪欲法から最適割当へ）。** 「最初の1件」ではなく全体として最も自然な組み合わせを選ぶ案。精度は上がりうるが、CL-7 が明示している「最初の1件」から外れる。加えて、どの組み合わせが「正しい」かは利用者にしか分からない。確認画面で直せる以上、複雑な割当を core に持ち込む理由がない。

**2行目も照合したうえで、確認画面で重複を警告する。** 警告の仕様が要件定義書にない。仕様に無い UI を前提にした core の挙動を作らない（CLAUDE.md §1）。

## 影響

- 同じ金額・近い日付の予定が実際に複数あるなら、予定も複数登録されている必要がある。1件しか登録していなければ、2行目は未照合のまま取り込まれる
- 制限は**1回の取込のなか**だけに効く。取込を2回に分ければ、同じ予定に2回目の照合が起こりうる。1回目の取込で実績が登録され、その予定は消し込み済みになるため、2回目の候補（未消込の予定）には現れない。したがって実際には起きない
- `matchPlan` は照合済みキーの集合を引数で受け取る。関数の外に状態を持たないため純関数のまま
- この挙動は `csv.test.ts`「同じ予定を2行が取り合わない」「候補が1件しかなければ2行目は照合されない」で固定してある
