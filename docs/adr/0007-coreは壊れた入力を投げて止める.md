# 0007. core は壊れた入力を黙って受け流さず、投げて止める

## 文脈

`src/core/` の関数は日付文字列と金額を受け取る。書式の壊れた日付（`2026/09/15`）や存在しない日付（`2026-02-30`）が渡ったとき、どう振る舞うかを決める必要がある。

選択肢は3つある。何もせず通す、既定値に読み替える、投げる。

このプロダクトでの失敗の性質を考えると、判断が変わる。PoC開発計画 §5.1 が指摘するとおり、**資金繰りの計算は間違っていても動く。** 残高が10万円ずれていても画面はエラーを出さない。壊れた日付を黙って通すと、並び順と期間の絞り込みが静かに狂い、残高が間違ったまま表示される。利用者は気づかない。

## 判断

core は**受け取った日付が仕様どおりでなければ `RangeError` を投げる。**

- `parseDate` は `'YYYY-MM-DD'` の書式と日付の実在を検証する
- `lastDayOfMonth` / `dayInMonth` は月と日の範囲を検証する
- CL-1 は単発予定の `date` と、オーバーライドの `date` を検証する

不正な値を既定値（今日、月初、0円など）に読み替えることはしない。

## 理由

**壊れたデータで計算を続けるより、止まるほうが安全である。** 例外は画面に出るが、1円ずれた残高は出ない。

投げる対象を「プログラムの誤り」に限っているのも要点である。core に渡るデータは、UI とストレージが書いたものであって、利用者が直接打ち込んだ生の文字列ではない。CSV 取込（CL-7）のように利用者の入力を扱う層は、core に渡す前に正規化と確認画面を通す仕様になっている（要件定義書 CL-7「確認画面：取込前に全行を一覧表示し、行ごとに修正できること」）。したがって core に不正な日付が届いた時点で、それは利用者の入力ミスではなく実装の欠陥である。欠陥は早く大きな音で落ちるべきである。

## 却下した選択肢

**不正な値を無視して、その予定を落とす。** 静かにデータが消える。予定が1件消えた残高は、正しく見えるが間違っている。最も避けたい壊れ方。

**既定値に読み替える（不正な日付を今日にする等）。** 同じ理由で危険。しかも「なぜこの日に予定があるのか」を後から追えなくなる。

**Result 型（`{ ok: true, value } | { ok: false, error }`）を返す。** 型で扱い漏れを防げるため筋はよい。ただし CL-1〜CL-9 が互いを呼び合う構造（CL-3 が CL-2 を呼ぶ、CL-6 が CL-3 を呼ぶ）なので、全段で分岐を書くことになり、計算そのものが読みにくくなる。読みにくい計算コードは、PoC開発計画 §5.1 が懸念する「静かな回帰」を招く。ここでは計算の可読性を優先した。

**zod でスキーマ検証する。** zod は CLAUDE.md §2.7 の許可リストにある。ただし用途は境界（フォーム入力、CSV取込、サーバーから読んだデータ）の検証であり、core の内部で毎回スキーマを回すのは過剰。core の検証は日付書式という一点に絞る。境界での zod 利用は別途決める。

## 影響

- core の関数は例外を投げうる。呼び出し側（UI 層）は、保存データが壊れている場合に備えてエラー境界を持つ必要がある。これは v1.0 の画面実装（PoC開発計画 フェーズ2）で扱う
- 金額については現時点で検証を入れていない。`Yen` は整数の約束だが型では強制できない（[[0001-金額を円単位の整数で扱う]]）。整数性の検証を入れるかは、CL-8（借入返済）の端数処理を書く段階で判断する
- テストで「壊れた入力は投げる」ことを固定してある。将来これを緩める変更は、テストが落ちることで気づける
