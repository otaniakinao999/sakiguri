# ADR-0045 共有の検査を、ポリシーより先に作る

日付：2026-11-16
関連：CLAUDE.md §2.5・§2.8・§2.11、ADR-0044

## 文脈

権限・招待・アカウント管理を、モニター配布の**前**に作ると決まった
（2026-11-16）。**後回しにすると値段が上がる唯一の項目**だからである ――
8表の所有の述語を書き換える作業は、利用者が実質1人のいまと、他人の
資金繰りが入ったあとでは危険度が桁で違う。

設計は案A（共有の付与）。`grants` を1つ足し、`user_id` は触らない。
権限は閲覧と編集の2段。

**ただし、この判断は測る側だけの話である。** `grants` の表も8表の
ポリシーもまだ書かない。

## 判断

### 1. ポリシーより先に検査を書き、**先に落とす**

ポリシーを書いてから流して全部通ると、**「正しいから通った」のか
「測れていないから通った」のかが区別できない。**

### 2. 「前提なし」を「通過」と数えない

共有の条項は半分が「**できないこと**」である ―― 閲覧では書けない、
失効したら見えない、客は `grants` を書けない。

**これらは、共有の仕組みが1つも無い今でも「通る」。** 相手に何も
与えていないので、できないのは当たり前である。これを緑で出すと、
**48通りの大半が通過と見え、何も測れていないことが隠れる。**

だから各条項は**前提**（どんな付与があるか）を宣言し、前提を作れない
ときは `前提なし` と出す。**通過とも失敗とも数えない。**

これは §2.11 の「『無いこと』を測る条項は、同じ実行で『在ること』も
測る」を、組み合わせの表に当てはめた形である。

### 3. 負荷試験アカウントを2つにする

**1つだと「他人の行が見えない」を測れない** ―― 見えない相手が居ない
（§2.11 の3つ目の形：対象の行が0件なら、その条項は必ず通る）。

`LOADTEST2_EMAIL` / `LOADTEST2_PASSWORD` を足し、
`pnpm loadtest:account --second` で作る。**2つが同じアドレスなら止まる。**

**番人を枠ごとに効かせる。** `client.ts` は「`+loadtest` を含むか」しか
見ておらず、2026-11-15 に完全一致を足したが、それは `roundtrip.ts` の
中だった。**枠が2つになると、1つ目のつもりで2つ目に入っていても通る**
ので、判定を `client.ts` へ移し、**どちらの枠か**まで見る（§2.8 ――
同じ判定を2箇所に書かない）。

### 4. `usage_events` は共有の対象外

| | |
|---|---|
| **誰も select できない** | 所有者も読めない（select のポリシーが無い）。「見えない」を測っても**必ず通る** |
| **共有する値ではない** | 指標の記録であって、利用者の資金繰りではない（ADR-0013） |
| **`teardown` が消さない** | 種を蒔くと、流すたびに本番の指標へ行が積まれる |

**種も蒔かない。** 測れないうえに本番の数字を汚す。

### 5. 拒否の理由を見分ける

`settings` と `overrides` は所有者の行が既に在るので、客の insert は
**権限ではなく重複（23505）で落ちうる。** そのとき条項は「正しい実装でも
壊れた実装でも同じ結果」になる ―― §2.11 の4つ目の形である。
`deniedByPermission` が 23505 を拒否と数えない。

## 却下した選択肢

### `verify-rls.mjs` を広げる

退けた。あれは**毎回ランダムなアドレスで使い捨てのアカウントを作る。**
削除には secret キーが要るので**消せず、検証のたびに増える**（自分で
そう書いてある）。共有の検査は何度も流すものなので、**増え続ける形には
しない。** 固定の負荷試験アカウント2つを使い回す。

### 48通りをそのまま48件にする

退けた。「客が `grants` を書けない」は**表ごとの条項ではない** ――
どの表に編集を持っていても、`grants` への insert は同じ1つの判定に当たる。
8件に割ると、**同じ検査を8回書くことになる**（§2.8）。1件にして、
なぜ1件なのかを書く。

## 影響

- `pnpm loadtest:sharing` を足した。`pnpm loadtest:account2` と
  `pnpm loadtest:teardown2` も
- **まだ流せていない** ―― 2つ目のアカウントがメール確認待ち（下記）
- `grants` の表も8表のポリシーも**書いていない。** 仕様（FR・AC）を
  受け取ってから

## 踏んだところ：メール確認は OFF ではなかった

2つ目のアカウントを作るとき、`signUp` は通ったが
`signInWithPassword` が `email_not_confirmed` で止まった。

```
auth.email.enable_confirmations   local false / remote **true**
auth.email.max_frequency          local 1s    / remote 1m0s
```

`supabase config diff --remote` で確かめた。**本番では確認が有効である。**

**作り直しを繰り返さない。** `signUp` は1回ごとに実際にメールを送り、
送信の枠を減らす（`max_frequency` が1分、既定の上限は30通／時）。
**測ることが対象を消費するなら、測らない**（§2.11）。1回で止めてある。
