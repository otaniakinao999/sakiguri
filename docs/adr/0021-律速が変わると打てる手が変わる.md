# 0021 律速が変わると打てる手が変わる

## 文脈

実績10万件の負荷試験で AC-28b（読み込み完了 3秒以内）が不合格になった。原因を絞り込む過程で、**律速の見立てが3回変わり、そのたびに検討していた対策が丸ごと入れ替わった。**

| 時点 | 律速の見立て | 出ていた対策 |
|---|---|---|
| 1 | 往復100回が直列 | 範囲リクエストの並列化 |
| 2 | 20MB を10万オブジェクトにするパース | **並列化は無意味。20秒が床** |
| 3 | 本文の転送 | **列を絞る／圧縮**（1・2のときは出ていなかった） |

見立て2から3への転換が典型だった。「パースが支配」だと思っているあいだ、`select("*")` で `user_id`・`created_at`・`updated_at` を運んでいることは**誰も問題として認識していなかった**。パースが律速なら、列を減らしてもオブジェクトの数は変わらないので効かないからである。転送が律速だと分かった瞬間に、同じ事実が対策になった。

見立て1と2は、どちらも**測らずに割り算で出した推定**だった。

- 1→2：「1回で47.7秒、3回で24.4秒。24.4 < 47.7 なので並行していたはず」
- 2→3：「101往復 × 中央値104ms = 10.5秒。28.7秒との差18秒はパース」

1は、resource timing のバッファが満杯になると**新しい方を捨てる**（古い方が残る）ことを知らずに、24.4秒を完了時刻として扱っていた。2は、`await fetch()` が**ヘッダ受信で解決する**ことを見落とし、中央値に本文もパースも含まれていると読んでいた。

どちらも、測れば分かることだった。実際に測ると、10万件のパースは **73ms**、読み込み後のメインスレッド作業は全部足して **0.2秒**で、18秒の説明にならなかった。

## 判断

**性能の対策を決める前に、律速を測って特定する。分解を割り算で出して、そのまま対策の根拠にしない。**

具体的に3つ。

1. **区間を分けて測る。** 1往復を「ヘッダ受信 / 本文受信 / `JSON.parse`」に分ける。合計だけでは、どれが支配的かが決まらない。
2. **外から見えない区間はローカルで再現する。** ブラウザから取れるのは通信までで、`JSON.parse` から先は resource timing に出ない。同じ機械で再現して桁を出す（`pnpm bench`）。実機と再現を混ぜて書かない。
3. **測定器の挙動を先に確かめる。** resource timing のバッファは250件で、満杯になると新しい方を捨てる。上限に当たった測定の「最後の完了」は完了時刻ではなく下限値になる。

**律速が変わったら、対策の一覧を作り直す。** 前の見立てで却下した案を、新しい見立てのもとで一度見直す。上の表の3行目は、1行目・2行目のときには検討すらされていなかった。

## 理由

性能の推定は、当たっているように見える形で外れる。24.4 < 47.7 も、104ms × 101 も、算数としては正しい。**前提（どの時刻か、何を含む時間か）だけが間違っていて、計算の途中では気づけない。**

そして推定が外れると、**外れた推定に合う対策だけが議題に残る。** 「パースが床」という見立ては並列化と索引を無意味にするので、その2つを保留する判断まで連れてくる。見立てが違えば判断も違う。誤差ではなく方向が変わる。

測るコストは低い。区間を分けるのはスニペットの数行、ローカル再現は `pnpm bench` 一発である。**推定で議論した時間のほうが、測る時間より長かった。**

## 却下した選択肢

**推定を出さずに測る。** 却下。測ってから原因を考えると後付けの説明になり、外れたことが記録に残らない。**推定は先に書く。ただし対策の根拠にはしない。** 外れた推定は情報である（実際、上の2回の外れが「測ってから分解する」という本ADRを生んだ）。

**プロファイラを常時入れる。** 却下。本番コードに計測を足すと、測っているものが本番と違うものになる。外から取れるもの（resource timing）と、同じ機械での再現（`pnpm bench`）に分ける。

## 影響

- `supabase/loadtest/measure-console.js` — 1往復を3区間に分け、`Content-Encoding` と実効スループットを出す
- `supabase/loadtest/parse-bench.test.ts`（`pnpm bench`） — パース以降をローカル再現する。通常のテストには混ぜない
- `src/lib/supabase/rows.ts` — `SELECT_COLUMNS`。見立て3で初めて出てきた対策
- `docs/受入基準の充足状況.md` — 実機と再現を分けて記録する
