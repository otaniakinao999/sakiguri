# ADR-0034 取込は判定を完璧にせず、残高で検算する

日付：2026-11-12 ／ 対応：FR-61・AC-68 ／ 関連：FR-50・AC-64・AC-65・制約10

## 文脈

利用者から「取込済みの明細が『登録済み』にならないことがある。CSVを数回
試したら**登録済みの数が毎回変わった**」という報告があった。

原因を1つに絞れると考えて調べたが、**内容の突き合わせは原理的に完全にできない**
ことが実データで分かった。2026年10月の銀行明細232行のうち、口座・日付・収支・
金額・摘要が**完全に重なる行が18行（6組）**実在する。

```
×4  2026/10/30  振込手数料        77円
×4  2026/10/23  ＡＴＭ手数料     165円
×4  2026/10/20  振込手数料        77円
×2  2026/10/23  ＡＴＭ　セブン銀行  200,000円
×2  2026/10/20  ＡＴＭ　ローソン    200,000円
×2  2026/10/20  振込＊カ）ラボル    200,000円
```

`duplicateKeyOf`（FR-50）の鍵に足せる項目はもう無い。4件のうち3件が登録済みで
あれば、次に読んだとき残るのは1件で、**それが正しい1件かどうかは判定では決め
られない。** 摘要の原文で判定しても（AC-64）、取込先の口座を覚えても（AC-67）、
この組は割れない。

一方、同じ明細には**残高の列**がある。これは取引の列挙とは独立に「この時点で
いくらだったか」を言っている。実データで残高の鎖は10月231/231・11月74/74で
繋がっていた。

## 判断

**判定を完璧にするのをやめ、結果を検算する。**

取込の確認画面で、CSVの残高の列と「取込後にその口座に在ることになる実績」を
突き合わせ、**一致しなければその差額を出す。** 残高の列が無いCSVでは出さない。

比べるのは**明細の中だけで完結する2つの値**である。

| | |
|---|---|
| CSVが言う期末残高 | 末尾行の残高 |
| こちらが記録する期末残高 | 先頭行の残高 − 先頭行の増減 ＋ Σ（範囲内の実績の増減） |

計算は `src/core/balance-check.ts`（純関数）、文は
`src/lib/balance-check-message.ts`。

## 理由

**判定が外しても、取り落としと二重計上がその場で分かる。** 「登録済み」が1件
多すぎた／少なすぎた、はどちらも額として現れる。利用者が次にすることが
「どの行を戻すか」になり、**判定の正しさを信じる必要がなくなる。**

**アプリ側の残高を持ち出さない。** 基準日残高（`account.balance`）から足し
上げた値と比べると、ずれたときに「取込が落ちた」のか「基準日残高が違う」のかが
分からない。さらに、同じ「残高」が画面の2箇所から別の計算で出ることになる
（CLAUDE.md §2.12）。期首を明細の中から採れば、測っているのは**「この明細に
書かれた増減を、こちらが全部ちょうど1回ずつ記録できたか」**だけになる。

**符号から原因を言わない。** `recorded − expected` が負になるのは「入金の行を
取り落とした」ときと「出金の行を二重に入れた」ときの**両方**である。原因を
決めつけると、利用者は無い行を探すことになる。文は向きだけを言う。

**残高の向きは `accountDelta` から引く**（§2.8）。閉じない振替（振替先が未設定・
振替先がカード）は `accountDelta` が0にするので、ここでも差として現れる。
**出すのが正しい** ―― 明細は動いたと言っていて、こちらの残高は動いていない
のだから、残高は本当にずれている。

## 却下した選択肢

**取込期間の指定だけにする**（会計ソフトにある形。OI-24）。期間で絞れば重複は
減るが、**保留から確定へ変わった明細や、後から遡って増えた明細を取り落とす。**
検算が入れば「期間」は絞り込みであって判定ではなくなるので、要るかどうかは
利用者の取込を見てから決める（OI-24 を残した）。

**鍵に項目を足す。** 足せる項目がもう無い（上の18行）。

**残高を実績に保存する。** 残高は口座の属性であって1件の取引の属性ではない。
保存すると同じ残高が2箇所から出る（§2.12）。`ImportRow` に持たせて、登録の
ときに捨てる。

**見出しの無いCSVでも残高の列を推定する。** 数として見ると金額の列と区別が
付かず、取り違えると検算が意味のない額を出す。**見出しからしか拾わない**
（見出しの無いCSVでは検算しない）。利用者は確認画面で選べる。

**鎖が繋がらないときも差額を出す。** 繋がっていない残高から引いた差は、取込の
良し悪しを表していない。`broken` として「検算できません」と出す。

## 影響

- `ColumnMapping` と `ImportRow` に `balance` が増える
- 確認画面の「3. 列の割り当て」に［残高の列］が増える
- 確認画面の「4. 内容を確かめて一括登録」に検算の知らせが出る。**取込の
  チェックを変えるたびに出し直す**ので、どの行を戻せばよいかが分かる
- 登録後の知らせにも同じ文が入る（`reset()` で確認画面が消えるため）
- 取込行から実績への変換（`actualFromImportRow`）と、検算の入力の組み立て
  （`checkImportBalance`）が1箇所になった。**写し取ると、画面に出した検算の額と
  実際に登録される額が食い違い、登録するまで誰も気づけない**（§2.8）
- `dev/screens/import-wired` のCSVに残高の列と1行を足した。**足さないとこの
  画面は検算を一度も出せない**（§2.11）。既定が「二重に入っている」状態で、
  その行のチェックを外すと一致する ―― 1クリックで両方を見られる
