# ADR-0036 重複判定を摘要の原文で行い、似た行は出すだけにする

日付：2026-11-12 ／ 対応：FR-58・AC-64・AC-65 ／ 関連：FR-50・FR-59・FR-61

## 文脈

重複判定（FR-50）の鍵は `name` を含んでいた。`name` は**表示名**である。

```ts
duplicateKeyOf({ accountId, date, type, amount, name })
```

実績編集で摘要を直すと、保存されている名前がCSVの摘要と変わり、**その行は
二度と「登録済み」にならない。** 仕分けルールで摘要を置き換えられるようにすると
（FR-59）、ルールを作った行が全部そうなる。利用者の「登録済みの数が毎回変わる」の
一因である。

もう1つ、逆向きの問題がある。**銀行やカードの明細は、保留から確定になるときに
摘要が変わる。** 摘要を鍵に入れていると、確定後の行を取り落とす。摘要を鍵から
外すと、同じ日・同じ額の別の取引を外してしまう。

## 判断

**2つを分ける。**

1. **判定は「取込時の摘要の原文」で行う**（FR-58・AC-64）。実績に
   `source_name` を持たせ、表示名とは別にする。**原文を持たない実績は表示名を
   原文として扱う**（手入力と、0009 より前のデータ）
2. **口座・日付・収支・金額が一致して摘要だけ違う行は「似た行があります」と
   出し、取込のチェックは外さない**（AC-65）。**外すのは原文まで一致した
   ときだけ**

## 理由

**外すのは取り落としで、出すだけなら利用者が判断できる。** 外して間違えると
取引が静かに落ちる（残高が合わなくなるまで誰も気づかない）。出して間違えても、
利用者は画面で見て無視できる。**非対称なので、出す側に倒す。**

**原文はどの機構も書き換えない。** 表示名を変えるのは実績編集・仕分けルール
（FR-59）・別の明細からの差し替え（FR-62）の3つあるが、原文はCSVから読んだ
ままである。書き換えたら、次に同じ明細を読んだときに当たらなくなる。

**原文を持たない実績は表示名を原文として扱う。** 既存データを壊さない。摘要を
直していない限り、今までと同じ判定になる。**直してあった行は当たらないが、
AC-65 が「似た行があります」として出すので黙って消えない。**

**原文まで一致した行に先に枠を使わせる（2段階）。** 1行ずつ決めると、先に来た行が
「似た行」の枠を取ってしまう。保存済みが摘要 B の1件、CSVが A・B の2行という
場合、

| | 結果 |
|---|---|
| 1行ずつ | `[似た行, 登録済み]` |
| 2段階 | `[なし, 登録済み]` |

**正しいのは後者。** 保存済みの1件は B そのものであって、A に対応する実績は
無い。**在りもしない相手について「似た行があります」と出すと、利用者はその
警告を見なくなる。**

**それでも鍵は完全ではない。** 口座・日付・収支・金額・摘要が完全に重なる行は
実在する（2026年10月の実データで18行）。だから**結果を残高で検算する**
（FR-61・ADR-0034）。この2つは**別の手当てであって、代わりではない。**

## 却下した選択肢

**摘要を鍵から外す。** 同じ日に同じ額の取引が2件あるのは普通のことで、摘要を
見ずに外すと本物のデータが消える。

**似た行を外して（登録済みと同じ扱いに）、利用者に入れ直させる。** 外した行は
画面で控えめに出るので、入れ直すべき行に気づけない。取り落としになる。

**原文を別テーブルに持つ。** 実績1件に1つしか無い値なので列で足りる。

**マイグレーション未適用でも動くようにする**（0008 でやった形）。読み込み側は
`source_name` を明示的に取りに行くので、列が無ければ 42703 で `loadAppData` の
`Promise.all` が落ち、**全員が画面を開けない。** 取る列を実行時に変えれば逃げ
られるが、**列の過不足を型で止めている `columns<Row>()` の守りが外れる**
（§2.8）。そこで §2.5.1 のもう一方 ――「**適用が済むまで push しない**」―― を
選んだ。

## 影響

- `actuals.source_name` が増える（0009）。**適用してからデプロイする**
- `Actual.sourceName`、`ImportRow.sourceName` が増える
- `ImportRow.alreadyRegistered`（真偽値）が `duplicate`（3状態）になった。
  **真偽値のままだと「似た行」を表せない**
- 確認画面の重複列が3つの状態を書き分ける。「登録済み」は控えめな色（こちらで
  外したという知らせで、利用者がすることは無い）、「似た行があります」は
  warning（外していないので、利用者が判断する必要がある）
- `dev/screens/import-wired` に3つの状態が全部出るようになった ―― 2行目が
  登録済み、4行目が似た行、残りは空

## 測ったこと

`core/__tests__/csv-source-name.test.ts`（14件）、`csv-duplicate.test.ts`（更新）、
`lib/__tests__/supabase-rows.test.ts`（6件・新設）。

**往復は「摘要を直した行」を混ぜて測る。** 直していない行だけだと、表示名で
判定していても全行が「登録済み」になって通る（利用者の指示どおり）。
**一致の厳しさは3状態を同じ表で測る** ―― 2状態だと、全部を似た行にする実装とも
摘要を見ない実装とも区別が付かない。

壊して測った10通り。

| 壊し方 | 落ちた |
|---|---|
| 原文を見ず表示名で判定 | 4 |
| 原文を実績に保存しない | 3 |
| 原文を取込行に入れない | 3 |
| 似た行も外す | 18 |
| 似た行を出さない（2状態に戻す） | 4 |
| 1行ずつ決める（枠の取り合い） | 1 |
| 件数で数えず「鍵があるか」で見る | 4 |
| 原文を DB に書かない | 3 |
| 原文を DB から読まない | 2 |
| 取る列から原文を外す | **vitest では割れない。`pnpm typecheck` が落ちる** |

**最後の1つは最初 vitest で割れなかった。** `columns<Row>()` が型で止めている
ので、落ちるのは `tsc` である（§2.8 の意図どおり）。**DB の往復（上の2通り）は
本当にどのテストも割らなかった**ので、`supabase-rows.test.ts` を足した ――
原文を保存しない／読まないと FR-58 が丸ごと効かないのに、画面は普通に動くので
次の取込まで誰も気づけない。
