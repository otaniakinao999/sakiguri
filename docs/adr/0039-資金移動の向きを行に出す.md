# ADR-0039 資金移動の向きを行に出す

日付：2026-11-12 ／ 対応：FR-63・AC-70 ／ 関連：制約11・AC-58b・AC-58d

## 文脈

**利用者の現金残高が出納帳と 46,000円 ずれた。** 原因は1行だった。

```
2026-10-23「ＡＴＭ　ローソン」23,000円   銀行 → 現金 として入っていた
                                        実際は 現金 → 銀行 の預け入れ
```

**向きが逆だと差は額の2倍**になるので、ちょうど 46,000円 である。同じ期間の
資金移動18件のうち**17件は本当に銀行→現金の引出し**で、**この1件だけが
預け入れ**だった。名前も同じ「ＡＴＭ　…」で並んでいる。

**取込は `transfer` を作らない**（`csv.ts` が符号から income / expense を
決めるだけ）。つまりこの行は手で振替にしたもので、**他と同じ向きにして
しまった**ものである。

利用者の言葉がそれを言っている。

> SAKIGURIでは資金移動に符号が表示されないので、この2件が計算上マイナスに
> なっているのか、こちらからは判断できませんでした。

**符号が出ていないのは正しい。** 合計の範囲では振替は閉じて残高を動かさない
ので、`viewDelta` が0を返し `amountView` が符号を落とす（AC-58b）。
**正しい挙動のせいで、間違った行が見つけられなかった。**

## 判断

**`type = transfer` の行に「移動元 → 移動先」を出す。**

出す場所は4つ ―― 入出金予定表・実績一覧・やること・ダッシュボードの要対応。
**行が出るところには必ず出す**（§2.12。利用者が見ていたのは、こちらが最初に
直そうとした画面ではなかった）。

**両側記録の行（`type` が income / expense で費目が TRF）には出さない。**

## 理由

**符号では足りない。** 口座を絞れば符号は出る（AC-58b は正しく働いている）が、
**利用者が見ていたのは合計の側**である。実績一覧には口座の絞り込みが無いので、
あの画面では**どの範囲を選んでも符号が付かない。**

| | 符号 | 向き |
|---|---|---|
| 入出金予定表（口座を絞る） | 付く | 出る |
| 入出金予定表（合計） | **付かない** | 出る |
| 実績一覧・やること・要対応 | **付かない** | 出る |

**両側記録の行に出さないのは、相手が分からないからである。** あの行は
`toAccountId` を持たない（適用規則5a）。そのうえ**口座を1つしか動かさない
ので、合計の範囲でも符号が付く** ―― AC-70 が埋めるのは「符号が付かないのに
向きも読めない」穴だけで、そこは `transfer` に限られる。片側だけを
「現金 → ？」と出すと、**分かっていない相手を分かっているように見せる。**

したがって**向きが出る行と出ない行は同じ一覧に混ざる。** これは条項に
書いた（AC-70）。

**`toAccountId` を読んでよいかの判定を1箇所にした**（`transferEnds`。§2.8）。
読む側は `touchesAccount`（一覧の絞り込みと口座削除）と
`formatTransferDirection`（向き）の2つで、**2026-11-11 の欠陥はこの規則の
読み手が2つあって一方だけ直っていたことだった**（収入の行が振替先の口座の
一覧に出た件）。条項が値の名前を挙げていても、読む経路の全部を測ったことには
ならない（CLAUDE.md §2.11）。残高（`accountDelta`）は `type = transfer` の
分岐の中でしか振替先を見ないので、同じ規則が別の形で1度だけ現れる。

**備考の列には入れない。** 備考は1行に1つしか出せず、繰延・未入力・
反映していない振替が先に取る（`noteOf` の優先順位）。**向きは落ちては
いけない。** 内容の下に添える。

## 却下した選択肢

**符号を必ず付ける。** 合計の範囲で振替に符号を付けると、**残高の列と
食い違う** ―― 「−23,000」と書いてあるのに残高が動かない行ができる。
AC-58b がそれを禁じている（符号は残高の動きから引く）。

**口座を絞ったときだけ向きを出す。** 絞っていないときに出ないなら、
利用者が見ていた画面では何も変わらない。

**実績一覧に口座の絞り込みを足して符号で読ませる。** 絞り込みは既にあるが
（FR-42）、**符号は「いま見ている範囲での向き」であって行の属性ではない。**
範囲を変えるたびに符号が変わるものを、取引の向きの手がかりにはできない。

**片側記録の行にも半分だけ向きを出す**（「現金 → ？」）。相手が分からない
ことを出すだけで、**符号で既に読める**行に重ねることになる。

## 影響

- `src/core/transfer-direction.ts` が増える（純関数）
- `touchesAccount` が `transferEnds` を呼ぶようになる。**挙動は変わらない**
  （同じ判定を1箇所から借りただけ）
- 3つのビューモデル（キャッシュフロー・ダッシュボード・実績入力）が
  **口座の一覧を受け取るようになる。** 必須の項目にしたので、渡し忘れた
  呼び出しは `tsc` が落とす
- `TodoRow` に `detail` が増える。行が2行になるので、**資金移動の行だけ
  高さが変わる**（1440px で 39px → 57px）
- 試験データに `type = transfer` の実績2件と単発予定1件を足した。
  **足すまで0件だった** ―― 行が0件の条項はどんな実装でも通る（§2.11）

## 測ったこと

`core/__tests__/transfer-direction.test.ts`（11件）、
`lib/__tests__/transfer-direction-screens.test.ts`（9件）、
`lib/__tests__/transfer-direction-rendered.test.ts`（4件・jsdom）。

**ビューモデルと画面を分けて測っている。** 行が向きを持っていることと、
向きが画面に出ていることは別の確認である（§2.7 の末尾）。`detail={...}` を
1つ落としてもビューモデルの検査は通る。

**同じ実行で、向きが出る行と出ない行の両方を数える。** 片側だけだと、
「全部に向きを出す実装」とも「どれにも出さない実装」とも区別が付かない。
**符号についても同じ** ―― 絞ったときに符号が付くことと、合計のときに
付かないことを対にして測る（AC-70 の条項）。

壊して測った15通り。**全部割れた。**

| 壊し方 | 落ちた |
|---|---|
| すべての行に向きを出す | 12 |
| 向きを出さない | 15 |
| 移動元と移動先を入れ替える | 12 |
| 振替先が未設定なら向きを出さない | 2 |
| 実績一覧だけ向きを落とす（ビューモデル） | 1 |
| ダッシュボードだけ向きを落とす | 1 |
| 入出金予定表だけ向きを落とす | 4 |
| やることだけ向きを落とす | 2 |
| `touchesAccount` が gate を借りるのをやめる | 5 |
| **試験データから `transfer` の2件を外す** | **5** |
| 実績一覧の画面で `detail` を渡さない | 1 |
| やることの画面で `detail` を渡さない | 1 |
| ダッシュボードの画面で `detail` を渡さない | 1 |
| 入出金予定表の表に向きの行を描かない | 1 |
| `TodoRow` が `detail` を描かない | 3 |

**試験データを外す行も測ってある。** 2件が消えても落ちないなら、
データが載っていないのと同じである。

実機（`/dev/screens/*` の4画面、1440px）で、逆向きの2件が向きで見分けられる
ことと、両側記録の2件には出ないことを確認した。

## 残した開示

**既に入っている逆向きの行は、これでは直らない。** 画面から読めるように
なるだけである。実データの1行（2026-10-23「ＡＴＭ　ローソン」23,000円）は
利用者が実績編集から振替元・振替先を入れ替える。

**取込は向きを作らない。** CSVの符号から income / expense を決めるだけで、
`transfer` にするのは手の操作である（`csv.ts`）。したがって**入力の時点で
向きを間違える経路は残っている。** 画面に出るようになったので、入力直後と
突き合わせのときに気づける ―― それが今回の変更の全部である。
