# ADR-0041 未記録の予定の境界を1箇所に置き、今日を別の組にする

日付：2026-11-13
関連：AC-72・AC-73・AC-49b・AC-49d、CL-3、CLAUDE.md §2.8・§2.9・§2.12

## 文脈

利用者からの報告2件。どちらもダッシュボードの同じ箇所である。

1. 「うち未記録の予定」の合計には**今日付の予定（計17,058円）が入っている**が、
   「やること」には出てこないため、**飛んだ先で金額が合わない。**
2. 注記「うち未記録の予定 −223,243円は、**上の残高どちらにも含まれています**」は、
   実際には**予定に設定した口座の残高にだけ**同額が入っている。

同じものを3つの場所が別々に絞っていた。

| | 絞り方 | 今日 |
|---|---|---|
| 金額 | `todayRow.proj − todayRow.act` | 含む |
| 件数 | `cashDateOf(plan) <= today` | 含む |
| 一覧 | `plan.date < today` | **含まない** |

`docs/受入基準の充足状況.md` は 2026-10 の時点で既にこの食い違いを書いていた
――「違うのは (a) 本日ちょうどの予定、(b) カード払いの予定の2点だけ」。
**(a) を「ほぼ同じ値になる」と読んで放置していた。** 実機では一致して見えた
（その日に予定が無ければ一致する）。

## 判断

### 1. 境界は1箇所に置く

`isUnrecordedOn(date, today)` を `lib/unrecorded.ts` に置き、一覧も件数も
ここから引く。**今日は未記録に入る。**

**日付の基準は呼び出し側が渡す。** 金額と件数は現金が動く日
（`cashDateOf`）、一覧は発生日（`plan.date`）。**基準の違いは残し、境界の
違いだけを消した。**

### 2. 今日の予定は別の組にして、注記を分ける

一覧を「今日の予定」と「期日を過ぎた予定」に分ける。注記は組ごとに置く。

| 組 | 注記 |
|---|---|
| 今日の予定 | 今日の残高には予定額のまま入っています。実績が分かったら消し込んでください。 |
| 期日を過ぎた予定 | 予定額のまま予測に残っています。実績を入れて消し込むか、支払日をずらしてください。…… |

空の組は見出しも注記も出さない。

### 3. 注記は口座の数に依存しない言い方にする

「その予定に設定した口座の残高と、現預金 合計に含まれています」。
**「現預金 合計」の行を出していないときは、その語を使わない。**

## 理由

**金額から一覧へ飛べるようにしたのはこちらである**（要望8）。飛べるように
した時点で、**一覧は金額の内訳として読まれる。** 片方だけに今日が入って
いると、利用者は「どちらが正しいのか」を判断できない（§2.12）。

金額の側は動かせない。`予測系列 − 実績系列`（AC-49b）であり、**今日の予定は
今日の残高に既に効いている。** 金額から外すと残高と一致しなくなり、
グラフのツールチップ（AC-49c）とも割れる。**直すのは一覧の側しかない。**

ただし**今日の予定は「遅れている」ものではない。** 同じ注記を当てると
「支払日をずらしてください」が今日の予定にも掛かる。一覧から外せない
（残高に入っている）が、同じ扱いにもできない。**組を分けるのがこの2つを
同時に満たす唯一の形だった。**

## 却下した選択肢

### 一覧を現金が動く日で絞る（件数と完全に揃える）

AC-72 の「一覧の合計が金額と一致する」を**完全に**満たせる。退けた。

**引落が未来のカード利用が一覧から消える。** それは利用者が消し込む対象
そのものである。要件定義書 §3.3 と AC-49d が「一覧の件数は**発生日**で
数える（利用者が一覧で見て消し込む対象がそれだからである）」と定めていて、
**この変更はその条項を破る。**

### 今日の予定を一覧に出さず、金額からも外す

AC-49b を破る。残高（予測系列）と注記が割れる。

### 注記に口座名を並べる（「現金と○○銀行の残高に含まれています」）

口座が増えると文が伸びる。**口座の数に依存する言い方を直す**のが目的なので、
数に依存しない言い方を選んだ。

## 影響

### 残っている食い違い（**2026-11-13 に決着。AC-72b**）

**一覧の合計と注記の金額は一致しない。**

一覧は発生日、金額は現金が動く日で見ている。§3.3 は
「発生日は過ぎたが引落日が未来のカード利用は、件数には入るが金額には
入らない。**これは仕様である**」と明記している。

フィクスチャでの実測：

```
一覧の合計   −¥120,100
注記の金額   −¥108,100
差            ¥12,000   ← 10/08 のサブスク（引落 11/10）そのもの
```

**AC-72（v1.51）の「一致すること」と §3.3 が衝突していた。** 条項の側が
誤っていたので、**v1.52 で AC-72b に分けた**（一致は求めない）。

**採ったのは2と3の両方である。**

| | |
|---|---|
| 1. 一覧を現金日に倒す | **却下。** 引落が未来のカード利用が一覧から消える。それは消し込む対象そのもの |
| 2. 引落が未来の行に「引落 11/10」を添える | **採用。** どの行が差の原因かが分かる |
| 3. 注記に含まれていない額を添える | **採用。** 足し算が合わない理由がその場で読める |

**どちらか一方では足りない。** 2だけでは「合計が合わない」こと自体が
言われておらず、3だけでは原因の行を探せない。利用者の報告は「飛んだ先と
金額が合いませんでした」で、**起きたのは足し算が合わないこと**だから、
その場で理由が読めて、かつ原因の行まで辿れる必要がある。

**差の額は検査で固定している。** 「合っている」ことにも「無視してよい」
ことにもせず、**画面に出す額が実際の差と同じであること**まで測る
（`sum − awaiting === amount`） ―― 説明の文に別の計算を通すと、
**合わない理由として合わない額**が出る。

### 試験データ

**今日付の予定が0件だった。** そのデータでは境界が `<` でも `<=` でも結果が
同じで、**今日を外している実装でも AC-72 が通る**（§2.11 の3つ目の形 ――
対象の行が0件のとき、その条項は必ず通る）。フィクスチャに1件足した
（`dashboard-fixture.ts` の o3「電気代」10/18）。**この退化そのものを検査に
している** ―― 今日と前日でモデルを2つ作り、件数と金額が動くことを先に測る。

### 画面

ダッシュボードのやること（SC-02）だけ。**入出金予定表と実績一覧は触っていない**
（あちらは期間で絞っていて、未記録の集合を出す画面ではない）。
`DashboardTodo.isToday` は省略可にしてある ―― 渡さなければ従来の見え方
（期日を過ぎた扱い）になるので、`/dev/screens/dashboard` の固定値は壊れない。
