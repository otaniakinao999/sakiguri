# ADR-0040 口座ごとの日別を出し、増減と残高を別々に作る

日付：2026-11-12 ／ 対応：FR-64・AC-71 ／ 関連：制約11・AC-68・AC-49a

## 文脈

**利用者の現金残高が出納帳と 46,000円 ずれたとき、どの日でずれたのかを
画面から辿る手段が無かった。**

| 画面 | 答えられること |
|---|---|
| 残高推移のグラフ | 合計の推移。**口座別にはできるが日ごとの増減は出ない** |
| 月次資金繰り表 | 月の入金・出金・月末残高。**月単位** |
| 入出金予定表 | 行ごとの残高。**口座を選んでも行は絞られない**（下の開示） |

原因の1行は 2026-10-23 の振替だったが、**それを見つけたのは本番の
`actuals` を読んで計算し直したから**で、画面からではない。

## 判断

**口座を1つ選ぶと、日ごとの増減と残高が出る表を置く。**

**増減は行から足し、残高は系列（`byAccount`）から取る。** そのうえで
**「増減の合計 ＝ 期末残高 − 期首残高」を画面に出す**（AC-71）。

## 理由

**残高の差から増減を引くと、条項が空振りする。**

```
delta[i] = balance[i] − balance[i−1]
```

この形だと合計は**必ず**「期末 − 期首」になる。差し引きが望遠鏡のように
畳まれるからで、**どんな実装でも通る**（CLAUDE.md §2.11 の4つ目の形：
正しい実装と壊した実装が同じ結果になる）。別々に作るから、
**行を二重に数えたときと落としたときに割れる。**

これは AC-68（取込の残高検算）と同じ考え方である ―― **判定を完璧にする
のではなく、独立した2つの値を突き合わせる。**

**予測系列から作る**（AC-49a）。実績系列で作ると、同じ日について画面に
2つの残高が出る（§2.12）。ただし**出納帳には予定の行が無い**ので、
未記録の予定がある日から先は食い違う。**その理由が読めるように、件数に
「予定◯件」を併記する。**

**増減が0の日も行として出す。** 残高に反映しない振替（振替先が未設定・
カード）は明細に在るのに残高を動かさない（`oneSidedReason`）。件数が
無いと「この日は何も無い」と読まれ、**出納帳との差の原因が1つ見えなく
なる。**

**明細の絞り込み（種別・状態）に従わせない。** 絞ると増減の合計が残高の
動きと合わなくなり、**留め具が毎回鳴る** ―― 鳴りっぱなしの警告は読まれ
なくなる。

**合っているときも式を出す。** 出ないものだけを見ると、正しく黙って
いるのか、こちらが違う場所を見ているのかを区別できない（§2.11）。

## 却下した選択肢

**期間のすべての日を行にする。** 「1日ずつ」の求めには素直だが、2ヶ月で
60行のうち50行が増減0になる。**動いた日が埋もれる。** 期首と期末を別に
出しているので、間の動かない日は残高が変わらないことが読める。

**行（取引）ごとに出す。** 入出金予定表が既にそれで、行ごとの残高も
持っている。**日ごとにするのは出納帳の形に合わせるため** ―― 出納帳は
日付で締める。

**合計（現預金すべて）でも出す。** 出納帳は口座ごとに付けるものなので、
2口座を足した「日ごとの残高」は突き合わせの相手がいない。**口座を選ぶ
よう案内する。**

**ずれを黙って合わせる**（`opening` を `closing − total` から作るなど）。
**ずれていることが分からなくなる。** 合わせるのではなく出す。

## 影響

- `src/core/account-daily.ts` が増える（純関数）
- キャッシュフローにパネルが1枚増える。**口座を選んでいるときだけ表が出る**
- ビューモデルが**選んでいる口座の id** を受け取るようになる（`scope` の
  集合とは別。日別は1口座ぶんしか出さない）

## 測ったこと

`core/__tests__/account-daily.test.ts`（11件）、
`cashflow/__tests__/account-daily-screen.test.ts`（7件・jsdom）。

**試験データを退化させない。** 現金に**入る日（+50,000）と出る日
（−23,000）の両方**を入れ、相殺して0にならないようにした（+27,000）。
0件の口座で測ると、増減も合計も0でどんな実装でも通る。

壊して測った16通り。**14通りで割れ、2つは割れなかった。**

| 壊し方 | 落ちた |
|---|---|
| **増減を残高の差から作る（退化した実装）** | **1** |
| 増減を金額から作る（符号を見ない） | 10 |
| 振替で入ってくる側を数えない | 7 |
| 同じ行を2回数える | 9 |
| その口座に関わらない行も数える | 3 |
| **期首残高を増減から作る** | **1** |
| 動きのない日も行にする | 4 |
| 件数を増減が0でない行だけにする | 1 |
| 画面へ `accountDaily` を渡さない | 4 |
| 合計のときも出す | 2 |
| `gap` を常に0にする | 1 |
| 日別の表を描かない | 4 |
| 期首残高の行を描かない | 1 |
| 合計の行を描かない | 1 |
| 留め具の文を画面に出さない | 1 |
| ずれていても黙る | 1 |

**退化した実装（残高の差から増減を作る）を落とすのは1件だけである。**
`gap` が常に0になるので、**正しいデータを通すかぎり結果が同じになる**
――その1件は、**系列の残高を1日ぶんずらした壊れた入力**を渡している。
この1件が無ければ、AC-71 は条項として空振りする。

**期間の外の行を数える**を壊しても割れなかった。調べたところ、
**行の組み立てが系列の行を回すので、範囲の外の日はそもそも読まれない**
―― 条件が二重で、外側の1つが死んでいた。**死んだ番人は外した**
（`detectColumns` で一度やった形。§2.11）。

**`Panel` に `hidden` を付ける**も割れなかったが、これは壊し方が悪い
（`Panel` は未知の props を DOM に渡さないので、**実装が変わっていない**）。
壊した箇所がその条項の見る値を本当に変えているかを確かめ、別の壊し方に
替えた。

実機（`/dev/screens/cashflow-wired`・1440px）で、現金を選んで
「期首残高 ¥52,000 ＋ 増減の合計 +¥27,000 ＝ 期末残高 ¥79,000」が出ること、
合計に戻すと案内に戻ることを確認した。

## 残した開示

**入出金予定表は、口座を選んでも行が絞られない。** 残高の列だけが
その口座のものになる。したがって現金を選ぶと、**銀行だけを動かす行が
残高を変えないまま並ぶ。** 日別の表を隣に置くと、この食い違いが目に
付きやすくなる。**この変更では直していない**（§4.2 の明細の定義に
関わるため）。

**日別は予定を含む。** 残高を予測系列から取る以上そうなる（AC-49a）。
出納帳と突き合わせるときは「予定◯件」の日から先が食い違う ―― 件数で
分かるようにしてあるが、**予定を除いた列は出していない。**
