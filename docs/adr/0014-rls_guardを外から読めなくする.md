# 0014. rls_guard を外から読めなくする

## 文脈

[0002_rls_guard.sql](../../supabase/migrations/0002_rls_guard.sql) で、RLS が無効またはポリシーの無いテーブルを列挙するビュー `public.rls_guard` を作った。CLAUDE.md §2.5 と PoC開発計画 §5.4 が求める「RLS の漏れを目視に頼らず検出する」ための仕組みである。

作ったあとで、このビュー自体が外から読めることに気づいた。実測すると次のようになる。

```
未サインイン（anon ロール）から
  rls_guard            HTTP 200  []
  存在しないビュー       HTTP 404  {"code":"PGRST205", ...}
```

`200 + []` は拒否ではない。**権限があり、クエリが成功し、該当が0件だった**という意味である。ビューは `security_invoker = true` なので anon の権限で `pg_class` / `pg_policy` を読みに行っており、それが通っている。

つまり **RLS を付け忘れたテーブルができた瞬間、未サインインの相手にそのテーブル名が返る。** 攻撃者にとっては、どこを叩けばよいかの下見になる。

いま0件なのは 0002 の適用時検査が効いているからであって、検知が破れたら漏れる構造になっている。

## 判断

`anon` と `authenticated` から `rls_guard` の権限を落とす。

```sql
revoke all on public.rls_guard from anon;
revoke all on public.rls_guard from authenticated;
```

点検はダッシュボードの SQL Editor から secret 権限で行う。

## 理由

**使わない権限は与えない。** アプリはこのビューを読まない（`src/` 配下の参照は0件）。読むのはマイグレーションの適用時検査（owner ロール）と検証スクリプトだけで、前者は revoke の対象外である。

**検知の仕組みが、検知したい事故の手がかりを漏らしていた。** 守るために作ったものが攻撃面を増やしていては本末転倒になる。

影響が小さいことも確かめた。壊れるのは `scripts/verify-rls.mjs` の1箇所だけで、そこは「読めないこと」を確認する形に書き換えてある。ロールバックは1行で済む。

## 却下した選択肢

**`rls_guard` を private スキーマに置き、PostgREST の公開対象から外す。** 構造としてはこちらが正しい。`revoke` は「公開されているものから権限を剥がす」対処であり、そもそも公開しない設計のほうが漏れにくい。

採らなかったのは、**起きていない問題のためにマイグレーションを増やすと手戻りになる**ため。`revoke` で実害は塞げており、確度が100%でない点（0002 を再適用したときに `create or replace view` で grant が戻らないか）は検証スクリプトが拾う。**実際に grant が戻ったら、そのときに private スキーマへ移す。**

**ビューを消して、点検を 0002 の適用時検査だけにする。** 適用のたびに検査が走るので最低限は担保できる。ただしマイグレーションを流さない限り気づけない。運用中に手で確かめる手段は残しておきたい。

**`security_definer` にして owner 権限で実行させる。** 逆効果。anon から読めるまま、権限だけが上がる。

## 影響

- `scripts/verify-rls.mjs` は「`rls_guard` が外から読めないこと」を検査する。読めるようになったら落ちる
- 点検は SQL Editor から。`select * from public.rls_guard;`
- アプリからこのビューを読むコードは書けない。書く予定もない
- 0002 を再適用したあとは、検証スクリプトを流して grant が戻っていないかを確かめること
