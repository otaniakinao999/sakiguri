# 0010. 家事按分の家計ぶんを残差で求める

## 文脈

要件定義書 CL-4 は3つのビューの計上額を表で定義している。

| 集計対象 | 計上額 |
|---|---|
| 合算ビュー | `amount` の全額 |
| 事業ビュー | `amount × bizRatio ÷ 100` |
| 家計ビュー | `amount × (100 − bizRatio) ÷ 100` |

金額は円単位の整数で持つため（[ADR-0001](0001-金額を円単位の整数で扱う.md)）、按分の結果は丸める必要がある。

表のとおり両側を独立に計算して丸めると、**事業ぶんと家計ぶんの合計が合算ビューと一致しないことがある。**

```
10,001円・事業割合50%
  事業 = round(10001 × 50 ÷ 100) = round(5000.5) = 5,001
  家計 = round(10001 × 50 ÷ 100) = round(5000.5) = 5,001
  合計 = 10,002  ≠  合算ビューの 10,001
```

年月別収支（SC-04）は同じデータを合算・事業・家計の3ビューで切り替えて見せる画面である。タブを切り替えると合計が1円変わる状態になる。

## 判断

事業ぶんは表のとおり `round(amount × bizRatio ÷ 100)` で求める。**家計ぶんは `amount − 事業ぶん` の残差で求める。**

```ts
businessShare  = (amount, r) => Math.round((amount * clamp(r)) / 100);
householdShare = (amount, r) => amount - businessShare(amount, r);
```

これにより `事業 + 家計 = 合算` が常に成り立つ。

## 理由

**画面上の破綻のほうが、式の字面より重い。** 1円のずれ自体は小さいが、それが「3つのビューで合計が違う」という形で現れると、利用者は数字全体を疑う。資金繰りサービスで最も失いたくないのは金額への信頼である。

事業側を式どおりに残したのは、**事業ぶんが対外的な意味を持つ数字**だからである。確定申告で経費として申告するのは事業ぶんであり（BS-6 申告準備、AC-05）、こちらが仕様の式から外れると説明が難しくなる。家計ぶんは差額であり、外部に出る数字ではない。

CLAUDE.md §2.1 は借入返済表について「最終回で残額を調整し、合計が元本と一致することをテストで保証する」と定めている。**同じ考え方をここにも当てている。** 端数は片側に寄せ、合計を守る。

## 却下した選択肢

**表のとおり両側を独立に丸める。** 仕様の字面には忠実。ただし上記の破綻が残る。丸め誤差が出るのは `amount × bizRatio` が 50 で終わるときだけなので発生頻度は低いが、低頻度で再現条件の分かりにくいずれは、見つかったときに原因究明が高くつく。

**家計ぶんを式どおりに求め、事業ぶんを残差にする。** 合計は守れる。ただし申告に使う事業ぶんが「引き算の余り」になる。金額の根拠を説明するとき、事業ぶんは自分の式を持っているほうがよい。

**丸めずに小数を保持し、表示時のみ丸める。** ADR-0001 で却下済み。累積誤差が出る。

**銀行家の丸め（round half to even）を使う。** 大量集計での偏りは減るが、合計が一致しない問題は解決しない。加えて `Math.round` と挙動が違うため、他の丸め箇所と規則が二本立てになる。

## 影響

- **要件定義書 CL-4 の表と実装が字面では一致しない。** `src/core/proration.ts` に理由をコメントで書き、テスト（`proration.test.ts`）で「独立に丸めると合わない例」を明示してある。表を読んで実装を「直す」ことがないようにするため
- `事業 + 家計 = 合算` を全事業割合（0〜100）で検査するテストを置いた。この不変条件を壊す変更はテストが落ちる
- CL-5 の集計は費目ごと・月ごとに按分後の値を足し上げる。丸めは各イベントで行うため、合計に対して丸めるのとは値が異なりうる。これは CLAUDE.md §2.1 の「計算の各段で丸める」に従った結果である
- 事業割合は 0〜100 に丸め込む。範囲外の値が入っても計算が破綻しない
