# 0018. マイグレーションを適用してからコードをデプロイする

## 文脈

CL-2 手順4 の修正（[[0017-カードの未払を確定分と未確定分に分ける]]）で、`accounts` に `unbilled_balance` 列を追加するマイグレーション 0005 を書いた。同じPRにコードを含め、**マイグレーションが未適用のまま main に push した。**

Vercel は main への push で自動デプロイする。結果として、本番に「`unbilled_balance` を書き込むコード」だけが載り、列が存在しない状態になった。カードの保存が 400 で失敗する。

コミットメッセージと報告には「マイグレーション 0005 の適用が必要です」と書いた。**書いたが、本番は直らなかった。** 注記は人間が読んで行動するまで何の効果も持たない。その間、機能は壊れている。

PoC の現時点では利用者が開発者本人しかいないため実害はなかった。モニター配布後に同じことをすれば、利用者に見える形で壊れる。

## 判断

**後方互換のあるマイグレーション（列の追加など）は、適用してからコードをデプロイする。**

**後方互換でないマイグレーション（列の削除・型変更・NOT NULL 化）は、「新旧どちらのコードでも動く状態」を経由する。** 追加 → コード切替 → 削除の3段階に分け、1つのPRにまとめない。

マイグレーションを含むPRの説明には、適用とデプロイのどちらを先に行うかを明記する。

適用が済むまで push しないか、未適用でも壊れないコードにするか、どちらかを選ぶ。**コミットメッセージへの注記は選択肢に含めない。**

CLAUDE.md §2.5.1 に規約として書いた。

## 理由

デプロイとマイグレーションは別の人間が別のタイミングで行う。いまの体制ではコードは自動で出て、マイグレーションは手で適用される。**自動のほうが必ず先に着く。** 順序を「先に適用」と決めておかないと、毎回このずれが起きる。

列の追加が後方互換なのは、**古いコードが新しい列を知らなくても動く**ためである。だから適用を先にしても壊れない。逆は壊れる。非対称なので、安全な向きに倒す。

列の削除が後方互換でないのは、古いコードがその列を読み書きするためである。3段階に分けるのは、どの瞬間を切り取っても「いま動いているコード」と「いまのスキーマ」が矛盾しない状態を保つためである。

注記を選択肢から外したのは、実際に効かなかったからである。今回は注記を書いたうえで本番が壊れた。同じ手段を「次は気をつける」で残すと、同じ結果になる。

## 却下した選択肢

**コードを列の有無に耐えるように書く。** 読み取り側は `?? 0` で吸収できるが、書き込み側は列が無ければ必ず失敗する。列の存在を実行時に判定して書き分けることは技術的には可能だが、スキーマの分岐がアプリ側に残り続ける。移行期間だけのつもりの分岐は消されない。

**マイグレーションをCIから自動適用する。** 順序の問題は解決するが、本番データベースへの自動適用は事故の影響が大きい。PoC の規模では手で適用して確認するほうが安全である。規模が大きくなったら再検討する。

**マイグレーションとコードを別のPRに分ける。** 分けても、適用の順序が保証されるわけではない。順序そのものを規約にするほうが本質的である。ただし後方互換でない変更では、3段階に分ける以上、PRも分かれる。

## 影響

- マイグレーションを含む作業は、適用を待つぶんリードタイムが伸びる
- 0005 は適用待ちのまま本番が壊れている。適用すれば直る
- 今回の順序違反は、作業を止めて確認すべき箇所を「注記を書いたから大丈夫」で通したことが原因である。注記では止まらない
