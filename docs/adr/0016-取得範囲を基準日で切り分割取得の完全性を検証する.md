# 0016. 取得範囲を基準日で切り、分割取得の完全性を検証する

## 文脈

`loadAppData` は6テーブルを `select("*")` で読んでいた。条件も順序も上限も指定していない。

```ts
supabase.from("actuals").select("*"),
```

PostgREST は1回の応答で返す行数に上限を持つ（Supabase の Max rows。既定 1000）。**この上限に当たっても、エラーにはならない。** 短い配列がそのまま返る。

その配列は `AppData.actuals` になり、CL-3 に渡る。CL-3 手順2 は「実績のうち `key` を持つものを収集し、そのキーを持つ予定インスタンスを予測から除外する」ため、読み込まれなかった実績が持っていたキーは集合に入らない。**消し込み済みの予定が未消し込みとして復活し、予定額のまま残高から引かれる。** 残高が低く出るので、生活防衛ラインの警告も同時に狂う。

- エラーが出ない
- 画面にも異常が出ない
- 残高は「それらしい値」で表示される
- 利用者に気づく手段がない

月100件の利用者なら10ヶ月で1000件に達する。モニター配布前に見つかった。

要件定義書 §5.1 は「1ユーザーあたり実績10万件まで劣化しないこと」を挙げているが、劣化以前に**正しさが壊れる**。

一方で、そもそも全期間を読む必要があるのかという問いがある。CL-3 の開始残高は基準日時点の残高として定義されており、FR-40 で「基準日より前の月は参照しない」と決めた。基準日より前の実績は、残高計算にも一覧にもグラフにも使われない。

## 判断

取得側に4つを課す（FR-47、§5.1.2）。

**1. 範囲を基準日で切る。** 実績と単発予定は `date >= asOf` で絞る。そのために `loadAppData` を2段階にし、先に `settings` を読んで基準日を確定させてから残りを読む。

**2. 順序を固定する。** `date` 昇順、同日は `id` 昇順。日付を持たないテーブルは `id` のみ。

**3. 分割して取得する。** 上限を超える件数は `range()` で分けて全件取る。**進める幅は受け取った件数ぶんとし、`PAGE_SIZE` ぶんではない。**

**4. 切り捨てを検知する。** `count: "exact"` で総件数を取り、受け取った件数と一致しなければ `IncompleteLoadError` を投げる。アプリは画面を出さず、再試行の手段を示す。発生を `load_incomplete` イベントに件数だけ残す。

## 理由

**範囲を基準日で切るのは、性能上の工夫ではなく計算の定義から従う制約である。** CL-3 が基準日より前を参照しない以上、読む理由がない。性能改善として入れると「速さのために精度を捨てた」と読まれるが、そうではない。副次的に「実績10万件」が蓄積総量ではなく基準日以降の件数を指すことになり、締め処理（OI-6）で読み込み範囲を縮められる。

**順序の固定は分割取得の前提条件である。** PostgreSQL は ORDER BY のないクエリの行順序を保証しない。順序を固定せずに範囲で分割すると、ページの境界で同じ行が2回返り、別の行が1回も返らない。そして**この状態は件数の照合をすり抜ける**。合計件数は一致するのに中身が違う。したがって順序の固定と件数の検知は、どちらか一方では足りない。テストで実証してある（`fetch-all.test.ts`「順序が崩れると、件数が合っていても中身が壊れる」）。

**進める幅を受け取った件数にするのは、サーバー側の上限が `PAGE_SIZE` より小さい場合に行を飛ばさないため。** 0〜999 を要求して100件しか返らないとき、次を1000から取ると 100〜999 が永久に読まれない。実装時にテストがこの穴を捕まえた。

**例外にするのは、間違った残高を見せないため。** 部分的なデータでも残高は計算でき、値が出てしまう。出た値は検証できない。読み込めなかったと伝えて止めるほうが安全である。

ただしこの例外は、ページングが正しく効いていれば**発生しないはずのもの**である。利用者向けの機能ではなく、分割取得のバグを検知するカナリアとして置く。だからイベントに残す。件数だけで、金額・費目名・口座名は入れない（[[0013-利用イベントに金額を入れない]]）。

## 却下した選択肢

**Supabase の Max rows を上げる。** 設定値を上げても効かない・1000で止まるという報告が複数ある（supabase/supabase#33741、#4544）。仮に効いても、別の上限（応答サイズ、タイムアウト）に当たるだけで構造は変わらない。「上限のある API から全件を取る」という問題は残る。

**件数の検知だけを入れる。** 上に書いたとおり、順序を固定しない分割は件数が一致したまま中身が壊れる。検知をすり抜けるので防げない。

**サーバー側でページングし、画面に必要なぶんだけ取る。** 残高計算は全期間の累積なので、画面に見えている範囲だけでは計算できない。クライアント側で計算する設計（[[0003-残高計算をクライアント側で行う]]）を捨てることになる。基準日で切れば取得量は抑えられるため、いまその判断をする必要がない。

**部分的なデータで計算し、警告を添えて表示する。** 資金繰りの判断に使う数字である。「たぶん合っている残高」に価値はない。

## 影響

- `loadAppData` が2往復になる。設定を読んでから残りを読むため、初回表示が1RTTぶん遅くなる
- 基準日より前の実績は読まれなくなる。基準日を過去に戻せば再び読まれるので、データは失われない
- 読み込み失敗時はアプリシェルごと出さない。サインアウトは可能にしてある
- `overrides` は日付で絞れない（予定インスタンスキーで引くため）。件数が問題になるようなら、キーの前方一致で絞る余地がある
