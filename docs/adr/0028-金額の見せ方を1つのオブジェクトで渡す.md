# ADR-0028 金額の見せ方（値・符号・色）を1つのオブジェクトで渡す

- 状態：採用
- 日付：2026-11-11
- 対象：AC-58b、`src/components/sakiguri/amount-view.ts`、キャッシュフロー／ダッシュボード／実績入力の3画面

## 文脈

要件定義書 §3.3 が「**符号はその行がいま見ている範囲で残高をどちら向きに
動かすかで決まる。`type` では決めない**」と決めた（AC-58b）。それまでは
「振替だから符号なし」を `type` で判定していて、**同じ規則が3画面に別々に
書かれていた。**

`Amount` は `signed`（符号）と `type`（色）が別の引数なので、部品に手を
入れる必要はない。**行の側がその2つを決めて渡す**ことになる。

## 決めたこと

**`amountView(...)` が1つで `{ value, signed, type }` を返し、行はそれを
`display` として持つ。**

```ts
const shown = amountView({ amount, delta, category, type });
//=> { value: -77_777, signed: true, type: "neutral" }
```

**行は `amount`（正の額）も別に持ち続ける。**

| 持ち物 | 使うところ |
|---|---|
| `amount` | ［実際の金額］の初期値（`OtherActions`）、操作に渡す額 |
| `display` | 画面に出す値・符号・色 |

**符号の素は `viewDelta`**（`core/balance`）。`accountDelta` を範囲の口座ぶん
足したもので、**残高系列が足しているのと同じ関数**である。

## 理由

**符号付きの値を `amount` に上書きしない。** 実績入力の画面は
`defaultAmount={row.amount}` で［実際の金額］の初期値にしている。ここに
符号付きの値を入れると、**支出の行を開いた瞬間に入力欄が `-95000` になる。**
表示のための変形を、入力に使う値に混ぜてはいけない。

**3つを別々の項目（`amountType` と `signed` と符号付きの額）にしない。**
3つ揃って初めて1つの見せ方になるので、呼び出し側が1つだけ更新できる形に
すると**符号と色がばらばらに古くなる。** 1つのオブジェクトなら、
`amountView` を通さずに作ることが型で難しくなる。

**範囲にカードを入れるかは画面ごとに違う。**

| 画面 | 範囲 | なぜ |
|---|---|---|
| 入出金予定表 | 系列が合計に使った現預金（口座別のときは絞る） | 行ごとの残高がその日の終値に着地する必要がある |
| 実績一覧・やること | 現預金＋カード | 行は**その行の口座**の動きを示す。現預金だけで足すと**カード払いの予定が符号を失う**（合計が動くのは引落日なので delta が0になる） |

`deposits`（振替が合計の中で閉じるかの判定）は**範囲とは別物**として渡す。
範囲で判定すると、銀行→現金の振替を銀行だけで見たときに「閉じていない」と
誤判定される。

## 影響

- **入金の行に `+` が付く。** 規則が「増える行は `+`」なので、振替の入金側
  だけでなく**売上入金なども `+¥330,000`** になる。3画面すべてで変わる
- 合計の中で閉じる振替と、残高に反映していない振替（`oneSided`）は
  **どちらも符号なし。** delta が0だからで、2つを区別していない
  （反映していない理由は明細の備考が言う）
- 行の型から `amountType` が消え、`display` になった。Figma と見比べる
  ための固定値のページ（`/dev/screens/cashflow`・`dashboard`）も同じ形で
  書く ―― **ここが本番と違う形だと、見比べる相手が本番ではなくなる**
