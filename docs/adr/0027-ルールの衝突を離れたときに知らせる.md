# ADR-0027 ルールの衝突は、入力欄を離れたときに知らせる

- 状態：採用
- 日付：2026-11-10
- 対象：AC-57f、`src/components/settings/RulesTable.tsx`、`src/core/csv.ts`

## 文脈

仕分けルールは、当たる条件 `(pattern, accountId, direction)` が一意である
（要件定義書 §3.2 ImportRule）。DB に一意索引を張るが、仕様は
**「画面は衝突を保存前に知らせること（DB のエラーを出さない）」**とも書いている。

ところが設定のルール表は、**一打ごとに `updateRule` で `data` を書き換える**
作りだった。保存という段が無いので、衝突する `pattern` を打った瞬間に保存が
走り、**DB の一意制約違反として返ってくる。** 利用者には何が衝突したのか
分からず、画面には通らなかった値が残る。

## 決めたこと

**当たる条件を変える操作だけ、適用の前に `ruleConflict` を通す。**
通らなければ**値を当てない**（画面も元に戻す）。

`pattern` は**打っているあいだは行の手元に置き、入力欄を離れたとき**
（blur / Enter）に確かめて適用する。

```tsx
const applyPatch = (patch: Partial<ImportRule>): boolean => {
  const reason = ruleConflict({ ...rule, ...patch }, others);
  if (reason) { setMessage(reason); return false; }
  setMessage(null);
  onPatch(patch);
  return true;
};
```

費目を変える操作も通す。**資金移動でなくなると `direction` が落ちるので、
費目を変えただけで当たる条件が変わりうる。**

## 理由

**一打ごとに確かめると、打ち切れない文字列ができる。** `ﾃﾞﾝｷ` のルールが
ある状態で `ﾃﾞﾝｷﾀﾞｲ` を打つと、**途中の `ﾃﾞﾝｷ` で弾かれて先に進めない。**
通らない値を画面に出さない作りと、途中の状態を通す作りは両立しないので、
**確かめる時点を「離れたとき」に移す。**

**判定は core の `ruleConflict` 1つ。** 画面に書くと、設定画面と取込の
確認画面で違う組み合わせを通す（CLAUDE.md §2.8）。同じ関数が
`sameMatchKey` を使い、`addRule` と DB の索引も同じ組み合わせを見る。

## 却下した選択肢

**保存ボタンを置いて、行全体を下書きにする。** 設定の他の表（口座・定期項目・
単発）はすべて一打ごとに保存する作りで、**ルールの表だけ保存の作法が変わる。**
利用者は「ここだけ保存を押す必要がある」ことを覚えることになる。

**衝突したまま保存して、DB のエラーを画面に出す。** 仕様が禁じている。加えて
エラーの文面は PostgreSQL のもので、どのルールと衝突したかを言わない。

**`pattern` の重複を許し、勝ち負けを `id` で決める。** 当たる条件が同じ2件は
**画面から見分けられない。** どちらが効いているか分からないルールが残る。

## 影響

- 当たる条件を変える操作が**失敗しうる**ようになった。失敗したことは行の下に
  理由として出る（`colSpan` の1行）
- `ruleConflict` の第2引数は省略できる。渡さなければ重複は見ない ――
  取込の確認画面はこちらを使う（`addRule` が同じ条件のルールを差し替えるので、
  重複が作られない）
- `pattern` の前後の空白は落として比べる。**DB は落とさないので、画面のほうが
  厳しい。** 厳しい側のずれは「知らせる」で済み、DB のエラーにはならない。
  文字種の正規化は OI-22
