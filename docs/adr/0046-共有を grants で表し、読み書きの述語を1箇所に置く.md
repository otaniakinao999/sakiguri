# ADR-0046 共有を `grants` で表し、読み書きの述語を1箇所に置く

日付：2026-11-16
関連：FR-23・FR-31・FR-67、AC-76〜AC-83、CLAUDE.md §2.5・§2.5.1・§2.8・§2.11、ADR-0045

## 文脈

共有を v1.0 に前倒しした（v1.58）。**モニター配布より前に入れる** ――
8表の所有の述語を書き換える作業は、利用者が実質1人のいまと、他人の
資金繰りが入ったあととで危険度が桁で違う。

設計は artifact「権限とアカウント」の案A。

## 判断

### 1. 所有は人のまま。表を1つ足す（AC-76）

`user_id` を `workspace_id` に差し替えない。**実データが入っている上で
所有の列を変えるのは、この案件で最も危険な種類の変更である**（§2.5.2）。
制約9 が事務所向けの横断画面を対象外にしているので、帳を人から切り離す
利きが無い。

マイグレーション 0011 は**表2つと列1つの追加、ポリシーの緩和だけ**で、
`grants` が0行のあいだ**挙動は現状と完全に同じ**である。

### 2. 述語を関数に切り出さない

読みやすさでは `can_read(user_id)` が勝つ。採らなかった理由は性能である。

**`set search_path` を付けた SQL 関数はインライン展開されない。**
展開されないと行ごとに関数を呼ぶので、**実績10万件（§5.1）で10万回**に
なる。`set search_path` を外せば展開されるが、それは
`security invoker` でも Supabase の検査が警告する形である。

代わりに**マイグレーションの中の2つの文字列**を7表に展開する。7回
書き写すのと違い、**1つだけ違う式になることが起こりえない**（§2.8）。
末尾で 7×4＝28本を数える。

**`in (select ...)` にしてある。** `grantee_id` だけで絞るので相関せず、
1回で済む。`exists (... and g.owner_id = user_id)` と書くと行ごとの
相関になりうる。

### 3. `for all` を4本に割る

1本のままだと、**閲覧の客に書き込みを許すか、客に読み込みを許さないか**の
どちらかになる。select は閲覧以上、insert / update / delete は編集だけ。

### 4. 受諾だけ `security definer`（AC-78 と AC-79 の継ぎ目）

**この2つは、素直に読むと両立しない。**

| | |
|---|---|
| AC-78 | `grants` への書き込みは `owner_id = auth.uid()` のときだけ |
| AC-79 | 招待は相手が**自分で受け取る**（`email = auth.jwt() ->> 'email'`） |

受諾は `grants` に1行作る操作で、**作るのは客**である。つまり
`owner_id ≠ auth.uid()` の書き込みが要る。§2.9 の形なので、優先順位を
決めずに両方を素直に実装すると、**AC-78 を緩めて客に書かせる**ことになる。

**関数の中でだけ権限を上げる。** `accept_invite(invite_id)` が
`security definer` で、作れるのは「自分のアドレスに宛てて、**持ち主が
出した**、まだ受諾していない招待」に対応する1行だけである。
**持ち主の意思は招待の行で既に表されている**ので、AC-78 の趣旨
（持ち主が知らない人が帳を見る状態を作らせない）は保たれる。

**直接の insert は依然として弾かれる。** `pnpm loadtest:sharing` の
「客は `grants` を書けない」がそれを測る。

**失敗の理由を分けない。** 「招待が無い」と「自分宛でない」を分けると、
招待の id を総当たりして存在を試せる（AC-79 と同じ理由）。

### 5. `created_by` は `on delete set null`

artifact の下書きは動作を書いていない。既定（no action）だと
**代行者のアカウントを消せなくなる。** 消えて困るのは実績の行であって、
誰が入れたかの印ではない。AC-80（失効しても実績が残る）と同じ向きで
決めた。

### 6. AC-80 は列の設計で守り、**適用時に数える**

`grants` から `actuals` への外部キーが1本でもあれば、失効で実績が消える
経路ができている。マイグレーションの末尾で `pg_constraint` を数える ――
**テストではなく、当たった瞬間に落ちる形**にする。

## 却下した選択肢

### `usage_events` にも共有の分岐を入れる

退けた。誰も select できない表なので**述語を足しても何も変わらず**、
「共有の対象」という誤解だけが残る（ADR-0045）。7表に限る。

### 招待のときにアドレスから `user_id` を引く

退けた。**誰でもアドレスの存在を試せる**（AC-79）。招待はアドレスを
そのまま保持する。

## 影響

- マイグレーション 0011。**後方互換**なので、適用してからデプロイする
  （§2.5.1）。書き出しは要らない（§2.5.2 の危うい形に入らない）
- **まだ適用していない。** ポリシーを入れる前に `pnpm loadtest:sharing` の
  基線を取ると決めており（ADR-0045）、2つ目の負荷試験アカウントが
  メール確認待ちで流せていない
- **`usage_events` は手付かず**。適用時に本数が変わっていないことを数える

## 客はどの帳を見るのか（2026-11-17、AC-84 で決まった）

**守りは切り替え器ではなく常時表示である。** 防ぎたいのは「代行者が別の
顧客の帳に実績を入れてしまう」ことで、**入れたあとに気づくのでは遅い。**
間違った相手を招待するのは取り消せるが（AC-83）、間違った帳に入れた記帳は
取り消しにくい。

| | |
|---|---|
| 置き場所 | **ワードマークの隣**（`Sidebar` の `items-baseline` の行）。狭い幅では横並び、広い幅では縦積みなので、**どちらの幅でも識別と一緒に動く** |
| 口座の隣に置かない | **口座は帳の中にあり、兄弟ではない** |
| 自分の帳 | **何も出さない。** 付与が0件の利用者はいまの画面と同じに見える |
| 既定 | 自分の帳 |

**選んだ帳は利用者と対で持つ**（`{ userId, ownerId }`）。`activeOwnerId`
だけを状態にすると、**利用者が変わった瞬間に前の人の帳を指したまま1回
読む。** 検査が3回目の読み込みとして捉えた。

**入口は設定の「渡されている帳」。** 守りではないので目立たせない。

### `invites` に `grantee_id`、`grants` と `invites` に `owner_email`

どちらも下書きに無い。**無いと画面が作れない。**

- **`owner_email`。** 客に出す帳の名前（AC-84）。`auth.users` は RLS 越しに
  引けないので、**引く代わりに持つ。** 持ち主自身のアドレスで、渡す相手を
  持ち主が選んでいる以上ここに持って差し支えない
- **`grantee_id`。** 持ち主の一覧はアドレスで並ぶが、失効には `grants` の
  主キー（持ち主, 相手）が要る。受諾のときに結んでおく
