# 0002. 日付を 'YYYY-MM-DD' の文字列で持つ

## 文脈

このプロダクトの計算は日付の境界判定に依存している。

- カード引落日は「利用日の日 ≤ 締日」で締め月が変わる（CL-2）
- 入金予定日も同じ構造を持つ（CL-9）
- 定期項目の `day = 31` は各月の末日に寄せる（CL-1、AC-02）

`Date.prototype.toISOString()` は UTC 変換を伴う。JST の `2026-09-01` は `2026-08-31T15:00:00Z` になり、日付が1日前にずれる。月末判定が絡むため、ずれると締めと引落の判定が壊れる。PoC開発計画 §5.3 は「AIは `toISOString()` を無意識に使う」と指摘している。

## 判断

日付は **`'YYYY-MM-DD'` の文字列**で保持する。

- 型は `DateStr = string`
- `Date` オブジェクトは月末計算などの内側だけで使い、境界では必ず文字列に戻す
- UTC 変換を伴う API（`toISOString`、`Date.UTC`、`getTimezoneOffset` 依存の計算）を使わない
- JST 固定で扱い、タイムゾーンを設定項目にしない

## 理由

`YYYY-MM-DD` は**辞書順が時系列順と一致する**。前後判定が `a <= b` で書け、整列が `localeCompare` で済み、年月の切り出しが `slice(0, 7)` で終わる。`getTime()` の差分計算が要らないため、タイムゾーンが入り込む経路そのものが無くなる。

要件定義書 5.5 は言語・通貨を日本語・日本円のみに限定している。多タイムゾーンの要求がないため、JST 固定の単純さを取れる。

## 却下した選択肢

**`Date` オブジェクトで保持する。** `toISOString()` を呼ぶ経路が残り続ける。等価判定に `getTime()` が要るため、時刻成分が混入していても気づけない。プロトタイプはこの方式で、`new Date()` のローカル時刻に依存している。

**dayjs / date-fns を入れる。** CLAUDE.md §2.7 が明示的に除外している。ライブラリを入れると、この規約の担保がライブラリのタイムゾーン既定設定に移る。設定を1行変えるだけで全体がずれる構造になり、規約が壊れたことを検知しにくい。

**UNIX タイムスタンプで保持する。** 時刻成分を持つため「同じ日か」の判定にタイムゾーンが必要になる。解こうとしている問題がそのまま残る。

## 影響

- `src/core/` の日付型は `DateStr`
- `ymd(d: Date): DateStr` と月末計算のユーティリティを1箇所に置き、CL-2 と CL-9 の両方から呼ぶ。両者は同じ構造の計算であり、実装が分かれると片方だけ壊れる（PoC開発計画 §5.6）
- 現在日時は引数 `today: DateStr` で受け取る。`new Date()` を core 内で呼ばない（[[0003-残高計算をクライアント側で行う]]）
- サーバー側・マイグレーションでも同じ規約に従う。Postgres の型は `date` を使い `timestamptz` を使わない
