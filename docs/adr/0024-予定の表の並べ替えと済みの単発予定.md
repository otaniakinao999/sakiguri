# ADR-0024 予定の表の並べ替えと、済みの単発予定の隠し方

- 状態：採用
- 日付：2026-11-02
- 対象：`SC-07 予定の設定`（`RecurringTable` / `OneoffsTable`）

## きっかけ

利用者から2つ。

1. 項目が増えると見るのが大変なので、**実績が登録されたものはアーカイブ**されてほしい
2. **予定のソート**ができると良い

どちらも、このADRを書いた時点では要件定義書に対応する FR が無かった。
**2026-11-05 に起こした**（要件定義書 v1.34）。

| | |
|---|---|
| FR-48 | 予定の表の並べ替え（高 / v1.0） |
| FR-49 | 実績が付いた単発予定を既定で隠し、切り替えで表示できること（高 / v1.0） |
| AC-54 | **値の編集で並びが崩れないこと。** 決め直すのは見出しの操作と行の増減だけ。増えた行は末尾。同値の相対位置が一意 |
| AC-55 | **既定で出さず切り替えで出せること。** 消さない。隠した件数を同じ場所に。定期項目は対象外。判定は実績の `key` から引き、予測に含まれないことで判定しない |

SC-07 の構成にも並べ替えと「実績が付いたものは既定で隠す」を書き足した。

## 決めたこと（1）並べ替えは「いつ決め直すか」を明示して持つ

**毎描画で並べ直さない。** 見出しを押したときと、行が増減したときだけ
順序を決め直す。順序は id の配列で覚え、**値が変わっても動かさない。**

### なぜ

設定の表は**常時編集できるグリッド**で、並べ替えの基準になる列も編集
できる。`onChange` は1打鍵ごとに `data` を書く。だから素朴に
`[...rows].sort(compare)` を描画のたびに評価すると、**打鍵のたびに行が
動く。**

**これは新しい問題ではない。** 単発の予定は以前から日付の昇順に並べて
いて、日付欄は編集できた。つまり**並べ替えを足す前から、日付を直すと行が
動いていた。**

実機で素朴な実装に戻して測ったところ、こうなった。

| 測ったこと | 素朴な実装 | いまの実装 |
|---|---|---|
| 金額を打ち替えたときの並び | 行が末尾へ移る | 動かない |
| 日付を打ち替えたときの並び | 行が末尾へ移る | 動かない |
| `9999999` と1文字ずつ打った結果 | **`9100` になった** | `9999999` |

3行目が実害。**行が動くと、続きの打鍵が別の行に入る。** 11項目中6項目が
落ちた（`verify-sort.mjs`。手順は下記）。

### 作り

- `src/lib/plan-order.ts`（純関数）
  - `comparePlans` — 列ごとの比較。**同値は必ず id で割る**（要件定義書
    §6.2 の「並び替えキーが一意であること」と同じ理由）
  - `freshOrder` — 押したときに今の値で並べる。**ここだけが並べ直す**
  - `applyOrder` — 覚えている順序のまま、いまある行を並べる。
    **id の集合だけを見る。値は見ない**
- `src/components/settings/use-plan-order.ts` — 2つの表で同じ仕掛けなので
  1箇所に置く（CLAUDE.md §2.12）

**覚えている順序は実体化する。** 算出しただけで覚えずにいると、
`applyOrder` の「覚えている順序が空なら全部並べる」が毎描画で働いて、
結局毎描画で並べ直す（＝直したかった挙動に戻る）。描画のあとに覚え直す。
`applyOrder` が冪等なので1回で落ち着く（テストで固定した）。

### 併せて決めたこと

- **増えた行は末尾に出す。** 並べ込むと、追加した直後の空行が表の
  真ん中に入って見つからない
- **定期項目の既定を発生日の昇順にした。** これまでは登録した順で、
  月の支払いを追うときに見る順と違っていた
- 費目は**コードの昇順**（要件定義書 §3.1.2 適用規則3）。表示名で並べない
- 口座は**口座の表示順**。名前順にするとプルダウンと食い違う

## 決めたこと（2）済みの単発予定は、消さずに隠す

実績が付いた単発の予定を既定で隠し、「済みも表示」で出せるようにする。

### なぜこの形か

- **消さない。** 片道で消すと、間違って登録した実績を直す道が画面から
  消える。隠すだけなら戻せる
- **定期項目は対象にしない。** 毎月くり返すので、1回ぶんの実績が付いても
  終わらない。定期項目に効くのは並べ替えのほう
- 見出しの件数は**全件のまま**にして、横に「実績が付いた N 件を隠して
  います」と出す。件数が減ると、消えたように見える

### 判定の仕方

**予測（`unmatchedForecast`）に無いことでは判定しない。** 予測は期間で
切ってあるので、**基準日より前の単発予定はそもそも展開されず、「済み」に
倒れてしまう**（§9.1：測る側が通る方向に間違っている）。

実績の `key` から引く（`src/lib/settled-plans.ts`）。キーの形を読むのは
`planKeySource` に任せる（CLAUDE.md §2.8）。

## 確かめ方

- 純関数：`plan-order.test.ts`（19件）、`settled-plans.test.ts`（7件）
- 実機：クラウドに写してビルドし、Playwright で操作した
  - `verify-sort.mjs` 11/11。**素朴な実装に戻すと 6件落ちることを確認**
  - `verify-archive.mjs` 12/12（済みの実績を持つ fixture を写しにだけ置いた）

**dev の fixture は、そのままでは差を出せない**（単発の予定1件・済み0件）。
並べ替えは画面の［＋追加］で行を足して測り、アーカイブは写しの fixture に
実績を1件足して測った（§2.11：留め具が差を出せる状態で通す）。

## 本番で確かめたこと（2026-11-07）

負荷試験アカウント（定期50件・単発40件）で6項目を実測し、全件通った。
**素朴な実装なら落ちるデータで通している。**

| 確かめたこと | 落ちうる条件があったか |
|---|---|
| 打ち替えても行が動かない | `9` は表の最小より小さく、`9999999` は最大より大きい。**素朴なら1打鍵目で先頭、最後に末尾へ動く**。実際は7打鍵すべて同じ行に入った |
| 発生日の昇順・同値の一意性 | 同じ発生日が**22件重複**した状態 |
| 増えた行が末尾 | 新しい行は今日・0円で表の最小より小さい。**素朴なら先頭に来る** |
| 済みを隠す／出す | 40件中7件を消し込んだ状態。**隠す側と出す側の両方が非0** |
| 0件の文言 | 全件を済みにして、**登録が無いときの文言と区別できる**ことまで見た |

### 並び順は保存しない（仕様）

追加した行は**その場では末尾**に出るが、**再読み込みすると並べ替えの位置に
移る。** 覚えている順序は `useState` なので保存されない。

**これは意図どおりとした。** 「末尾に置く」は、いま足した行を見失わない
ための**追加した時点の規則**であって、その行の定位置を決めるものではない。
入力し終えた行が、次に開いたとき並びの中にあるのはむしろ正しい。
AC-54 の条項にこの範囲を書き足した。

### 負荷試験データがこの条項を試せなかった

`scripts/loadtest/seed.ts` は実績を**全件 `plan_key = null`** で作っていた。
そのため `settledOneoffIds` が空集合になり、**AC-55 は対象行0件のまま
全条項が通る**（§2.11 の3つ目の形）。本番の確認は手で実績を結んで補ったが、
**seed にその口が無いままだと、次に測る人が同じ空振りをする。**

`--settled=N` を足した（既定7、0〜40）。`--rows` のぶんは従来どおり全件
`plan_key = null` のままで、候補照合の総当たりは変えていない。消し込む
実績は**消し込み先の単発予定に金額・日付・費目を合わせる**（合わせないと
予実の差が実在しない理由で出て、別の条項の計測を濁す）。
消し込み済みの件数は**展開した予測から引く**（「`--settled` 件だから N 件」
と書くと、単発予定の日付が予測の期間から外れたときに合わなくなる）。

### その `--settled` が、減る方向に効いていなかった（2026-11-09）

**足した口そのものが壊れていた。** 実績を `upsert` するだけだったので、
7件入れたあとに `--settled=0` を流しても**前の7件が残る。**

| | seed の出力 | DB の実際 | 画面 |
|---|---|---|---|
| 既定 | `7 / 33` | `o:` つき7件 | 添え書き「7件を隠しています」 |
| `--settled=0` | **`0 / 40` 隠す側を試せない** | **`o:` つき7件（残っている）** | **添え書きが出たまま** |

**いちばん悪いのは出力が事実と逆だったこと。**「試せない」と書いてあるのに
実際は隠れている。**次に測る人は画面ではなく出力を信じる**ので、
空振りを知らせるつもりの行が、空振りを隠す行になっていた。

直しは2つ。

1. **入れる前に、前回ぶんを消す。** `plan_key` が `o:` で始まる実績を消す。
   **id の形では消さない** ―― 「`--settled` が作った行」を id に埋めると、
   画面から消し込んだ実績が残って同じずれが出る。消したいのは「単発予定を
   消し込んでいる実績」そのもの。`--rows` のぶんは全件 `plan_key = null`
   なので当たらない
2. **集計を DB から読む。** 「`--settled` 件だから N 件」をやめ、実際に
   入っている行を数える。1 で揃うはずだが、**揃っていることを出力に
   頼らせない。** 食い違ったときは「`--settled=N` と食い違う」と出す

### 書いた順序が逆だった

`docs/受入基準の充足状況.md` に **AC-55「負荷試験データでこの条項を試せる」を
「済」で載せたのは、実投入の前だった。** 載せた時点で確かめていたのは型検査と
引数の境界だけで、**依頼に書いた確認手順そのもので落ちた。**

§3.1 の「条項を破りうるデータが存在した状態で通ったことを確かめる」は、
**留め具を足したときの留め具自身にも効く。** 2026-11-09 に実機「未」へ
取り下げ、直したうえで実投入してから「済」にする。
