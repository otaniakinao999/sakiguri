# 将来変わりうる列

**いま対処するものではない。** 把握のための一覧。実データが入ったあとに消す・名前を変える・型を変えると、戻せないものが出る。どこにその risk があるかを先に書いておく。

変更するときは CLAUDE.md §2.5.2（書き出し → 行数の確認 → 件数を伝える）に従う。**使わなくなった列は消さずに残してよい。**

対象：`supabase/migrations/0007` までのスキーマ

---

## 高い

### `actuals.plan_key` / `overrides.plan_key`（列ではなく、中身の形式）

```
r:<定期項目の uuid>:<YYYY-MM-DD>     定期項目の第N回
o:<単発予定の uuid>                   単発予定
```

**列を変えなくても、この形式を変えた瞬間に既存の全行が意味を失う。** 消し込み済みの実績が未消し込みに戻り（CL-3 手順2 は `key` の一致だけで除外する）、オーバーライドは「元の予定が見つかりません」になる。

形式を知るのは `recurringKey` / `oneoffKey` / `planKeySource` の3関数だけにしてあるので、**コードは1箇所で直せる。直せないのは保存済みの行のほうである。**

変えるなら、マイグレーションで既存の `plan_key` を新形式に `update` する。新旧を見分ける手段（接頭辞）を残すこと。

変わりうる場面：定期項目の繰り返しが日付以外（週次・隔月）を持つようになったとき。いまの形式は日付1つで第N回を表している。

### `actuals.unplanned`（boolean）

いまは「予定に対応しないと利用者が確定したか」の真偽値。`key is null` には「**まだ判定していない**」と「**判定した結果、突発だった**」が混ざっており、この列は後者だけを立てている。

OI-16（`key` を持たない実績と未消込の予定が同一取引を指す場合の扱い）と OI-4（自動スキップ）を v1.5 で決めると、**状態が3つ以上になって enum 化する可能性がある。** boolean → text は型変更で、`false` が「未判定」なのか「予定あり」なのか、移行時に決める必要がある。

### `accounts.unbilled_balance`

基準日時点の、次回引落に含まれないカード利用額（CL-2 手順4）。**`payMonthOffset = 2` のカードでは未払が3束になるが、いまは2項目で近似している**（OI-19）。

OI-19 を「引落日ごとの内訳入力」に倒すと、この列は単一の数値では足りなくなる。別テーブルか jsonb に置き換わる。

## 中くらい

### `recurring_items.months`（smallint[]）

`null` が毎月、配列が指定月。**週次・隔週・隔月を入れるなら、この表現では足りない。** `frequency` 列を足して `months` を残す形にできるので、消さずに済む可能性は高い。

空配列が入ると予定が1件も出なくなるため、AC-21 で `months: []` を作らないことを保証している。表現を変えるときはその保証も移す。

### `type` の check 制約（3テーブル）

```sql
check (type in ('income', 'expense', 'transfer'))
```

`recurring_items` / `oneoff_items` / `actuals` の3つに同じものがある。**種別が増えると3箇所を直す。** 制約の緩和（値を足す）は安全だが、値を減らす・名前を変えるのは既存行に当たる。

`cost_type`（`fixed` / `variable`）と `accounts.kind`（`bank` / `cash` / `card`）も同じ形。

### 費目コード（`category_code`。列ではなく値）

3テーブルが同じ列を持つ。**コードを消す変更は、その費目を使っている行を先に数える**（CLAUDE.md §2.5.2）。

```sql
select 'actuals' as t, category_code, count(*) from public.actuals         group by 1,2
union all
select 'recurring',     category_code, count(*) from public.recurring_items group by 1,2
union all
select 'oneoff',        category_code, count(*) from public.oneoff_items    group by 1,2
order by 1, 2;
```

コードではなく**表示名**を変えるのは安全である。コードで保持して名前で突き合わせない設計にしてあるため（`src/core/categories.ts`）。

### `accounts.settle_account_id`

カードの引落元口座。**外部キー制約が無く、nullable。** 引落元の口座を消したときに空になりうるので、そう作ってある（`toAccount` が `?? ""` で受ける）。

将来ここに外部キーや NOT NULL を足すなら、既存の null と、存在しない口座を指している行を先に数える。制約の追加は既存行に当たる変更である。

## 低い

| 列 | なぜ低いか |
|---|---|
| `settings.last_reconciled_at` | FR-43 の警告のためだけに持つ。閾値の調整（OI-20）では列は変わらない。消し込みの履歴テーブルを作れば不要になるが、残しておけば害はない |
| `overrides.note` | 繰延の理由。画面で表示・編集している。消す理由が無い |
| `biz_ratio`（smallint 0〜100） | 小数の按分が要れば型変更だが、§2.1 が整数で扱うと決めている |
| `created_at` / `updated_at`（全テーブル） | 読んでいない（`SELECT` の列からも外した）。**だからこそ消す理由も無い。** 消すと行がいつ入ったか分からなくなる |
| `usage_events.props`（jsonb） | スキーマレス。イベントが増えても列は変わらない |

---

## v2.0 で増えるもの（既存列は変わらない）

借入（CL-8）と売掛金（CL-9）はテーブルの追加になる。既存の列には当たらない。

ただし §7 制約3 のとおり、**いまは借入返済を定期項目1件として登録している。** CL-8 を入れるとき、その定期項目を新テーブルに移すか、そのまま残すかを決める必要がある。移すなら既存行の付け替えが要る。
