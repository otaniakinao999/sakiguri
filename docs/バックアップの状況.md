# バックアップの状況

要件定義書 §5.2 は「日次でバックアップし7日分を保持する」。**実データを入れる前に、これが実際に有効かを確かめる。**

---

## 確認手順（2分）

Supabase ダッシュボード → 対象プロジェクト → 左メニュー **Database** → **Backups**

| 見えるもの | 意味 |
|---|---|
| 日付の並んだバックアップ一覧 | **有効。** 保持日数を数えて §5.2 の7日と突き合わせる |
| 「Upgrade to Pro」などの案内だけで一覧が無い | **無効。** 下の「無効だった場合」へ |

同じ画面に **Point in Time Recovery** の項目があれば、そこも見る。これは有料のアドオンで、日次バックアップとは別物。

**プランは Settings → Billing で確認できる。**

## プランごとの違い

私の知識では次のようになっているが、**料金と機能は変わるので画面の表示を正とする。**

| プラン | 日次バックアップ | 保持 |
|---|---|---|
| Free | **無し** | — |
| Pro | あり | 7日 |
| Pro + PITR アドオン | あり＋任意時点への復元 | アドオン次第 |
| Team | あり | 14日 |

**Free だと思われる場合、もう1つ別の危険がある。** Free プロジェクトは一定期間アクセスが無いと一時停止される。実データを置いたまま放置すると、停止されたプロジェクトから復帰させる手間が増える。

## 無効だった場合

### 有効にするには

**Pro プランにする**（Settings → Billing → Plan）。これだけで日次バックアップ7日分が付く。要件定義書 §5.2 を満たすのはこれである。

モニターに配布するなら、**配布前に済ませておく。** 他人のデータを預かる状態で自動バックアップが無いのは、§5.2 を満たしていない以前の問題になる。

### それまでの代替

**`supabase/backup/export.sql` を手で動かす。**

全テーブルを1つの JSON に書き出すクエリと、そこから戻す手順を同じファイルに書いてある。SQL Editor に貼って実行し、結果のセルをコピーして日付入りの名前で保存する。

```
sakiguri-backup-2026-10-01.json
```

**書き出したファイルは、この端末の外にも1つ置く。** 端末が壊れるとバックアップごと失う。

代替であって、置き換えではない。

| | 自動（Pro） | 手動（export.sql） |
|---|---|---|
| 頻度 | 毎日 | 思い出したとき |
| 範囲 | データベース全体 | `public` の6テーブルのみ |
| `auth.users` | 含む | **含まない** |
| 復元 | ダッシュボードから1操作 | JSON を貼って SQL を流す |

**`auth.users` を含まないのが一番大きい違い。** プロジェクトごと失った場合、アカウントを作り直すと uuid が変わるので、JSON の中の古い uuid を全置換してから復元することになる。手順は `export.sql` の C に書いてある。

### CLI（`supabase db dump`）は採用しない

一度「`pg_dump` のほうが確実で、パスワードは不要」と書いたが、**これは誤りだった。**

```
$ npx supabase link --help
  --password, -p string    Password to your remote Postgres database.

$ npx supabase db dump --help
  --db-url string          Dumps from the database specified by the connection string
  --password, -p string    Password to your remote Postgres database.
```

`supabase login` はブラウザでの認可で済むが、**それはマネジメント API の認証であって Postgres の認証ではない。** `db dump` の実体は `pg_dump` で、Postgres に直接つなぐ以上データベースのパスワードが要る。渡し方が3つ（`--password` / `--db-url` に埋める / 対話で入力）あるだけで、**パスワードなしで通る経路は無い。**

| 試したこと | 結果 |
|---|---|
| `link --help` / `db dump --help` の flags | どちらも `--password` を持つ |
| `db dump --project-ref … --dry-run`（未ログイン） | アクセストークンの不足で先に停止。パスワードの入力まで到達しない |

**最後まで通していない。** そこから先はサインインが要り、この会話にパスワードを貼らない方針を崩すことになるため、そこで止めた。ただし flags を見れば `pg_dump` にパスワードが要ることは確定しているので、**採用しない判断に必要な情報は揃っている。**

したがって PoC は Dashboard の SQL Editor に寄せる方針のまま、`export.sql` を使う。`auth.users` が含まれないのは引き受ける。
