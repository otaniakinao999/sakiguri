## 2. CL-3 手順4 の用途が書かれていない

**現状**：§3.3 CL-3 手順4（実績系列）の用途が明示されていない。実装は**グラフの線を本日で切るためだけ**に使っており、残高の表示には一切使っていない。

明示がないと、AC-49 で直した「2つの系列を同じ名前で並べる」defect が再発する。

**追記する一文**（手順4 の末尾）：

> 実績系列は**グラフの線を本日で切るためだけに使う。** 画面に出す残高の値には使わない（AC-49）。

## 3. §5.1 が、存在しない締め処理を根拠にしている

**現状**（L728）：

> 総量がこれを超えても、基準日を前に進める操作（締め処理）で読み込み範囲は縮む。締め処理の設計は OI-6 の対象である。

**締め処理は存在しない。** OI-6 は PoC 期の検討対象外で、`asOf` は不変の入力として扱っている。

**差し替える文**：

> 総量がこれを超えても読み込み範囲を縮める仕組みは、現時点で無い。基準日は不変の入力であり、**基準日以降の件数は単調に増える。** 頭打ちを作る設計（締め処理）は OI-6 として v1.5 の検討事項とする。

## 4. OI-6 の期限が実態と合っていない

**現状**（L876）：期限が「v1.0 実装前」。実際には v1.0 に入れない。

**差し替え**：期限を「**v1.5 設計時**」に。

## 5. 「実績10万件」という件数要件の根拠

**現状**（§5.1「同時保持データ量」）：1ユーザーあたり実績10万件。

机上で置いた数字で、現実の3〜20倍。

| | 年間の件数 |
|---|---|
| 個人事業主（月100〜300件） | 1,200〜3,600 |
| ビジネスプラン（月2,000件） | 24,000 |

項目3で「単調に増える」と書き換えるなら、件数は**年数と組で**書く必要がある（「10万件」だけだと、いつの時点の話か決まらない）。

**書き方の案**：

> 1ユーザーあたり、基準日以降の実績 **24,000件**（ビジネスプランの1年ぶん）まで劣化しないこと。長期利用で単調に増えるため、**上限ではなく1年ぶんの目安**として読む。頭打ちの設計は OI-6（v1.5）。

## 6. AC-28b の目標値

**現状**：AC-28b は「5.1 の目標値」（初回表示3秒以内）を参照している。**10万件では未達**（実測。`docs/受入基準の充足状況.md`）。

項目5で件数要件を直すなら、AC-28b の条件も同じ件数に合わせる。10万件のまま残すと、達成する意思のない基準が表に残る。
