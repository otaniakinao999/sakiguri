# v1.5 に送った課題

10万件の負荷試験で見つかったが、**v1.0 では着手しないと判断したもの。**

判断の共通の理由：**モニターの実績は数百件で、どれも効果が出ない。** v1.19 で件数要件を年数から導き直した結果、v1.0 は **3,000件（約1.5年）**、v1.5 は **24,000件（約12年）** になった（要件定義書 §5.1）。以前の10万件は50年相当で、この検討はその数字に引っ張られていた。存在しない利用者のために設計を曲げない。

各項目に**着手条件**を書く。条件を満たさないうちは触らない。

---

## 1. 分割取得の並列化

**何か**：`fetchAll` は `for` ループの中で `await` するので、1,000件ずつ直列に取る。10万件なら100往復が順番に走る。総件数を先に取れば、範囲リクエストを並列に投げられる。

**なぜ今やらないか**：数百件なら1往復で終わる。並列化する対象が無い。

**判断に必要な数字**：`measure-console.js` の D（8ページを直列と並列で比較）。

- 並列が3〜4倍速い → 帯域に余裕がある。効く
- 並列が1.0倍 → 回線が飽和している。**効かない。この項目を捨てる**

**着手条件**：**AC-28b（3,000件で初回表示3秒以内）が実測で未達であり、かつその内訳で往復の待ち時間が支配的であると確認できたとき。** または v1.5（24,000件、AC-28c）の設計時。

**内訳の確認が条件に入る理由**：未達でも、原因が本体の転送量なら並列化では縮まない。実際、10万件のときの28.7秒の内訳は、ヘッダ受信（往復の待ち）が約10.5秒、本体の転送が約18秒だった。**未達というだけで並列化に進むと、効かない対策に AC-35 の再取得規則までセットで抱き込むことになる。** 内訳は `measure-console.js` の B が出す。

**件数を条件にしない理由**：v1.0 の 3,000件は3往復である。ここを並列にして縮むのは2往復ぶん（数百ms）で、3秒の目標に対して測れる差にならない。一方 v1.5 の 24,000件は24往復で、直列だとそれだけで3秒を超えうる。**効くかどうかを決めるのは往復数ではなく、目標値に届いているかどうかである。** 回線が遅ければ3往復でも未達になるし、速ければ24往復でも間に合う。以前の「5,000件」は10万件を前提に「5往復以上」と置いた数字で、根拠が消えている。

**注意**：総件数を最初に1回だけ取ると、取得中に別端末から行が増えた場合に最後の照合が空振りする。**v1.20 の §5.1.2 が「1回だけ再取得し、そこで一致すれば正常とみなす」規則を条件付きで定めている。分離・並列化と再取得規則は必ず同じ変更で入れる。片方だけ入れてはならない。**

**v1.0 では実装してはならない**（v1.20 §5.1.2）。いまは総件数を行と同じ応答から取っているので、比べる2つが同一時点の値であり、この問題自体が起きない。

## 2. 照合の索引（AC-48）

**何か**：FR-46 の候補照合が総当たりで、10万件 × 予定1,160件で **1,015ms**（ローカル再現）。CL-7 の照合条件は金額の完全一致を含むので、金額で索引を張れば実績1件あたり一定回数で済む。

**なぜ今やらないか**：**v1.19 が「v1.0 は総当たりでよい」と明記した**（§5.1・AC-48）。3,000件 × 1,200件 = 360万回。10万×1,160 の 1,015ms から比例で約 34ms の見込み。

**着手条件**：v1.5 の 24,000件（AC-48b）。24,000 × 1,200 = **2,880万回**で、比例なら約 270ms。メインスレッドが止まる領域に入る。

**注意**：索引側は**金額で絞るだけ**にして、最終判定は必ず `planMatches` を呼ぶ。索引に照合条件を書き写すと、条件が増えたときに2箇所に分かれる（CLAUDE.md §2.8）。**総当たりを前提に定数を削る方向（±12日を狭める等）には寄らない。**

## 3. 応答の圧縮

**何か**：読み込みの律速は本文の転送である（`docs/受入基準の充足状況.md`）。応答が非圧縮なら、圧縮を有効にするのが最も安く効く。

**なぜ今やらないか**：**まだ有効か無効かを確認していない。** `measure-console.js` の B が `Content-Encoding` を出す。

**分岐**：

| Content-Encoding | 判断 |
|---|---|
| `(なし)` | **v1.0 で入れる。** 並列化より安く、桁が大きい。この表から外す |
| gzip / br | すでに効いている。この項目は不要。削除する |

**着手条件**：上記の確認が済んだ時点で、どちらかに振り分けて**この項目を消す。** 保留のまま残さない。

## 4. 締め処理（OI-6）

**何か**：基準日を前に進める操作。実績の読み込み範囲に上限を作る唯一の仕組み。

**なぜ今やらないか**：基準日を動かすと、動かす前後で残高の定義が変わる。**計算の定義に触る変更なので、思いつきで入れられない。** 過去の実績が残高計算から外れるため、外した分をどう開始残高に畳み込むかを設計する必要がある。

**現状の帰結**：頭打ちが無い。§5.1 の設計値 2,000件／年で、5年で10,000件、12年で24,000件まで単調に増える。v1.0（1.5年・3,000件）の規模では問題にならない。

**着手条件**：v1.5 の設計時。または、1利用者の基準日以降の実績が **24,000件**（ビジネスプラン1年ぶん）を超えたとき。
