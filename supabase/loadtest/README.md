# 負荷試験のファイル（AC-28a / AC-28b / AC-34 / AC-48）

> ## **スクリプトに移行中**
>
> 投入・削除・AC-34 は `scripts/loadtest/` の Node スクリプトで行う。SQL Editor への貼り付けと `load_user_id` の13箇所の差し替えが要らなくなる。
>
> ```bash
> pnpm loadtest:account    # アカウントを用意する（冪等。1回でよい）
> pnpm loadtest:seed       # 3,000件 / 550日
> pnpm loadtest:ac34       # 重複・欠落・並びの逆転
> pnpm loadtest:teardown   # 行だけ消す。アカウントは残す
> ```
>
> **スクリプトは本人セッションで動く。** RLS があるので負荷試験アカウントの行しか触れない。SQL Editor は service_role で動くため、id を取り違えると実データに当たる。**安全性が構造的に違う。**
>
> **下の SQL はまだ消していない。** スクリプトを実機で通してから消す。それまでは二重に手段がある状態（CLAUDE.md §2.8 の懸念そのものなので、長く置かない）。


**1ファイル＝1回の操作。** ファイルを開いて全部コピーし、Supabase の SQL Editor に貼って実行する。**中から一部を切り出す必要はない。**

| 順 | ファイル | どこで | 何をする |
|---|---|---|---|
| 1 | `01-insert.sql` | SQL Editor | 実績・口座・定期項目・単発予定を作る |
| 2 | `02-count.sql` | SQL Editor | 入った件数を確かめる（3本まとめて実行してよい） |
| — | `dupcheck-console.js` | ブラウザのコンソール | AC-34 重複・欠落・並びの逆転 |
| — | `timeline-console.js` | ブラウザのコンソール | AC-28b 読み込みの回数と時間 |
| — | `measure-console.js` | ブラウザのコンソール | 転送の内訳と圧縮の有無（任意） |
| 3 | `03-cleanup.sql` | SQL Editor | 行を消す（**アカウントは消さない**） |
| 4 | `04-count-after-cleanup.sql` | SQL Editor | 消えたことを確かめる |

最後に、Supabase ダッシュボード → **Authentication → Users** でアカウントを削除する。`usage_events` は on delete cascade で一緒に消える。

ローカル再現（データ不要）は `pnpm bench`（`parse-bench.test.ts`）。

## 実行の前に

### 1. `+loadtest` を含むメールアドレスでアカウントを作る

```
otani.akinao+loadtest1@showtime.design
```

**`03-cleanup.sql` は6テーブルから行を消す。** 実データの入ったアカウントの id を入れて実行すると、その利用者のデータが消える。

取り違えを id の見た目だけで防ぐのは無理なので、**メールアドレスで止める。** `01-insert.sql` と `03-cleanup.sql` の両方の先頭に、`+loadtest` を含まなければ例外にするガードが入っている。

```
ERROR: 負荷試験用アカウントではありません: otani.akinao@showtime.design
```

`+` 付きのアドレスは同じ受信箱に届くので、新しいメールアドレスを用意する必要はない。

### 2. id を調べる

```sql
select id, email from auth.users order by created_at desc limit 5;
```

### 3. `load_user_id` を差し替える

**4ファイルすべてに入っている。計13箇所。**

| ファイル | 箇所 |
|---|---|
| `01-insert.sql` | 1 |
| `02-count.sql` | 4 |
| `03-cleanup.sql` | 1 |
| `04-count-after-cleanup.sql` | 7 |

置換前の値はすべて `00000000-0000-0000-0000-000000000000` なので、**エディタの「すべて置換」で一度に済む。** 手で1つずつ直さない（13箇所あるので必ず漏れる）。

残っていないことは、貼る前にエディタで `0000-0000` を検索して0件になることで見る。

> **`01-insert.sql` と `03-cleanup.sql` は、差し替え漏れでも止まる。** `auth.users` に無い id だからである。
> **`02-count.sql` と `04-count-after-cleanup.sql` は止まらない。** 数えるだけなので、漏れていると「0件」が返るだけになる。**0件を「消えた」と読み違えないこと。**

### 4. 件数を決める

`01-insert.sql` の `row_total` と `span_days`。

```sql
row_total integer := 3000;   -- 作る実績の件数
span_days integer := 550;    -- 何日ぶんに散らすか
```

| 目的 | `row_total` | `span_days` | 測れるもの |
|---|---|---|---|
| v1.0 の目標値 | 3,000 | 550 | AC-34、AC-28b。約1.5年分（§5.1 の形そのもの） |
| ページング | 3,000 | 90 | AC-28a。月約1,000件になり FR-42 の200件閾値を超える |
| v1.5 の目標値 | 24,000 | 4,400 | AC-28c、AC-48b。約12年分 |

**AC-34 に10万件は要らない。** AC-34 が見るのは「API の1回あたり返却上限（1,000）を超える件数で、重複と欠落が起きないこと」である。3,000件あれば3ページに分かれるので、上限をまたぐ経路はそれで通る。

以前は10万件を入れていたが、§5.1 の件数要件が v1.19 で 10万 → 3,000 / 24,000 に書き換わったため、**10万件は要件ではなくなった**（10万件は50年相当。個人事業主の利用期間として想定しない）。

## 注意

**検証用アカウントには入れないこと。** PoC の指標（`csv_imported` の matched / rows 比）に負荷試験ぶんが混ざると読めなくなる。

**UI を通さず直接 insert するので `usage_events` は発生しない。** アプリ側に試験用のフラグを足さずに済ませるための方法である。

**psql のメタコマンド（`\set`）は SQL Editor で使えない。** だから DO ブロックの中で変数を宣言している。

**定期項目を0件にしない。** 実績だけ入れても、CL-1 の展開も FR-46 の候補照合も FR-43 の未消し込み件数も空振りする。`01-insert.sql` は定期項目50件・単発予定40件を一緒に作る。

**ガードを外して実行しないこと。** 止まったときに外したくなるが、外した状態で id を貼り間違えたら実データが消える。
