# 負荷試験（AC-28a / AC-28b / AC-34 / AC-48）

**スクリプトで行う。SQL Editor への貼り付けは要らない。**

```bash
pnpm loadtest:account                        # アカウントを用意する（冪等。1回でよい）
pnpm loadtest:seed                           # 3,000件 / 550日
pnpm loadtest:ac34                           # AC-34 重複・欠落・並びの逆転
pnpm e2e ac28b                               # AC-28b 初回表示（4G・本番ビルド）
pnpm loadtest:teardown                       # 行だけ消す。アカウントは残す
pnpm loadtest:seed -- --rows=3000 --span=90  # 月1,000件にする
pnpm e2e ac28a                               # AC-28a ページングと到達性
pnpm loadtest:teardown
```

**アカウントは恒久。消さない。** 使い捨てにすると測るたびに人の手で作り直すことになる。v1.5 の24,000件でも同じアカウントを使う。

---

## 安全装置が2つある

1. **RLS。** スクリプトは本人セッションで動くので、負荷試験アカウントの行しか触れない。**他の利用者の行には物理的に当たらない。** service_role キーは使わない（あれは RLS を迂回して全利用者の全行を読み書きできる）
2. **メールアドレスの番人。** `LOADTEST_EMAIL` が `+loadtest` を含まなければ、サインインの時点で止まる

以前は SQL Editor に貼る形だった。あれは service_role で動くので、`load_user_id` を1箇所でも貼り間違えると実データに当たる。**スクリプトは原理的に当たらない。** 安全性が構造的に違う。

## 件数を決める

`pnpm loadtest:seed -- --rows=N --span=D`

| 目的 | `--rows` | `--span` | 測れるもの |
|---|---|---|---|
| v1.0 の目標値（既定） | 3000 | 550 | AC-34、AC-28b。約1.5年分（§5.1 の形そのもの） |
| ページング | 3000 | 90 | AC-28a。月約1,000件になり FR-42 の200件閾値を超える |
| v1.5 の目標値 | 24000 | 4400 | AC-28c、AC-48b。約12年分 |

**AC-34 に10万件は要らない。** AC-34 が見るのは「API の1回あたり返却上限（1,000）を超える件数で、重複と欠落が起きないこと」である。3,000件あれば3ページに分かれる。10万件は50年相当で、§5.1 の件数要件から外れている（v1.19）。

## `seed` は測りたい差が出るかをその場で出す

```
測りたい差が出るか（CLAUDE.md §2.11）
  分割取得（1,000件）  通る（3ページ）
  月内ページング（200件）  **通らない**（--span を小さくする）
  振替の純額  生活 -10000 / 事業 10000（どちらも0でない）
  overrides の行  40件（0件だと並び替えキーの一意性を試せない。§9.1）
```

**0件や相殺や閾値未満のまま測ると、条項は通るが何も確かめていない**（要件定義書 §9.1）。作った人が別の日に思い出す形にしない。

実際に3回起きている。振替が口座ごとに相殺して0だった件、`created_at` が全行同じで列を絞った効果が消えた件、`overrides` が0件のまま「全テーブルで並び替えキーが一意」を掲げていた件。
